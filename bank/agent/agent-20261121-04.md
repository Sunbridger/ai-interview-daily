# 运行时参数覆盖被 falsy 吞掉：think=False 与 temperature=0 静默失效怎么定位

## 为什么会有这个问题

Agent 运行时的模型参数通常有多个层级来源：代码里的默认值、模型 profile、任务/用户级 override、以及高峰降级策略。很多实现为了省事写成 `override.get(k) or default` 或 `if not v: v = default`，而在 Python 里 0、0.0、False、空字符串都是 falsy，于是「显式关闭」被当成「没有设置」，直接回落到默认值。这类 bug 的可怕之处在于不报错：think=False 本意是关掉 reasoning 以压首 token 延迟，结果模型继续思考；stream=False 本意是批量聚合，结果还在流式；temperature=0 本意是让评测可复现，结果输出抖动导致回归对比失真。更隐蔽的一层是 None 的双重语义——既可能是「没传」，也可能是「交给 provider 用默认值」，缺少 sentinel 就无法表达三态，再叠加 pydantic 的 exclude_unset/exclude_none 误用，会出现显式 False 被丢弃或显式 None 反向覆盖默认值。

## 怎么做

1. 先取证再改代码：在真正发往 provider 的出口处打印脱敏后的完整 payload，同时打印各层配置对象，逐字段对比「请求层给的」与「最终生效的」。只看配置对象永远发现不了被合并逻辑吞掉的值。
2. 定位合并点：全局搜索 `or `、`.get(...) or`、`if not value` 这类写法，把分散在各处的合并逻辑收敛到一个 resolver 函数，禁止业务代码自己拼 kwargs。
3. 引入三态语义：用 sentinel（如 `UNSET = object()`）或 pydantic 的 `model_fields_set` 区分「未提供」「显式 None」「显式值（含 False/0）」。合并时只跳过 UNSET，显式值一律照写；显式 None 是否下发给 provider 由出口层决定。
4. 显式化合并优先级并绑定作用域：default < profile < request < runtime-policy（降级/限流），override 通过请求对象或 contextvar 传递，绝对不要写全局单例，否则并发请求会互相污染，出现「A 请求的参数跑到 B 请求」。
5. 加防护网：为每个关键字段写参数矩阵单测（unset / None / True / False / 0 五态 × 合并顺序），并对最终 payload 做 snapshot 断言；出口处再加一条断言，例如 think 必须是 bool 或不存在，不允许是 None 混进请求体。
6. 补观测：trace 里记录 effective_params 与 params_source（哪个层级提供了该字段），这样线上出现延迟或成本异常时可以直接归因到某次配置下发，而不是靠猜。

## 关键代码

```python
UNSET = object()

def resolve(defaults, profile, request):
    out = dict(defaults)
    for layer in (profile, request):
        for k, v in layer.items():
            if v is UNSET:
                continue
            out[k] = v          # False / 0 是合法值，不能被 or 吞掉
    return out

# 旧写法：{k: (req.get(k) or v) for k, v in defaults.items()}
# resolve({"think": True}, {}, {"think": False}) -> {"think": False}

from pydantic import BaseModel

class ModelArgs(BaseModel):
    think: bool | None = None
    temperature: float | None = None

def to_payload(args: ModelArgs, defaults: dict) -> dict:
    explicit = args.model_dump(exclude_unset=True)   # 区分「没传」与「传了 False」
    return {**defaults, **{k: v for k, v in explicit.items() if v is not None}}
```

## 真实场景

某项目为压高峰延迟，按任务给支持 thinking 的模型下发 think=False，但上线后监控显示首 token 延迟与 reasoning token 占比几乎没变化。排查路径：先确认降级策略确实命中（策略日志有记录），再把出口 payload 打出来，发现 think 字段实际是 True——实例默认 True，合并时用了 `override.get('think') or default`，False 被吞成默认值。同类问题还出现在批处理任务上：显式 stream=False 未生效仍在流式；以及评测流水线中 temperature=0 不生效，导致同一 prompt 回归结果不可复现、误判为模型退化。修复方式是把分散的合并收敛到一个 resolver + sentinel，并在 CI 里加五态参数矩阵测试与 payload snapshot。

## 面试官追问

1. **Q：** 为什么不能简单用 `is not None` 判断就完事？

   **A：** 因为 None 本身可能是有语义的：调用方可能想显式表达「这一项交给 provider 用默认值」，而「完全没传」应当继承上一层配置。所以要区分三态——UNSET（未提供，继续继承）、None（显式交给下游默认）、具体值（含 False/0，必须透传）。用 sentinel 配合 pydantic 的 model_fields_set 才能无损表达，`is not None` 会把显式 None 和未提供混为一谈。

2. **Q：** 怎么防止这类问题再犯？

   **A：** 三层防护：一是合并逻辑单点化，业务代码不允许自己拼参数；二是 CI 跑参数矩阵测试（unset/None/True/False/0）并对最终 payload 做 snapshot 断言，任何字段语义变化都会让测试红；三是出口处记录 effective_params 与 params_source 到 trace，线上出现「降级没生效」时能一眼定位是哪一层覆盖出了问题，而不是重新发版加日志排查。
