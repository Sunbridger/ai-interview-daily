# 给每个字段都建 named vector 后存储翻了好几倍：多向量集合的成本建模与拆分策略

## 为什么会有这个问题

向量库的实际占用远不止「维度 × 条数 × 4 字节」。一是命名向量的 slot 对齐：部分引擎在同一 collection 内对多路命名向量按最大维度统一分配，小维度向量并不省空间，可选命名的稀疏写入也会被放大；二是每路向量都带一份独立的图索引，HNSW 的邻接表随 m 线性增长；三是 payload 与标量索引、副本数、WAL 与快照会叠加放大。常见错误认知是按理论 raw 字节做容量规划，然后把「多模型对照」「title/summary/content 多路」长期堆在同一个 collection 里，上线后磁盘、内存、快照时间一起失控。

## 怎么做

1. 先做分层估算：raw 向量 + 每路图索引 + 元数据与 payload + 副本 + 快照留存，得出 bytes/point 的量级，再乘写入增速和保留周期。
2. 用实测校准估算：在一个测试 collection 上写入固定批量的点，比较写入前后磁盘增量的差值，得到真实 bytes/point，与理论值比对找出放大来源。
3. 对每路向量做边际收益评估：在评估集上分别移除某一路，看 recall@k 与答案质量的下降幅度，对无增益的路直接下线。
4. 按用途决定布局：需要一次请求内多路召回的（dense + sparse、title + content）放同一 collection 用命名向量；只是离线对照实验或生命周期不同的放独立 collection，便于整体删除与独立重建。
5. 用稀疏向量 + 单路稠密替代「多稠密向量堆叠」，必要时对存量向量做量化或降维，先在小流量验证 recall 损失。
6. 建成本护栏：collection 级存储与增速告警、按租户分片、冷数据下沉，并定期跑一次「删除某路后指标变化」的复盘。

## 关键代码

```python
def estimate_bytes(n_points, named_dims, payload_bytes=256, m=16, replicas=1):
    slot = max(named_dims.values())
    n_vec = len(named_dims)
    raw = n_points * n_vec * slot * 4
    graph = n_points * n_vec * m * 2 * 4
    meta = n_points * (32 + payload_bytes)
    return (raw + graph + meta) * replicas

# 实测校准：写入前后磁盘增量的差值
def measure(client, coll, batch):
    before = client.stats(coll)["disk_bytes"]
    client.upsert(coll, batch)
    after = client.stats(coll)["disk_bytes"]
    return (after - before) / len(batch)

print(estimate_bytes(10_000, {"title": 256, "summary": 768, "body": 1536}))
print("actual bytes/point:", measure(client, "kb", points))
```

## 真实场景

某项目为了做多路召回，对 title、summary、body 以及两个不同 embedding 模型各建一路命名向量，容量按「各路维度之和 × 条数 × 4」估算并申请了磁盘。上线一段时间后发现磁盘用量显著超过预估、节点内存吃紧、快照耗时明显变长。排查路径：统计 collection 的 disk_bytes 与累计写入点数，算出真实 bytes/point，与理论 raw 值对比，发现最小的那路向量占用与最大维度那路基本一致，确认存在 slot 对齐放大；再在测试 collection 上逐路删除做对照，发现其中两路对 recall 几乎无贡献。最终下线无增益向量、把对照实验迁到独立 collection，并把稠密多路收敛为 dense + sparse。

## 面试官追问

1. **Q：** 多路向量召回的结果该怎么融合才不引入新的偏差？

   **A：** 优先用 RRF 这类基于排名的融合，规避不同模型分数量纲不可比的问题；若要用加权分数，必须先做归一化并在一批带标注 query 上调权重；融合之后再过一次 cross-encoder 精排，避免靠融合权重硬扛排序质量。

2. **Q：** 什么情况下应该拆成多个 collection，而不是继续加命名向量？

   **A：** 当各路数据的生命周期或重建频率不同、需要按租户或权限隔离、需要不同的索引参数与量化策略、或需要独立扩缩容与独立删除时，拆 collection 更合适；代价是无法在一次请求里完成跨 collection 多路召回，需要在应用层并行查询再合并，注意超时与部分失败的降级。
