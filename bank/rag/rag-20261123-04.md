# 语义缓存上线后成本降了，却出现答案过时和跨客户串答案：缓存键、阈值与定向失效怎么设计

## 为什么会有这个问题

RAG 的成本与延迟大头在生成侧，语义缓存（对 query 向量做近邻匹配、命中即复用历史答案）是最直接的降本手段。问题在于「query 向量相似」不等于「答案等价」：否定词（要不要 / 需不需要）、时间与版本限定（新政策 vs 旧政策）、实体替换（换成另一个产品名或套餐）、权限范围不同的租户，向量距离都可能很近。常见错误有三类：一是只用单一相似度阈值就上线，没有做实体与约束一致性校验；二是缓存键里只放 query，没带 tenant、知识库版本、prompt 与模型版本，导致越权复用和版本漂移；三是失效策略只有统一 TTL，知识库更新后旧答案还会继续回放很久。另一个隐性错误是把「命中率」当收益指标，没有扣掉命中后的差评与不一致率。

## 怎么做

1. 明确缓存作用域（scope）：归一化后的 query + tenant_id + 权限范围 + 知识库版本 + 模型/prompt 版本，任一维度变化一律视为未命中，从结构上杜绝越权与版本漂移。
2. 做两级判定：先向量近邻取 top-n 候选，再对候选做约束一致性校验——数字、日期、专有实体、否定词方向是否一致，不一致直接跳过，宁可回源。
3. 阈值不靠拍脑袋：构建等价/不等价 query 对标注集，扫阈值看 precision-recall 曲线，按业务错答成本定阈值；高风险类目（计费、合规、合同条款）直接禁用缓存或要求近乎文本级匹配。
4. 定向失效：缓存条目记录其答案引用的 doc_id/chunk_id 集合，文档更新时反查受影响的条目批量删除；统一 TTL 只作为兜底，不作为主要手段。
5. 影子与灰度：先以影子模式只记录「若命中则返回什么」，与线上实时答案比对，统计不一致率与差评率，再放量到低风险类目。
6. 观测口径：同时看命中率、命中后的负反馈率、缓存答案与实时答案的一致率、以及分租户的命中分布，避免某一租户命中异常。
7. 降级设计：缓存层超时或不可用时直接跳过，主链路不受影响；缓存写入异步化，不阻塞首字节响应。

## 关键代码

```python
SCOPE = ("tenant_id", "kb_version", "prompt_version")

def lookup(q, ctx):
    cat = classify(q)
    if cat in NO_CACHE_CATEGORIES:
        return None
    cands = idx.search(embed(normalize(q)), k=5,
                       flt={k: ctx[k] for k in SCOPE})
    for c in cands:
        if c.score < THRESHOLD[cat]:
            continue
        if not constraints_ok(normalize(q), c.query):
            continue
        return CacheHit(answer=c.answer, cite=c.cited_doc_ids)
    return None

def constraints_ok(qn, cn):
    if has_negation(qn) != has_negation(cn):
        return False
    return extract_slots(qn) == extract_slots(cn)

def invalidate(doc_ids):
    for e in idx.scan(flt={"cited_doc_ids": {"any": doc_ids}}):
        idx.delete(e.id)
```

## 真实场景

某项目的问答接口在高峰期成本压力大，接入语义缓存后整体调用量与平均延迟明显下降。随后客服侧反馈两类问题：政策类问题返回的是旧版本说法；个别客户看到明显属于其他客户的方案细节。排查路径：先抽查被判为命中的样本，会发现两条 query 仅产品名不同但相似度远高于设定阈值；再查缓存 payload，发现缓存键里没有 tenant 与知识库版本字段；最后查失效链路，文档更新后条目仍在，只能等统一 TTL 过期。关键指标是对比「缓存答案」与「强制回源答案」的不一致率，以及命中样本的负反馈率——命中率上升但这两个指标同步恶化，说明阈值与 scope 设计有问题，而不是缓存本身不该用。

## 面试官追问

1. **Q：** 命中率涨了但差评也涨了，怎么确认是缓存导致的？

   **A：** 做两组对照：一是影子回源，对命中样本同时算一次实时答案，比对不一致率并按类目拆分；二是按是否命中分桶看负反馈率，若命中桶显著高于未命中桶且集中在特定类目（政策、价格、权限相关），即可归因。再抽不一致样本看相似度分布，判断是阈值过低还是 scope 缺字段。

2. **Q：** 文档更新后，怎么让相关缓存条目及时失效而不是等 TTL？

   **A：** 在缓存条目里落答案的引用来源（doc_id/chunk_id），知识库更新事件触发时按来源反查删除；对无法精确归因的条目按知识库版本整体提升 version 使旧条目自然失效（scope 不匹配），TTL 只做兜底。同时保留一个可开关的「高风险类目不走缓存」白名单用于事故止血。
