01Agent 长任务断点恢复：状态序列化失败与恢复后副作用重放怎么兜底

资深 ｜ checkpoint状态序列化幂等可观测性 ｜ 面经来源 ↗

为什么会有这个问题

框架的 checkpointer 通常把整个 state 字典原样落盘，而运行期很容易把 HTTP client、数据库 session、回调闭包、锁对象这类不可序列化的东西顺手塞进 state，写入时才炸；更隐蔽的是「能存进去但恢复不回来」：类字段改名、枚举值增删、发布回滚导致旧 checkpoint 用新代码反序列化，结果是半恢复的状态继续往下跑。常见误区是认为选个支持 pickle 的存储就解决了持久化，实际上可序列化不等于可恢复、可重放，恢复语义（哪些 step 已完成、副作用是否发生过）和序列化格式是两件事，必须分开设计。

怎么做

  1. 状态分层：把 state 拆成 persistent（纯数据，字段白名单，Pydantic 建模）、runtime（client、连接池、回调，只活在进程内）、derived（可由前两者重算的中间结果）。persistent 里出现非数据对象视为 bug，在 CI 里加一条 state 模型的 JSON 化单测守住。
  2. 写入前守卫并降级：dump 后跑一次严格 JSON 校验，失败时剔除可疑字段、打 degraded 标记并上报指标，而不是让整个 step 抛异常中断任务；degraded 的 checkpoint 要能标识出来，便于后续排查。
  3. 版本化与迁移：checkpoint 必须带 schema_version，加载时走 migration 注册表逐版本升级；无法迁移的直接判为 dead-letter 进重跑队列，禁止「缺字段也硬跑」。
  4. 副作用幂等：用 (thread_id, node, step_seq, tool_name, args_hash) 生成幂等键，工具入口先查已完成记录再执行；发消息、下单这类不可幂等动作改成 outbox 模式，先落库再异步投递，恢复时只补投未确认的记录。
  5. 恢复链路可观测：单独埋 resume_attempt、resume_success、replay_steps、duplicate_side_effect 四个指标，恢复过程用独立 trace/span 标记，和正常执行区分开，否则故障会被平均掉。
  6. 演练：定期做「杀进程 + 回滚版本」的混沌测试，验证恢复路径，而不是等大促发布时才发现。
from pydantic import BaseModel, Field import hashlib, json, logging class AgentState(BaseModel): schema_version: int = 2 thread_id: str step_seq: int = 0 plan: list[dict] = Field(default_factory=list) tool_results: dict[str, dict] = Field(default_factory=dict) scratch: dict = Field(default_factory=dict) def safe_dump(state, checkpointer): payload = state.model_dump(mode='json') try: json.dumps(payload, allow_nan=False) except (TypeError, ValueError) as e: logging.warning('checkpoint_degraded thread=%s err=%s', state.thread_id, e) payload['scratch'] = {} payload['degraded'] = True checkpointer.put(state.thread_id, payload) def idem_key(thread_id, node, seq, tool, args): raw = '|'.join([thread_id, node, str(seq), tool, json.dumps(args, sort_keys=True)]) return hashlib.sha256(raw.encode()).hexdigest()[:32] def run_tool(ctx, name, args): key = idem_key(ctx.thread_id, ctx.node, ctx.step_seq, name, args) hit = ctx.done_store.get(key) if hit is not None: return hit result = ctx.tools[name](**args) ctx.done_store.put(key, result) return result

真实场景

某项目的长链路 Agent 单任务 10~40 步，包含检索、外部工具调用、写工单库，跑在 K8s 上，滚动发布时 Pod 会被杀掉。现象有两类：一部分任务恢复后立刻抛 TypeError，报某个字段不是 JSON 可序列化类型；另一部分恢复是成功的，但把「发送通知」「提交工单」又执行了一遍，用户收到重复消息。监控上 checkpoint 写入成功率接近 100%，但 resume_success_rate 只有六成左右，重复副作用没有独立指标，是靠客诉才发现的。排查路径：先在 dump 前加严格 JSON 校验，定位是哪个节点往 state 里塞了 client 与回调；再对比恢复前后的 step 序列，看哪些 step 没有幂等记录；最后检查旧 checkpoint 缺 schema_version 导致字段错位，恢复出来的 plan 是上一版结构。

    B -- 否 --> C[剔除可疑字段并标记 degraded]
    B -- 是 --> D[写入 checkpoint 附带 schema_version]
    C --> D
    D --> E[服务重启后恢复任务]

    F -- 是 --> H[按 step_seq 重放已完成节点]

    I -- 否 --> K[执行并登记幂等键]

面试官追问

Q：直接用 pickle 把整个 state 存下来不行吗？

A：能存不等于能恢复。pickle 依赖类路径，代码重构一次或回滚一版就解不开；跨语言、跨版本不可读，反序列化本身还是攻击面。生产上应当显式 schema + 版本号，运行期资源不落盘、恢复时重建，宁可多写一点迁移代码，也不要赌类结构不变。

Q：恢复之后怎么确认没有重复执行副作用？

A：两个手段叠加：一是幂等键 + 完成记录表，恢复时以 step_seq 为游标重放，命中记录直接取结果；二是把不可幂等的外部动作收敛到 outbox，先落库再异步投递，恢复只补投未确认的。再加一个 duplicate_side_effect 计数器做兜底观测。

02自报置信度不可信时，Agent 的人工接管闸门该怎么设计

进阶 ｜ HITL置信度校准escalation成本权衡 ｜ 面经来源 ↗

为什么会有这个问题

模型在输出里写的 confidence 是生成出来的一个 token，不是真实的正确概率，在分布外输入和长尾样本上系统性偏高，而且会被 prompt 里的措辞带偏（你要求它保守，它就整体下压，区分度反而更差）。用它当唯一阈值会导致两类错误同时发生：高风险任务给了 0.9 被自动放过，简单任务给了 0.6 被反复转人工，人工队列被低价值请求淹没。本质问题是「用一个未校准的打分去卡一个代价不对称的决策」，正确做法是把自报分数降级成特征之一，先用可验证信号做硬拦截，再用带标签数据把分数校准成 P(correct)，最后按期望损失而不是固定阈值决定是否升级。

怎么做

  1. 先做 hard gate 再谈打分：schema 校验、工具返回码、引用能否解析回原文、金额/权限/必填字段的规则断言，任一失败直接转人工，不进入置信度排序。这一步能拦掉大部分确定性错误，且完全不需要模型自评。
  2. 特征化：把 self_confidence 当作一个普通特征，与 evidence_coverage（检索证据覆盖度）、多次采样的答案一致性、工具调用成功率、同类历史样本通过率拼成特征向量。
  3. 收集标签：每条轨迹记录特征与最终是否正确，标签来自人工复核结果和延迟回填（用户是否二次追问、工单是否被返工）。注意采样偏差，被自动通过的样本也要抽样复核，否则校准器只见过难样本。
  4. 校准与验证：用 isotonic regression 或 Platt scaling 拟合 P(correct)，用分桶准确率和 ECE 验证，确认高分区间的实际准确率确实高；校准器要按 intent/场景分桶训练，全局一个模型常常被大类样本带偏。
  5. 按期望损失定阈值：escalate 当且仅当 (1-p) * cost_error > cost_human，不同意图配不同代价；同时把人工接管分档（轻量确认 / 全量重做），压低单次人工成本，比一味调阈值更有效。
  6. 闭环监控：跟踪 escalation_rate、override_rate（人工推翻模型的比例）、miss_rate（自动通过后被判错的比例）、人工处理时延，定期重训校准器并做漂移告警。
from sklearn.isotonic import IsotonicRegression def features(t): return [[t.self_conf, float(t.schema_ok), float(t.tool_ok), t.evidence_coverage, float(t.samples_agree)]] calibrator = IsotonicRegression(out_of_bounds='clip') # calibrator.fit(X_train, y_correct) def route(t, cost_error, cost_human): if not t.schema_ok or not t.tool_ok: return 'human', 1.0, 'hard_gate' p_err = 1.0 - float(calibrator.predict(features(t))[0]) if p_err * cost_error > cost_human: return 'human', p_err, 'loss_gate' return 'auto', p_err, 'pass'

真实场景

某项目的工单处理 Agent 在输出 JSON 里带一个 confidence 字段，规则是低于 0.8 转人工。上线后两个现象同时出现：自动提交的工单里仍有一批分类错误，这些错误样本的自报值普遍在 0.9 以上；同时大量简单咨询被转人工，人工队列积压、SLA 变差。翻日志发现 confidence 分布几乎挤在 0.85~0.95，几乎没有区分度。排查路径：把历史轨迹按最终是否正确做标注，画 reliability diagram，发现高置信区间的实际准确率远低于自报值；再算各信号与结果的相关性，发现工具返回码和 schema 校验的区分能力明显强于自报分数，于是改成硬信号先拦、校准分数后判。

flowchart TD
    A[Agent 产出结果与自报置信度] --> B{硬信号是否通过}
    B -- 否 --> C[直接转人工并记录原因]
    B -- 是 --> D[组装特征并计算校准后错误概率]
    D --> E{期望损失是否高于人工成本}
    E -- 是 --> C
    E -- 否 --> F[自动提交 抽样复核回流标签]

面试官追问

Q：冷启动阶段没有标注数据，阈值怎么定？

A：先用 hard gate 兜住确定性失败，这部分不依赖标签；同时把自动通过的请求做高比例抽样人工复核，用复核结果当第一批标签。无标签期用保守阈值，优化目标优先保漏放率而不是转人工率，等标签积累到能拟合校准器再放松。

Q：业务方要求把转人工率压到 5%，怎么处理？

A：把指标翻译成代价语言：画出不同阈值下漏放率与转人工率的权衡曲线，说明 5% 对应的漏放率是多少，让业务显式接受。若不接受，就只能降低单次人工成本（分层接管、只确认关键字段）或提升信号质量，单纯压阈值等于把风险转移到线上。

03多 Agent 编排：跨 Agent 的 trace 传播与净收益判据怎么落地

资深 ｜ multi-agentobservabilitytracing成本归因 ｜ 面经来源 ↗

为什么会有这个问题

单 Agent 的调用链是一条线性 span，父子关系天然成立；一旦改成 orchestrator 加多个子 Agent 并行 fan-out，链路就变成运行时才确定的 DAG，父子关系只能靠代码显式传递。最常见的错误认知是「每个 Agent 都打了 run_id 就能还原链路」，但实际并发下常见三种断链：一是子 Agent 跑在线程池里，contextvars 不跨线程自动传播，子 span 全变成孤立 trace；二是 trace 上下文被塞进 prompt 靠模型转述，模型改写或截断后彻底丢；三是重试没有 attempt 区分，同一 subtask 的 span 重复上报无法去重。断链的直接后果不是看日志不方便，而是无法把 token、延迟、失败归因到具体子任务，于是「多 Agent 到底比单 Agent 多赚了什么」这个决策问题永远回答不了，只能靠感觉保留架构。

怎么做

  1. 建立 trace 传播契约：规定每次 Agent 调用必须携带 trace_id / span_id / parent_span_id / subtask_id / attempt 五个字段，通过函数参数或 contextvars 传递，严禁放进 prompt 让模型转述。
  2. 在 orchestrator 层先建任务表再派发：subtask_id、assigned_agent、依赖关系、状态机（pending/running/done/failed），span 挂在 subtask 上而不是挂在 Agent 上，这样同一 Agent 承担多个子任务时能分开统计。
  3. 每次 LLM 调用与工具调用都记用量：model、prompt_tokens、completion_tokens、cached_tokens、tool 调用次数与耗时，逐层向上聚合到 subtask 和 trace 根，得到单任务成本。
  4. 给失败分类而不是只记异常栈：error_kind 至少区分 tool_error / schema_error / timeout / invalid_arg / handoff_conflict，聚合后看 top 失败模式，才能判断是编排问题还是单 Agent 能力问题。
  5. 定义净收益判据并用同一离线集做对照：以单 Agent 为 baseline，比较任务成功率、P95 端到端延迟、单任务 token 成本、失败可恢复率四项；只有成功率提升稳定超过业务阈值、且成本与延迟在预算内，才保留多 Agent 拆分，否则回退成单 Agent 加工具。
  6. 控制可观测性自身的成本：span 元数据全量存，prompt 与 response 按比例采样存；设置 trace 存储预算上限，避免可观测性开销反超推理开销。
  7. 并发派发时优先用 asyncio.gather（会复制当前 context），必须用线程池时提交任务要显式 copy_context().run(...)，用进程池则把 trace 上下文序列化后作为参数传入。
  8. 上线后做持续判定：按 trace 抽样走单 Agent 对照路径或离线重放日志，设置成本护栏，超出预算自动降级为单 Agent 编排。

真实场景

某项目的调研 Agent 采用 orchestrator 加三个子 Agent（检索、抽取、写作）并行。症状是 P95 延迟明显高于改造前的单 Agent，成功率却只小幅提升，且监控面板只看得到整体 trace 失败率，定位不到具体子 Agent。排查路径：第一步在 orchestrator 日志里发现子 Agent 的 span 没有 parent_id，原因是子 Agent 被丢进线程池执行，contextvars 丢失，所有子 span 成了独立 trace；第二步补上显式传播后，看到绝大部分 token 消耗集中在抽取子 Agent 的结构化输出校验重试上；第三步按 error_kind 聚合，确认失败集中在 schema_error 与 invalid_arg，属于输出格式问题而非检索质量问题；第四步用受控输出约束加单次重试上限，成本与延迟回落，多 Agent 拆分才真正体现出成功率收益。整个排查能走通，靠的就是 trace 不断链加上按 subtask 的用量归因。

面试官追问

Q：子 Agent 被放进线程池或进程池后 trace 断了，你会在哪一层修？

A：优先在派发层修而不是在 Agent 内部修。线程池用 copy_context().run(...) 包裹提交的任务，让子线程拿到父 context 的副本；进程池无法共享内存，就在提交时把 trace_id / parent_span_id / subtask_id 显式序列化进任务参数。更稳的做法是不依赖隐式上下文，orchestrator 派发时统一传入一个 TraceContext 对象，Agent 实现里只读不重建，这样换执行模型也不会断。

Q：净收益如果只做过一次离线 A/B，线上怎么持续证明多 Agent 还值得留？

A：把判据做成在线指标而不是一次性结论：按 trace 记录路由决策和每个子任务的用量，定期对同一批线上请求做影子重放走单 Agent 路径对照；同时设预算护栏，当单任务成本或 P95 延迟超过阈值时自动降级为单 Agent 加工具链。关键是把架构决策和指标绑定，让回退成为配置行为而不是一次重构。

04Agent 流式输出：线上退化成假流式与工具中间态错乱怎么定位

进阶 ｜ streamingssefastapi故障定位 ｜ issue来源 ↗

为什么会有这个问题

流式的价值是首 token 时间与感知延迟，但整条链路上任何一环做缓冲，都会退化成「等模型全部生成完再一次性吐出」。最常见的错误认知是「返回 StreamingResponse 就是流式」：实际上 GZipMiddleware 会攒块压缩、Nginx 默认 proxy_buffering on、部分网关会聚合 SSE 再转发，把异步生成器包在被 await 完的中间件里同样会失去逐块下发。Agent 场景还多两层复杂度：一是流里混着 token delta、tool_call 开始与参数、tool_result、step 边界、最终消息等多种事件，前端要增量渲染；二是工具调用可能在中途失败，此时部分文本已经流给用户，需要「修正」语义而不是覆盖，否则前端渲染态与最终消息不一致。再加上断线重连与客户端关闭页面，后端如果感知不到断开，上游 LLM 仍在生成，白烧配额。

怎么做

  1. 分层定位是否真流式：先 curl -N 直连应用端口看是否逐块返回，再逐层加反向代理和网关复测；同时看响应头有没有 Content-Encoding: gzip、Transfer-Encoding: chunked，以及是否被加了 X-Accel-Buffering。
  2. 定义事件契约：为事件类型建 schema（token / tool_start / tool_args / tool_result / step / correction / done / error），每条带 message_id 与全局单调 seq，correction 用于修正已下发的中间态，不再覆盖文本。
  3. 显式关闭缓冲：响应头带 X-Accel-Buffering: no、Cache-Control: no-cache、Connection: keep-alive；对 text/event-stream 绕过压缩中间件；代理侧关闭 proxy_buffering 并调大 proxy_read_timeout。
  4. 处理客户端断开：用 request.is_disconnected() 或捕获 CancelledError，主动 aclose 上游 LLM 流，并把已生成部分以中断状态落库，避免重复计费。
  5. 断线续传：把 message_id 与最近 seq 及事件窗口写进 Redis，重连带 Last-Event-ID 从 seq+1 重放；窗口做有界，超出则让前端拉一次完整消息做 reconcile。
  6. 保证最终一致：前端在 done 事件上用完整消息覆盖渲染态，过程中的 token 与 tool 中间态只作为预览，避免工具失败后留下矛盾内容。
  7. 用契约测试守住：对流式端点写集成测试，断言至少收到两个 chunk、seq 单调、done 唯一、工具失败时必有 correction；CI 常跑，防止依赖升级或中间件调整把流式打回一次性返回。

面试官追问

Q：为什么不能直接对 SSE 响应开 gzip？

A：压缩需要攒够一块数据才输出，在 chunked 传输下会破坏逐块语义；部分网关还会因为统一压缩把 SSE 聚合成一个完整响应再转发，直接退化为非流式。虽然个别实现支持压缩后立即 flush，但引入了中间件与代理的额外不确定性，流式端点应当显式 bypass 压缩，压缩收益远小于流式体验损失。

Q：多个子 Agent 并行时，各自的输出怎么合并到前端的一条流里？

A：不要让子 Agent 各自直连客户端，改由 orchestrator 做单写者：子 Agent 的流打上 subtask_id 标签后 fan-in 到一个 asyncio.Queue，SSE 生成器从队列消费并分配全局单调 seq。保序只保证同一 subtask 内部，跨 subtask 允许交错但带标签，前端按 subtask 分区渲染；这样既不会出现多流抢写导致的 seq 冲突，也方便在 done 事件里一次性收敛成最终消息。

RAG 专题

05加了 rerank 和混合召回，p95 延迟翻倍但答案没变好：怎么定位瓶颈并量化收益

资深 ｜ hybrid-searchrerankchunk策略延迟预算 ｜ 面经来源 ↗

为什么会有这个问题

向量召回用的是 bi-encoder，query 和 chunk 各自独立编码，属于粗粒度语义近似；对错误码、型号、订单号、专有名词这类「字面必须命中」的 query 天然不敏感，所以只靠 dense 召回时，黄金证据经常根本进不了 top-k。rerank 用 cross-encoder 做 query-doc 联合打分，精度更高，但代价是 O(N) 次前向推理，延迟随候选数线性增长。常见错误认知有两个：一是把 rerank 当成「加上就提分」的开关，候选 50 条全精排、top 20 全塞进 prompt，结果 token 成本和噪声一起涨，LLM 反而被干扰；二是用「召回率@k」作为唯一指标，但真正决定答案质量的是「进入 prompt 的上下文是否包含正确证据，并且没有挤爆预算」。另有隐蔽坑点：BM25 与向量分数的量纲完全不同，直接加权融合等于让某一路分数统治排序。

怎么做

  1. 先建分层离线评估集：200 条左右真实 query，标注 gold chunk id 与 gold answer，按类型分桶（精确词、口语化、多跳、无答案）。
  2. 分离测量：召回层看 recall@k（正确 chunk 是否在候选集内），排序层看 nDCG@k / context precision，先判断瓶颈在召回还是在排序，再决定加不减 rerank。
  3. 召回层用 BM25 + dense 双路并行，融合用 RRF 而非分数加权，避免量纲问题；两路各自 limit 取大一些（如 80），保证 gold 能进候选。
  4. rerank 只对融合后的前 40–60 条做精排，取 top 5–8 进 prompt；rerank 服务必须设超时（如 600ms）+ 熔断，超时降级为 RRF 原始顺序，不能让主链路 5xx。
  5. chunk 策略改成「小 chunk 召回 + 大 chunk 或 parent/sentence-window 回填喂 LLM」：检索粒度小保精度，生成粒度大保上下文完整，同时控制 token。
  6. 上下文预算显式裁剪：按 rerank 分数与 token 数做 knapsack 式取舍，去重相邻 chunk，并保留引用 id 便于回答后归因。
  7. 埋点与 A/B：分别记录召回、融合、rerank 各段 p95、进入 prompt 的 chunk 数、总 token 数，用端到端正确率与单次回答成本做联合判据，而不是只看排序指标。
RRF_K = 60 def rrf_fuse(*rankings, k=RRF_K, top_n=60): scores = {} for ranking in rankings: for rank, doc_id in enumerate(ranking): scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1) return [d for d, _ in sorted(scores.items(), key=lambda x: -x[1])[:top_n]] async def retrieve(query, tenant, top_k=6): flt = {"tenant": tenant} dense, sparse = await asyncio.gather( vdb.search(await embed(query), limit=80, flt=flt), bm25.search(query, limit=80, flt=flt), ) fused = rrf_fuse([c.id for c in dense], [c.id for c in sparse]) try: ranked = await asyncio.wait_for(reranker.rank(query, fused[:60]), timeout=0.6) picked = [c.id for c in ranked[:top_k]] except (asyncio.TimeoutError, RerankError): metrics.inc("rerank_fallback") picked = fused[:top_k] return [await expand_to_parent(cid) for cid in picked]

真实场景

某项目的知识库问答上线「BM25 + 向量 + rerank」后，检索段 p95 从约 800ms 涨到 2s 以上，但人工抽检的答案正确率没有提升，个别类型还下降了。排查路径：第一步按 query 类型分桶重跑评估集，发现精确词类 query 的 recall@50 只有一半左右——dense 召回阶段 gold chunk 就没进候选，rerank 再强也救不回来；第二步看 prompt 组装日志，rerank top 20 全被塞进上下文，平均 token 数接近原来的 3 倍，长文档里的干扰段落挤掉了关键句；第三步看网关指标，rerank 服务在流量高峰偶发超时，重试把主链路拖成 5xx。改成「双路召回扩到 80 → RRF 融合 → rerank 只排 60 取 6 → parent chunk 回填 → 超时降级」后，延迟回到可接受区间，精确词类 query 的命中明显改善。

面试官追问

Q：为什么融合用 RRF 而不是把 BM25 分数和余弦相似度加权求和？

A：两路分数分布完全不同，BM25 无上界且随语料长度漂移，余弦相似度集中在很窄的区间，直接加权等于让其中一路主导排序，而且权重需要随语料变化重新调。RRF 只用名次信息，对分数量纲不敏感、无需调参、对单路异常也更鲁棒；只有在两路都是同源可比的分数（同模型同归一化）时，加权求和才有意义。

Q：什么情况下你会决定不上 rerank？

A：候选集本来就只有几十条、延迟预算很紧（如在线补全场景）、或者 reranker 与业务语料领域不匹配（专业词表、代码、长表格）导致精排反而不如原始顺序。这时优先做混合召回、字段过滤、query 改写和 chunk 切分优化，收益/成本比更高；rerank 可以作为离线重排或高价值 query 的分级策略按需开启。

06知识库更新后旧答案还在被召回：增量索引的差集删除、版本可服务与缓存失效

资深 ｜ 增量索引软删除版本切换缓存失效 ｜ 面经来源 ↗

为什么会有这个问题

文档更新在 RAG 里不是「覆盖一个文件」那么简单：一篇文档被切成 N 个 chunk，切分策略一改，chunk 边界和 id 就全变；如果用随机 uuid 作为 point id，upsert 只会新增，旧 chunk 永远留在库里，且因为历史命中多、相似度不差，仍会排到前面。链路上还有三个不一致源：向量库与元数据库（权限、生效时间、租户）双写无事务；向量库删除在分片/压缩下是异步生效的；query 侧的语义缓存与 LLM 缓存不带版本号。最常见的错误认知是「重新 embedding 一遍就等于更新了」，忽略了删除是需要显式算差集的。

怎么做

  1. 把 chunk id 设计成确定性标识：doc_id + 归一化后的内容 hash（或稳定的段落锚点），内容不变则复用向量，只对新 chunk 付费 embedding，同时天然支持去重。
  2. 写入前先取旧版本清单算差集：需要 upsert 的、需要 delete 的、可复用的三份；删除必须显式执行，不能依赖 upsert 覆盖。
  3. 用「版本可服务」而不是「原地覆盖」：新 chunk 带 version 与 ingested_at 写入，校验条数与抽样检索通过后再把 serving_version 推进，检索侧统一加 version ≤ serving_version 过滤，失败只回退版本号，不需要重建索引。
  4. 元数据以业务库为 source of truth，向量库只存 id、少量 filter 字段和 hash；检索后回表校验权限、生效时间与版本，这同时解决权限即时回收的问题，代价是一次批量主键查询。
  5. 缓存全部带版本：语义缓存 key 里拼 index version 或 doc updated_at，发布时按 doc 前缀失效；LLM 回答缓存同理，否则前端会命中旧答案。
  6. 建陈旧检测与回归门禁：定期抽查高频 query 的 top-k，断言不包含过期 version 的 chunk；每次发布后用固定评估集跑一遍，专门统计「引用过期内容」的比例。
  7. 把快照备份与恢复演练纳入流程：定期验证从对象存储恢复 → 校验点数与抽样检索可用，避免灾难时才发现备份链路配置有坑（如鉴权或协议不匹配）而不可用。

真实场景

某项目的客服知识库修改了退款政策，运营上传了同名文件，但机器人连续几天仍按旧政策回答，且旧政策说法在引用里带着原文档链接。排查路径：查向量库发现该 doc_id 下的 chunk 数只增不减，新文件被分配了新的 doc_id，旧 doc 的 chunk 从未删除；查网关日志发现大量请求命中语义缓存，缓存 key 只包含 query 文本、TTL 设了数天；查删除接口调用记录基本为零——代码里只有 upsert。进一步看监控，collection 点数持续单调上升。改成确定性 chunk id + 差集删除 + serving_version 推进 + 缓存带版本失效，并加上发布后的陈旧抽样断言，同类问题不再出现。

面试官追问

Q：为什么不在检索后让 LLM 自己判断内容新旧？

A：不可靠且不经济：LLM 没有权威的时间基准，遇到冲突文本倾向于自信编造；而且这会把正确性成本压到每次生成上。新旧判定应该由数据层用 version 与 serving 状态保证，LLM 只负责在答案里呈现引用来源，必要时由业务侧显式标注「信息截至某时间」。

Q：版本切换瞬间，双写或过滤会不会造成漏召回？

A：会有窗口期。常见做法有两种：一是短窗口内新老版本都写、检索侧按 version ≤ serving_version 过滤（切换前读老、切换后读新，不会读到写了一半的数据）；二是双读合并后按 doc 级 version 去重。关键是要保证「先写完新、再校验、最后推进 serving_version」的顺序，且校验包含条数、抽样检索和关键 query 回归，失败只回退版本号即可。

07加一个 tenant_id 过滤条件后召回明显变差、长尾延迟飙升：filtered search 的执行路径怎么排查，向量库怎么选

进阶 ｜ vector-dbfiltered-searchHNSW选型 ｜ 面经来源 ↗

为什么会有这个问题

向量检索默认是在 ANN 图上做近似最近邻，一旦叠加结构化过滤条件（tenant_id、时间窗、权限标签），执行路径会分叉成三种：post-filter 先取 topK 再过滤、pre-filter 先过滤再在子集上调索引或暴力、过滤感知索引（Qdrant 的 payload index、Milvus 的 partition key 与 scalar index、Weaviate 在低选择率下回退 flat）。常见错误认知是「where 条件只是附加约束，跟召回质量无关」。实际上 post-filter 在低选择率下会把 topK 吃掉大半，返回条数不足就直接变成答非所问；而 pre-filter 在高选择率下退化成全量扫描，p99 随过滤后集合大小线性上涨。更隐蔽的是同一套代码换引擎或升级版本后，默认策略从过滤感知变成后置过滤，线上只有长尾变慢、没人报错。

怎么做

  1. 先量化两个量：过滤字段的选择率（命中数除总数）和基数（不同取值个数）。按选择率分档决定执行路径，而不是一套参数打天下。
  2. 在引擎侧确认执行计划：Qdrant 看过滤字段是否已建 payload index 以及 collection 是否使用 payload_m 分片；Milvus 看是否用 partition key 或 scalar index；Weaviate 观察是否发生 flat 回退。未建索引的高频过滤字段基本等于全量扫描。
  3. 构造三组压测集：无过滤、高选择率（大于百分之十）、低选择率（小于千分之一），用 scroll 全量打分作为 ground truth，同时记录 recall@k 与 p95、p99。
  4. 低选择率场景补兜底：把 topK 按一除选择率放大后再截断，或对大租户单独走 partition 或 candidate id 集合上的暴力打分（候选少于几千条时暴力远快于走图）。
  5. 若租户数可控且跨租户查询不存在，考虑按租户拆 partition 或 collection；租户数到千级以上则回到单 collection 加 partition key，避免元数据管理成本失控。
  6. 把过滤字段写进索引设计规范：只对高基数且高频过滤的字段建 payload index，避免全字段索引带来的写入放大与内存膨胀。

真实场景

某项目把知识库从单租户扩成多租户，检索请求固定带 tenant_id 过滤，topK 取 10。上线后出现的现象是：小租户经常只返回两三条、问东答西；同时 p99 从几十毫秒抬到几百毫秒，长尾全部集中在文档量最大的几个租户。排查路径：先算选择率，发现头部租户不到千分之一、长尾租户超过百分之三十；再在引擎侧确认过滤字段没有建 payload index，实际走的是后置过滤，低选择率下 topK 被过滤得所剩无几，而大租户又把 topK 放大后触发了更宽的图遍历。最终按选择率分档：头部租户改 partition，小租户走候选集合暴力打分，中间档补 payload index 并对齐 hnsw_ef，召回与 p99 同时回到基线。

面试官追问

Q：为什么不直接无脑放大 topK 解决问题？

A：放大 topK 只在高选择率下近似有效。选择率为千分之一时，要凑够 10 条需要放大到一万条，网络传输和二次打分开销都跟着涨，而且返回结果里大量是不相关候选，反而稀释上下文。正确做法是先判断选择率落在哪一档，低选择率优先换执行路径（partition、候选集合暴力、倒排先取 id），而不是继续加大 k。

Q：什么时候该给每个租户建独立 collection 或 partition？

A：看三个条件：租户数可控（几百级别）、单租户数据量足够大、且不存在跨租户联合召回。满足时隔离收益明显，召回质量和延迟都稳定，还便于单租户导出与删除。租户数到千级以上，collection 元数据和集群资源会被切碎，应退回单 collection 加 partition key 或过滤字段索引，用查询路由解决隔离。

08备份任务天天显示成功，真要回滚时却恢复不出来：RAG 索引快照的可用性该怎么验证

资深 ｜ snapshot灾备演练collection-alias数据血缘 ｜ issue来源 ↗

为什么会有这个问题

向量索引的冷备成本和热数据不对称：百万级 chunk 重新 embedding 要数小时到十几小时，还要再付一次 embedding 费用，所以团队普遍依赖索引快照做冷备与回滚。这里有三层错误认知。第一层，备份任务退出码为零就等于可用，实际上传到对象存储时 endpoint、TLS 证书链、凭证配错会在 SDK 内部重试后写空对象或被 except 吞掉，调度器状态依旧显示成功。第二层，快照即数据，但快照不携带外部依赖：embedding 模型版本、chunk 策略版本、collection 的维度与距离度量、payload index 与分区配置、alias 指向，任何一项缺失恢复出来都是另一套索引。第三层，能恢复就等于能用，跨大版本恢复或量化参数不一致时，服务能起来但召回质量已经悄悄劣化，没有任何报错。

怎么做

  1. 先定 RTO 与 RPO，把重建成本（时间、embedding 费用）和快照恢复成本算清楚，明确哪些 collection 值得备、备份频率多高。
  2. 备份产物按三件套存放：快照文件本身、collection 配置导出（维度、distance、量化与索引参数、payload index、分区）、数据血缘（embedding 模型名与版本、chunk 策略版本、源文档处理水位）。三者缺一都不算可恢复。
  3. 备份后立即校验：断言对象存储里的快照对象存在且 size 非零、校验和匹配，并且断言上传调用真的返回成功，不允许宽泛的 except 吞异常。
  4. 从最新快照恢复到临时 collection，抽一组固定 query 与线上做召回交集比对，同时校验配置 diff 为空，形成可量化的恢复健康分。
  5. 线上通过 alias 切流量，代码里禁止写死 collection 名。恢复流程固定为创建、恢复、抽样比对、alias 原子切换四步，比对不通过直接阻断切换而不是调低阈值。
  6. 把恢复演练做成周期任务（每次 schema 或模型变更后必跑），记录耗时与召回交集指标；备份任务本身要有对象存在性、耗时、字节数的可观测指标与告警。
def restore_and_verify(snapshot_url, target, sample_queries, cfg_path, min_hit=0.95): assert remote_object_size(snapshot_url) > 0, "snapshot missing or empty" client.create_collection(target, vectors_config=load_cfg(cfg_path)) client.recover_snapshot(target, location=snapshot_url, priority="snapshot") wait_until_green(target) assert diff_config(target, "docs_live") == {}, "collection config mismatch" hits = [] for q in sample_queries: new = top_ids(client.query_points(target, query=q.vec, limit=10).points) old = top_ids(client.query_points("docs_live", query=q.vec, limit=10).points) hits.append(len(set(new) & set(old)) / 10) score = sum(hits) / len(hits) if score < min_hit: raise RuntimeError(f"restore degraded: {score:.3f}") return score

真实场景

某项目把索引快照传到自建 MinIO，endpoint 写成 https 但证书链不全，SDK 重试若干次后抛异常被一层宽泛的 except 捕获，只打了日志；监控上的「备份成功」取的是调度器任务状态而非对象存储里的实际对象。半年后一次 embedding 模型升级需要回滚，才发现最新可用快照已经是三个月前，且恢复出来的 collection 距离度量与线上不一致、payload index 也没重建，最终只能全量重建、业务停摆半天。排查路径：先看对象存储里快照对象的 size 与最后修改时间，再翻任务日志里被吞掉的 exception，最后对 collection 配置做逐字段 diff，问题链路才完整暴露。

面试官追问

Q：为什么不干脆放弃快照、每次全量重建？

A：规模小、chunk 策略还在频繁变动的阶段，重建确实更简单可靠，也省掉快照版本管理。但数据量到百万级后，重建要数小时且 embedding 费用可观，重建窗口内无法回滚、也无法做灰度对比，风险集中在升级时刻。判断依据是重建耗时是否超过可接受停摆时间、以及回滚窗口是否必须存在，而不是一刀切。

Q：快照恢复后召回交集差异多少算可接受？

A：如果索引参数和量化设置完全一致，恢复后图结构应当基本一致，交集接近满分；出现明显差异一般不是索引近似误差，而是配置或数据版本不一致（维度、距离度量、量化参数、payload index 缺失）。所以不应该调低阈值放行，而应把它当成配置漂移信号去修恢复流程。若确实用了 SQ 或 PQ 量化，必须在备份产物里记录量化参数，恢复时严格复用同一套。

09async def 接口 P99 抖动到秒级：同步 SDK 打满共享线程池，怎么定位并隔离

进阶 ｜ async线程池阻塞调用性能排查

为什么会有这个问题

大家都知道「async def 里不要写阻塞调用」，但真正的坑在另一半：FastAPI 会把 def 端点、以及所有同步依赖（鉴权、DB session、同步 SDK 工厂）自动丢进 AnyIO 的 worker thread 执行，而这个线程池默认只有 40 个 token，且是整个进程共享的。于是同步调用不阻塞事件循环，却把线程池占住；一旦贴顶，后续所有同步端点、所有同步依赖一起排队， síntomas 是 CPU 很低、事件循环 lag 正常、p99 却到秒级。三类常见错误认知：一，认为「改成 async def 就没事」，结果在 async 里直接调同步 SDK，真的把事件循环卡死；二，认为线程池会随并发自动扩容，实际默认上限 40；三，用 run_in_threadpool 包一层以为隔离了，其实用的还是同一个默认 limiter。更常见的是连 timeout 都没设，token 被长期占死。

怎么做

  1. 先分清是事件循环卡住还是线程池饥饿：容器内 py-spy dump --pid 看有多少线程停在 socket read；把 anyio.to_thread.current_default_thread_limiter().borrowed_tokens 打成 metrics，对照 QPS 看是否贴顶；同时看事件循环 lag 是否正常。
  2. 把调用分三类处理：可换 async 客户端（httpx.AsyncClient / 官方 async SDK）的首选换掉；真同步阻塞（旧 SDK、文件 IO）隔离到独立线程池并显式设并发上限；短 CPU 任务留在原地但要有上限。
  3. 隔离不要复用默认 limiter：自建 CapacityLimiter 或 ThreadPoolExecutor，上限按「目标 QPS × 平均耗时 ÷ 下游可承受并发」估算，并给 SDK 设明确 timeout 与重试上限，保证 token 一定归还。
  4. 同步依赖同样要治：依赖里禁止做网络调用，必须做的改成 async，或用带短超时的本地缓存顶掉高频调用。
  5. 健康检查与探针接口必须是 async def 且不依赖任何同步依赖，否则会和业务一起排队，被 K8s 误判摘流，把小抖动放大成雪崩。
  6. 出口加三个告警：事件循环 lag、线程池 borrowed/排队数、超时率；压测复现原始曲线，确认隔离后 p99 与 borrowed_tokens 不再相关。
import anyio from fastapi import FastAPI, Depends app = FastAPI() LIMIT = anyio.CapacityLimiter(8) # 独立于 AnyIO 默认 40 token def legacy_client(): # 同步依赖也占线程池，禁止做网络调用 return LegacySDK(timeout=5) @app.post("/answer") async def answer_bad(q: str, c=Depends(legacy_client)): return c.ask(q) # 直接阻塞事件循环，最坏情况 async def blocking_ask(q: str) -> str: # 同步 SDK 包一层，必须有 timeout return LegacySDK(timeout=5).ask(q) @app.post("/answer-ok") async def answer_ok(q: str): try: async with LIMIT: # 按下游容量做背压 return await anyio.to_thread.run_sync(blocking_ask, q) except TimeoutError: return {"code": "upstream_timeout"} # 快速失败优于排队

真实场景

某项目把内部 LLM 的同步 HTTP SDK 直接放进 async def 端点，上线后白天 p99 从几百毫秒涨到数秒，但 CPU 只有三成、下游耗时曲线平稳；紧接着 /healthz 也开始超时，触发 K8s 探针失败，实例被反复摘流再拉起，重启能好一阵又复发。排查路径：py-spy dump 看到几十个线程全部停在 requests 的 socket read；borrowed_tokens 指标贴满默认 40；把 /healthz 改成纯 async、无任何依赖后，实例不再被误杀，但 /answer 仍在排队，说明压力来自共享线程池而非事件循环。最终改为 async 客户端 + 独立 CapacityLimiter(8) + 5s 超时，超时直接降级返回，p99 回落且 borrowed_tokens 变成平稳曲线。

面试官追问

Q：直接把线程池上限调大、或加机器不就行了？

A：调大只是把压力原样转给下游，还会带来 GIL 争用和上下文切换，尾延迟通常更差；正确做法是按下游容量定上限、超限快速失败（超时/429/降级），并让排队长度可见。加机器能缓解但不解决问题根因。

Q：run_in_threadpool 和 asyncio.to_thread 有什么区别？

A：前者用 AnyIO 的默认 limiter（进程内共享，默认 40），后者用 asyncio 默认 executor（默认 min(32, cpu+4)），两者互不共用，所以换一个不等于做了业务隔离；要真正隔离必须自建 limiter 或 executor，否则一条慢链路仍会拖住所有同步调用。

10SSE 流式接口 worker 被长连接占满、客户端断开后仍在计费：多进程部署怎么收口

资深 ｜ SSEStreamingResponse部署资源回收

为什么会有这个问题

SSE 在 FastAPI 里只是把一个 async generator 交给 StreamingResponse，能推起来很容易，难的是三件事同时成立：一，连接是长连接，而 worker 是有限资源，一个进程能挂的连接数并不等于能同时跑的生成器数；二，客户端随时会断，但上游 LLM 的生成与计费不会自动停；三，一旦发出 200 和首个分片，后续任何错误都无法再用状态码表达。常见错误认知包括：以为 async for 循环里客户端断了会自然 break（实际上有的路径靠取消传播，生成器被 buffer 卡住或上游还在排队时不会立刻感知）；以为 finally 里可以随便 await 做清理（取消作用域下 await 会立即抛 CancelledError，清理做不完）；以为 asyncio.Semaphore 能做全局限流（它是进程内的，-w 4 就是 4 倍预算）；以为设了 X-Accel-Buffering: no 就万事大吉（还有网关 idle timeout 和 GZip 中间件会把流攒住）。

怎么做

  1. 断开与清理分层：依赖框架的取消传播（生成器被 close 时在 finally 里释放上游），再加周期性 await request.is_disconnected() 作为兜底；把清理拆成「必须完成」（停上游、归还配额）和「尽力而为」（审计日志），前者用 asyncio.shield 或投递给独立任务，别让它被取消打断。
  2. 并发上限按 worker 换算：进程内 asyncio.Semaphore 限制同时在跑的生成器数量，且必须在开始流之前判定（流一旦开始就改不了状态码），超限直接 429；总上限 = worker 数 × 单进程上限，并与上游 RPM/TPM 配额对齐。
  3. 响应头与中间件清理：media_type=text/event-stream、Cache-Control: no-cache、X-Accel-Buffering: no；重点检查是否有 GZipMiddleware（会把分片攒起来变成假流式）、CORS 中间件、以及网关的 proxy_read_timeout 与 idle timeout。
  4. 把心跳和续传做进协议：用注释行 `: ping` 做心跳，间隔小于所有中间层最短 idle timeout；每个分片带 id: <seq>，客户端用 Last-Event-ID 续传；错误走 data: {"type":"error"} 事件而不是状态码。
  5. 部署侧取舍：给流设最大时长和最大 token 硬上限，超时主动发 end 事件关闭；滚动发布时设置 --timeout-graceful-shutdown 并接受旧 worker 会等到长连接结束，或先摘流再等连接自然衰减；连接数指标按 worker 维度看，不要只看整体平均。
  6. 测试要覆盖断连：用 httpx.AsyncClient + ASGITransport 或真实 uvicorn 写「中途断开」用例，断言上游 close 被调用、配额已归还；再压测确认 worker 连接数与生成器数线性可控、不随空闲连接膨胀。
import asyncio, json from fastapi import FastAPI, Request from fastapi.responses import StreamingResponse, JSONResponse app = FastAPI() SEM = asyncio.Semaphore(64) # 进程内上限，总量需乘 worker 数 @app.get("/chat/stream") async def chat_stream(request: Request, q: str): if SEM.locked(): # 必须在开流之前拒绝，开流后改不了状态码 return JSONResponse({"code": "busy"}, status_code=429) async def gen(): seq, up = 0, None try: async with SEM: up = await request.app.state.llm.open(q, timeout=60) async for tok in up: if await request.is_disconnected(): break seq += 1 yield f"id: {seq}\ndata: {json.dumps({'t': tok})}\n\n" yield "data: [DONE]\n\n" finally: if up is not None: await asyncio.shield(up.aclose()) # 必须完成：停生成、归还配额 return StreamingResponse(gen(), media_type="text/event-stream", headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

真实场景

某项目把一问一答从一次性返回改成 SSE 后，功能测试全过，上线一周出现三类现象：晚高峰部分实例 CPU 内存都正常，但新建连接要排十几秒才出首字节；账单侧的上游 LLM 调用量明显高于前端实际完成的对话数；滚动发布时客户端报流中断，用户只看到半句话。排查路径：按 worker 维度打连接数与活动生成器数，发现 worker 数 2、单进程 semaphore 设 64，实际总并发翻倍且被长连接占满；用 request_id 对账发现大量生成器在客户端关闭后仍一直跑到上游 60s 超时；再查网关 idle timeout 60s 而心跳间隔 90s，长连接被中间层静默断掉、两端都没立即感知。最终落地：心跳缩短到 15s、分片带 id 支持 Last-Event-ID 续传、清理放 shield、总上限按 worker 数对齐上游配额、给流加最大时长后主动结束。

面试官追问

Q：客户端断开了，怎么保证上游一定停？

A：三层防护：框架的取消传播把生成器关掉，在 finally 里 aclose 上游连接；is_disconnected 轮询兜底处理取消没及时传播的路径；最后加服务端最大生成时长与最大 token 的硬上限，即使前两层都失效也会自然收尾。真正的兜底是最后一道，前两层只是让停止更及时。

Q：多进程部署下 semaphore 怎么实现全局限流？

A：进程内 semaphore 只能防单实例被打爆，全局要靠外部：网关或 Redis 令牌桶，或按 worker 数静态切分下游配额；工程上更稳的是两段式，先取全局令牌再开流，取不到直接 429，避免长连接建立起来又被拒绝，浪费连接与首字节等待。
