01工具从 8 个涨到 40 个后误选与越权执行：工具准入标准、描述契约与决策执行分离怎么落地

资深 ｜ tool-usefunction-calling权限与幂等工具治理 ｜ 面经来源 ↗

为什么会有这个问题

工具是模型唯一的行动接口，但它能被正确使用的前提，完全取决于描述文本和参数 schema；而模型对语义相近的工具没有可靠的区分能力。很多团队把内部细粒度函数原样暴露（get_order / search_order / update_order_note），工具数量随业务线性增长，模型在几十个近似选项里做选择，误选和参数幻觉几乎必然发生。更危险的是把决策与执行混在一起：工具内部直接写入副作用，模型一次错误的 function call 就变成真实写操作。常见错误认知是『在 system prompt 里写清楚不要调用危险工具就行』——prompt 只是概率性约束，执行层的确定性校验才是真正的边界。

怎么做

  1. 准入判定：只暴露意图级动作（业务动词），要求参数可枚举或可校验、结果可幂等或可补偿；不可逆且没有补偿路径的操作不直接暴露，改造成『提交申请』类工具。把多个细粒度函数合并成一个带 action 枚举的粗粒度工具，让模型做选择题而不是记忆题。
  2. 描述契约：每个工具写清做什么、何时该用、何时不该用（给出负例）、参数语义与取值范围、返回结构与失败语义；同一个字段在各工具中的含义必须一致。描述里带负例能显著降低相邻工具的混淆。
  3. 分层挂载：按 Agent 角色只挂 5–12 个工具，其余通过 tool retrieval 预筛或转交给子 Agent；用命名空间前缀（order.* / user.*）帮模型建立语义分组，避免同名工具互相干扰。
  4. 执行层收口：模型只产出 tool_name + args 的 intent，执行层做严格 schema 校验、权限判断、预算控制、幂等键、写操作 dry-run 或审批；校验失败返回结构化错误让模型自我修正，而不是直接抛 500。
  5. 度量与回归：采集工具调用分布、参数校验失败率、误选样本、人工纠正率；描述每次改动都跑固定评测集，看是否引入回退，否则改描述等于盲改 prompt。

真实场景

某项目接入订单与售后能力后，工具从 8 个涨到 40 余个。线上出现三类症状：用户问『订单到哪了』时偶尔触发了修改备注类工具；参数里出现 schema 之外的枚举值，服务端直接 500；客户端重试导致同一个取消动作重复提交。排查路径是：先从 trace 里按 tool_name 聚合调用分布，找出被误选的高频工具对；再统计 invalid_args 的错误占比和具体出错字段；最后对比工具描述文本，发现三个订单相关工具的描述都以『订单相关操作』开头，参数名一个叫 id 一个叫 order_no。修复方向是把三个工具合并为带 action 枚举的单一工具、补负例描述、执行层加 schema 校验与幂等键。

面试官追问

Q：工具描述改了一版，怎么证明没有引入回退？

A：把线上真实请求采样成带标注的评测集（请求 → 期望工具与关键参数），每次改描述或增删工具都跑一遍，重点看误选率和参数校验失败率两个指标；同时灰度对比转人工率和错误率。没有评测集就改描述，等于盲改 prompt，问题只会在下一个流量高峰暴露。

Q：先查后写的两步操作怎么保证一致性？

A：不要把两步都交给模型自由编排。把『查+写』收敛成一个服务端事务型工具，或让模型只产出写意图并携带业务主键，由执行层先校验前置条件再落库；需要用户确认的写操作走确认态或审批，模型只负责发起意图，不负责决定是否最终生效。

02多 Agent 互相委派形成环：任务签名环检测、预算随链递减与降级策略

资深 ｜ multi-agent循环依赖预算控制可观测性 ｜ 面经来源 ↗

为什么会有这个问题

多 Agent 的委派关系是运行时由模型判断生成的，不是启动时固定的 DAG。A 认为该交给 B，B 判断信息不足又把任务踢回 A，或者任务描述被改写后重新触发上游 Agent，就会形成逻辑上的环。它比死循环更难发现：每一跳都合法、每个 Agent 都在正常工作，只有从整体 trace 看才会发现路径在重复。常见错误认知是『给每个 Agent 设 max_iterations 就够了』——计数是各自独立的，扇出叠加后总量仍然爆炸，而且环的代价是 token 和延迟，不是显式报错。

怎么做

  1. 委派上下文强制透传：每次委派带 trace_id、delegation_path（祖先 Agent 加任务签名）、剩余预算（步数、token、时长），预算沿链递减而不是每层重置，让环在早期就耗尽预算而不是烧到全局超时。
  2. 任务签名做环检测：把目标与关键约束规范化后哈希，判断 (callee, signature) 是否已出现在祖先路径上；用签名而不是原文，避免措辞漂移导致去重失效。
  3. 静态加动态双层护栏：编排图启动时做拓扑校验，禁止硬编码回边；运行时设深度上限、同签名重复次数上限、全局预算，三者任一触发即中断。
  4. 命中后的降级策略：不要直接抛错，而是升级到 Supervisor、用已有部分结果合成答复或转人工，并把 cycle_detected 作为一等事件打点，形成可统计的指标。
  5. 可观测：trace 里用 span 的 parent 关系还原调用树，统计每层扇出、重复签名率、平均委派深度；异常会话可按 trace_id 完整回放定位断点。
import hashlib, json def task_sig(goal: str, constraints: dict) -> str: norm = json.dumps({'goal': goal.strip(), 'c': constraints}, sort_keys=True, ensure_ascii=False) return hashlib.sha1(norm.encode()).hexdigest()[:12] def delegate(parent, callee: str, goal: str, constraints: dict) -> dict: sig = task_sig(goal, constraints) path = parent.delegation_path + [(callee, sig)] if (callee, sig) in parent.delegation_path: return {'status': 'cycle_detected', 'path': path, 'action': 'escalate'} if len(path) > parent.limits.max_depth: return {'status': 'depth_exceeded', 'path': path, 'action': 'escalate'} child_budget = parent.budget.spend_child() if child_budget.remaining_steps <= 0: return {'status': 'budget_exhausted', 'path': path, 'action': 'summarize_partial'} return callee.run(goal=goal, constraints=constraints, delegation_path=path, budget=child_budget, trace_id=parent.trace_id)

真实场景

某项目用分诊 Agent 把会话路由到订单 Agent 与售后 Agent。上线后少量会话耗时是均值的数倍、token 消耗异常高，且最终没有有效答复。排查时按 trace_id 拉出调用树，发现『售后 → 订单 → 售后』反复出现；再看每次委派的任务描述措辞都略有不同（『请确认该订单是否已发货』对『查询该订单物流状态』），简单的字符串去重完全失效；而单 Agent 的步数上限一次都没有被触发。修复方向是把任务签名改成目标加约束的结构化摘要、预算随委派递减、命中重复签名时升级给 Supervisor 汇总已有结果。

flowchart TD
    A[Agent A 收到任务] --> B[计算任务签名]
    B --> C{签名是否已在祖先路径}
    C -->|是| D[判定为环 升级 Supervisor]
    C -->|否| E{深度与预算是否足够}
    E -->|否| F[降级 用已有结果合成答复]
    E -->|是| G[委派给下游 Agent 预算递减]
    G --> H[下游 Agent 执行]
    H --> I[写入 trace 记录 delegation path]

面试官追问

Q：任务签名怎么设计，既不误杀合法的多轮往返，又不漏掉环？

A：签名应编码『要达成的目标加关键约束』，而不是整段自然语言。合法的往返通常目标在变化（先澄清再执行），签名会不同；环的特征是同一目标被反复重新委派。可以再叠加一个短窗口计数：同签名在最近若干跳内出现两次以上才拦截，给合法重试留余量。

Q：为什么不能只靠全局超时兜底？

A：超时只能止损不能定位，而且环往往是慢速的：每跳都在二三十秒的合理区间内，全局超时触发时预算已经烧掉了。超时也不告诉你环发生在哪一层，排障成本很高。环检测加预算递减能在早期以很低成本拦住，并且留下可统计的事件。

03多 Agent 心跳超时导致的「假死」误判：如何推导阈值、保证接管互斥并用 fencing 兜底

资深 ｜ multi-agentleasefencing可观测性 ｜ 面经来源 ↗

为什么会有这个问题

心跳的本质是「推进能力信号」，不是「进程存活信号」。Agent 单步耗时呈现明显的长尾：一次 LLM 推理可能几十毫秒也可能几十秒，工具调用可能卡在外部 HTTP 或大文件解析，等待人工审批更是不可预估。用固定的 TTL 去判活，长尾必然被误判成假死；更危险的是误判之后的处理：多数实现直接「超时后重新派单」，而重跑并不等于接管——旧执行体可能只是被阻塞，恢复后仍会继续写状态，于是两个执行体同时推进同一个 task，产生重复下单、重复发消息、重复扣减这类不可逆副作用。常见错误认知有两个：一是把心跳当成 ping（只要进程在就发），二是认为超时之后重启任务即可（缺少互斥与写入校验，重启就是双写）。

怎么做

  1. 把心跳从 ping 改成 progress heartbeat：每次心跳携带 step 序号、当前阶段（thinking / tool_running / waiting_human）、最近一次产出摘要。对于合法长任务要发「忙等心跳」，让观察者能区分「卡住」与「正在干长活」。
  2. 阈值按阶段分别推导，不要全局一个数：统计各类阶段的耗时分位数（LLM 首 token、单个工具执行、人工审批），TTL 取 max(该阶段 p99 × 安全系数, 下限)；waiting_human 不走超时，改为显式的挂起状态并从判活范围中剔除。
  3. 用租约替代超时判定：任务由 lease 持有，续租即心跳；续租失败时执行体立即自我终止（self-fence），不再写任何业务状态，而不是「再试一次」。
  4. 接管互斥：抢占时必须用原子 compare-and-set 替换持有者，并把 fence 单调递增；所有下游写入都带上当前 fence，存储侧或业务侧校验并拒绝过旧 fence 的写入。
  5. 把误判做成指标：统计「被判死后又重新发心跳」的次数与比例、任务重启次数、重复副作用条数；接管初期可先做影子接管（只读对账，确认旧执行体确实停滞后再写），降低误杀损失。

真实场景

某项目的多 Agent 编排里，子 Agent 接到一个耗时较长的外部工具（批量抓取 / 大文件解析），心跳线程与业务执行共享同一个事件循环或线程，长同步调用把心跳饿死，主控在固定阈值后判定「假死」并重新派单。随后旧执行体从阻塞中恢复继续提交结果，两个执行体都对同一资源写入，出现重复工单；而监控上「失败率」毫无变化，只有「任务重启次数」和「下游幂等冲突数」同时抬头。排查路径：先看心跳间隔分布与该阶段实际耗时分位数是否错配（错配即阈值问题，不是任务问题）；再看重启时间点是否高度集中在含长工具调用的 step 上；最后检查续租失败后是否存在「继续写」的代码路径、写接口是否根本没有 fence 或幂等键。

面试官追问

Q：心跳发不出去，是该把 TTL 调大还是改架构？

A：先定位阻塞源。若心跳与业务在同一线程 / 事件循环，任何同步长调用都会饿死心跳，调大 TTL 只是把误判往后推，长尾一旦超过新阈值又会复发。正确做法是把心跳放到独立线程或独立进程，或改成「外部观察者轮询进度表」，让心跳不再依赖业务线程的调度机会；阈值只解决「多快发现」，架构才解决「能不能发现」。

Q：接管之后如何保证两个执行体不会都以为自己还活着？

A：靠 fence 而不是靠时钟：持有者每次写之前校验自己的 fence 仍然是最新的，被接管后写入直接被拒并抛错中止；同时抢占必须是原子的 CAS，不能让两个接管者同时成功。若规模更大，用 etcd / Redis 做领导者选举，把「谁是当前执行体」变成全局唯一事实，而不是各进程本地判断。

04单轮多个 tool_calls 的隐式依赖：只读并行、写串行与幂等键如何落地

进阶 ｜ tool-calling并发幂等失败语义 ｜ 面经来源 ↗

为什么会有这个问题

模型在一轮里返回多个 tool_calls 是为了压延迟，但它并不理解副作用顺序：create_order 与 pay_order、update 与随后的 get 校验，在模型眼里只是「同一次输出」。框架如果统一用 asyncio.gather 全部并行，写操作并发会破坏业务不变量——出现部分成功、读到中间态、同一资源被扣两次；而如果因为其中一个失败就整体重试，就会把已经成功的写再执行一遍。常见错误认知有两个：一是认为同一轮的 tool_calls 之间没有依赖（它们只是同批输出，不代表彼此独立），二是认为失败即重试（写操作天生不可盲目重放）。

怎么做

  1. 先给工具补元数据：read_only / destructive / idempotent，并按资源维度标注（order、user、inventory）。没有显式声明的工具一律按写处理，保证缺省是安全侧。
  2. 调度规则：连续的只读调用合批并行；写调用严格串行并保持模型输出顺序；写之后针对同一资源键的读必须排队到写完成之后。依赖不靠模型声明，而是由「读写属性 + 资源键」推导，模型声明的依赖只作为补充且要校验存在性，校验不过则降级为串行。
  3. 写调用统一带幂等键：idempotency_key = hash(task_id, step, tool_name, normalized_args)，同一 key 的第二次调用直接返回首次结果，而不是再打一次下游。
  4. 失败语义分开：只读失败可以指数退避有界重试并去重；写失败不回滚、不自动重试，把结构化错误（错误码、是否已生效、幂等键）回填给模型，让它决定下一步。
  5. 可观测性：为每个 tool_call 记录 start / end、资源键、幂等键、是否命中幂等，便于定位「部分成功」；同一 step 内工具 span 时间是否重叠，本身就是并行是否越界的直接证据。

真实场景

面试官追问

Q：让模型自己在 tool_call 里声明 depends_on 靠谱吗？

A：不可靠，模型经常漏写或写错 id，而且声明本身也可能指向不存在的调用。工程上以工具元数据加资源键推导为主路径，模型声明只作为补充；一旦声明的依赖无法解析，就降级为串行而不是忽略——宁可慢一点，也不能乱序执行写。

Q：写操作全串行会明显拖慢整体吗？

A：影响有限，因为真正的时延大头通常是只读检索与 LLM 推理。若确实存在多资源写，可以按 resource_key 分桶：桶间并行、桶内串行，既不破坏单资源不变量，也保留了并发收益。切忌为了并行把不同资源的写混在一起做全局 gather，那等于放弃顺序保证。

RAG 专题

05HNSW 的 ef 调大后离线召回达标了，但线上 p99 翻几倍、跑两周还越来越慢：参数、内存与墓碑怎么一起算

资深 ｜ 向量索引HNSW召回评测更新治理 ｜ 面经来源 ↗

为什么会有这个问题

HNSW 的参数被分成了两类，很多人把它们混为一谈：M 与 efConstruction 决定图本身的质量（每个节点的出度、建图时候选队列的长度），一旦建完就基本改不了；ef（查询期）只是把搜索前沿放宽，它只能在「已有的图」上延伸搜索，无法补回图里根本没连上的近邻。所以典型错误认知是「召回不够就把 ef 调大」，短期指标确实会涨，代价是每次查询要访问的候选点线性增加，QPS 和 p99 直接崩。第二个被忽视的点是更新：向量库普遍按 segment/段组织，upsert 与 delete 先写标记，旧点变成墓碑，在合并（compaction/optimize）之前查询仍要路过它们，于是出现「参数没变、数据没涨，但延迟和内存一路走高」。第三个坑是 filtered search：带 filter 时 ef 的候选池被过滤条件稀释，选择率低的条件实际有效候选远小于 ef，recall 会莫名下降，而纯向量基准测不出来。

怎么做

  1. 先建立可复现的召回基线：固定评测集（query → 已知相关 doc id），用暴力检索或 exact search 的结果作为 ground truth，统一用 recall@k 口径，禁止用人工「看起来相关」判断。
  2. 做内存预算建模：向量本体 n×dim×4 字节，加上图结构（底层约 2M 个邻居、上层约 M 个，每个 4 字节 id），再加上 payload 与原始文本；先给 M 定一个内存上限，再谈参数。
  3. 在小规模集合（如全量 10% 采样）上固定 M/efConstruction，只扫描 ef，画 recall–QPS–p99 三条曲线，取曲线拐点作为 ef 默认值，而不是取 recall 最高的点。
  4. 为带 filter 的查询单独校准：按过滤选择率放大 ef（如 ef_eff = min(ef_base / selectivity, cap)），或让存储层先做 payload 预过滤，再把结果喂给图搜索；两条路径都要有基准。
  5. 把更新纳入运维：监控 segment 数量、被标记删除的点占比、单 segment 大小；设置合并/优化阈值，大批量变更走「新集合重建 + 别名原子切换」，而不是原地长期 upsert。
  6. 上线后做在线抽样评测（按比例抽样并标注），同时看 p99、每查询访问点数、segment 数与内存；把召回衰退和延迟衰退分开归因，避免把墓碑问题误判成参数问题。
import time import numpy as np def recall_at_k(gt, got, k): return len(set(got[:k]) & set(gt[:k])) / k def mem_bytes(n, dim, m, payload_bytes=200): vec = n * dim * 4 graph = n * (2 * m * 4 + m * 4) # 底层 2M 邻居 + 上层近似 M return vec + graph + n * payload_bytes def sweep(client, coll, queries, gt, k=10, efs=(32, 64, 128, 256)): rows = [] for ef in efs: hits, lat = [], [] for q, g in zip(queries, gt): t0 = time.perf_counter() res = client.search(coll, q, limit=k, params={"ef": ef}) lat.append(time.perf_counter() - t0) hits.append(recall_at_k(g, [r.id for r in res], k)) rows.append({"ef": ef, "recall": round(float(np.mean(hits)), 4), "p99_ms": round(float(np.percentile(lat, 99)) * 1000, 1)}) return rows

真实场景

某项目的离线基准显示 ef 从 64 提到 256 后 recall@10 明显上升，于是直接改了线上默认值。上线后 QPS 掉到原来的一小部分、p99 涨了数倍，而业务侧反馈「答案没变好」。更麻烦的是集合每天有大量 upsert，跑了两周后即使把 ef 调回原值，延迟仍高于初始水平。排查路径：先看集合的 segment 数量与被标记删除点占比，发现长期未合并、内存虚高；再抓一批真实请求，发现大部分查询带租户与时间过滤，选择率极低，ef 的候选池被过滤条件吃掉大半，实际有效搜索深度远小于配置值；最后用同一评测集在「只读快照」上复测，确认图质量受 M 约束，单纯抬 ef 的收益早已饱和。处理方式是：重建集合时提高 M 与 efConstruction，线上 ef 取拐点值，filter 查询按选择率放大 ef，并把合并策略与别名切换纳入例行运维。

面试官追问

Q：为什么把 ef 一直调大不能解决召回问题？M 到底影响什么？

A：ef 只扩大查询期要探索的候选队列，搜索仍然沿着图中已有的边前进；M 决定每个节点保留多少邻居，M 太小会导致本该近邻的点在图里压根没连上，这时再大的 ef 也走不到。efConstruction 影响建图时挑邻居的搜索深度，决定边的质量。三者职责不同：M/efConstruction 是建图期的质量上限，ef 是查询期的成本-召回旋钮，因此正确做法是先按内存预算定 M、用采样数据验证建图质量，再扫 ef 取拐点。

Q：IVF-PQ、DiskANN 这类方案在你的场景里什么时候反而更合适？

A：当内存是主要约束、数据量很大、可接受一定量化误差时，IVF-PQ 用聚类加乘积量化压缩向量，内存占用显著下降，nprobe 可以调节召回与延迟；但它需要训练码本，分布漂移要重训，且对高 recall 场景通常吃亏。DiskANN 把图放在 SSD 上、内存只放压缩向量与少量入口点，适合超大规模且能接受单次查询的磁盘 IO 延迟、更新不频繁的场景。选型看四个维度：内存预算、目标 recall 下限、更新频率、p99 容忍度，任何一项给不出来就不该拍板。

06换了 embedding 模型后拒答阈值全部失效、新旧向量还混在一个集合里：影子索引、阈值重标定与灰度切换怎么做

资深 ｜ embedding索引迁移灰度阈值标定 ｜ 面经来源 ↗

为什么会有这个问题

换 embedding 模型不是「换个 encoder 重跑一遍」这么简单。第一，向量空间整体改变：不同模型的训练目标、语言分布、是否归一化、pooling 方式都不同，两个空间的余弦相似度数值不可比，跨空间算出来的距离在语义上没有意义——但只要维度相同，代码不会报错，于是静默污染，表现为「召回莫名其妙、有的文档永远召不回、有的永远排第一」。第二，所有依赖分数的下游全部失效：拒答阈值、rerank 前置过滤、混合检索的加权融合、缓存命中判定，都是按旧模型的分数量纲调出来的，直接沿用会造成大规模误拒或误放行。第三，全量重算是硬成本：docs×tokens 的编码开销、限流窗口、失败重试，还要保证回填期间线上照常可服务、可回滚，这本质是一次带状态的数据迁移。

怎么做

  1. 冻结模型契约：把模型名、版本、维度、归一化方式写进集合元数据与别名命名，写入与查询两端都做校验，宁可启动失败也不要混写。
  2. 新建影子集合：用新模型建独立 collection + 独立 alias，在线新文档双写两份；旧集合保持可读，作为回滚底座。
  3. 历史数据分批回填：按 doc id 水位做断点续跑，同 id upsert 保证幂等，用并发与 QPS 上限保护在线读写，失败批次可重放而不重复计费。
  4. 阈值重标定而非直接沿用：在同一评测集上分别跑旧/新索引，把分数按分位数对齐（如都取 top-1 分数的 p10/p50/p90 做映射），再重设拒答与融合阈值，禁止跨模型比绝对值。
  5. 同集对比与灰度：用固定评测集比 recall@k、端到端答案正确率、拒答率、长尾与多语言 query 表现；达标后按租户或流量比例切读，双读对比但只返回主路结果。
  6. 缓存与回滚：query embedding 缓存 key 带上模型版本，答案缓存带上索引别名版本；切换动作是别名原子切换，旧索引保留一个观察窗口，异常时一键切回。

真实场景

某项目把 embedding 模型从旧版换到新版本，维度恰好一致，为了省事直接对原集合 upsert 覆盖。结果是：回填任务中途因限流超时中断，重跑时又从头扫，一半文档是新向量一半是旧向量；检索侧完全看不出异常，但部分老文档彻底召不回。同时拒答阈值沿用旧值，新模型分数整体偏低，大量本可回答的问题被判为不可答，用户侧表现为「知识库明明有却说不知道」。排查路径：先抽样比对集合内的 model 元数据分布，确认混写；再用同一评测集分别在纯旧向量与重新全量写入的新向量上跑 recall 与拒答率，发现阈值必须按分位数重标定；最后核对 query embedding 缓存未带版本，命中了旧模型的向量。收敛做法是重建影子集合、断点续跑回填、阈值按分位数重设、按租户灰度后再别名切换。

面试官追问

Q：新旧模型维度相同，是否可以共用一个集合，靠 payload 里的 model 字段过滤来区分？

A：不建议。同一集合内的向量会被同一个图/聚类结构组织，两个空间的点混在一起会互相成为邻居，过滤只能保证返回结果的来源，不能保证搜索路径没被污染，距离本身仍然不可比；而且索引结构无法按 filter 分区训练。正确做法是集合或别名级隔离，模型版本写进集合元数据做写入校验，迁移用双写加别名切换完成。

Q：怎么判定这次模型切换是成功的，而不只是「跑通了」？

A：三个层面同时看：检索层用固定评测集的 recall@k 与 MRR 对比新旧索引；答案层看端到端正确率、拒答率与拒答是否正确（该拒的拒、不该拒的别拒）；分布层看长尾 query、多语言、时间新近文档的表现，避免新版只在头部热门问题上变好。阈值必须先按分位数重标定再比较，否则分数尺度差异会伪装成效果差异；另外回填遗漏率（集合内 model 元数据分布）也要作为验收项。

07想用 GraphRAG 解决「跨文档多跳与汇总类」问题：抽取成本、实体归一化与增量社区重建怎么一起算

资深 ｜ graphrag成本建模增量索引query路由 ｜ 面经来源 ↗

为什么会有这个问题

向量 RAG 的检索单元是 chunk，本质是「局部语义相似」；当问题需要跨多篇文档做聚合、对比、多跳推理（例如「哪些组件同时被 A 和 B 两个流程依赖」），单 chunk top-k 里根本不存在这样一条证据，召回再准也答不对。GraphRAG 的取舍是「用离线昂贵的抽取与社区摘要，换在线可聚合的图结构」，它不是「更准的向量检索」，而是一次预处理成本与查询能力的置换。常见错误认知有三个：（1）先上 GraphRAG 再想评测，结果事实型问题毫无提升却背了全量抽取成本；（2）实体不做归一化，同一实体在图中分裂成十几个节点，社区摘要被噪声淹没、边数爆炸；（3）把图当成 append-only，文档更新后只加边不删旧边，导致摘要里长期存在已删除的事实，且每次新增文档都触发全量社区重建。

怎么做

  1. 先用评测集判定「是否真的需要图」：从真实日志里抽出 50–100 条聚合型/多跳型 query 单独成集，对比纯向量基线在这些 query 上的答案正确率；如果提升不明显，优先用 metadata 过滤 + 结构化关系表 + 少量 SQL 覆盖，成本低一到两个数量级。
  2. 做成本建模：抽取阶段按「每千字文档消耗的 token」估算全量成本，社区摘要按层数近似超线性增长估算；把「全量重建一次」和「每月增量 N 篇」分别算出来，与业务对新鲜度的要求对齐，再决定语料范围（只对高价值语料建图）。
  3. 实体归一化先行：维护别名表 + embedding 聚类召回候选 + 人工抽检 top 实体，产出稳定的 canonical_entity_id；抽取阶段就落归一化后的 id，而不是事后合并。设置度数下限，孤立/低度数节点不进图，避免社区碎片化。
  4. 把图的写入设计成「以文档为中心可回滚」：每条边带 source_doc_id 与 doc_version，更新文档时先按 doc 反向裁剪旧边再加新边；社区摘要按节点局部失效（invalidate），只对受影响的社区重算，而不是整图重建。
  5. 在线加 query 路由：用小分类器或规则把 query 分成事实型 / 聚合型；事实型走向量分支，聚合型走图 + 社区摘要，混合时把图结果当 evidence 注入并严格限制 token 预算，避免把整个社区摘要塞进 prompt。
  6. 灰度与回归：按 query 类型分别看正确率与 p95 延迟，同时对「已删除文档的事实是否还被引用」做定期抽检。

真实场景

某项目把十几万份工单与设计文档一次性跑 GraphRAG：抽取阶段消耗了大量模型调用才完成，图和社区摘要建好后上线。观察到的典型现象是：普通「XX 怎么配置」类问题答案与原来的向量 RAG 基本无差别，只有「哪些模块同时依赖这两个服务」「这个季度反复出现的问题集中在哪些组件」这类聚合型问题明显变好；同时新增文档后，每次重建社区摘要耗时很长，且摘要里偶尔还能看到已经下线文档里的旧事实。排查路径：第一步按 query 类型拆分日志，确认收益集中在少部分聚合型 query；第二步抽样失败案例，发现同一供应商/组件在图中分裂成多个节点（归一化缺失），摘要被重复实体稀释；第三步检查更新流程，发现文档更新走的是 append 而非「先删旧边」，且社区重建是全量触发。改进方向是缩小建图语料范围、补齐 canonical id、改成按文档反向裁剪 + 局部社区失效，并给在线加 query 路由。

Q：如果业务方坚持「全部语料都要建图」，你怎么回应？

A：不直接否定，而是把成本与收益摊开：给出全量抽取的 token 成本、首次建图时长、增量重建频率对应的月度开销，以及按 query 类型的收益分布——通常 80% 以上流量是事实型，图的边际收益集中在少数聚合型 query 上。然后给折中方案：按业务价值给语料分级（高频引用文档先建图），或用更轻的抽取器（规则 + 词典辅助）先覆盖实体与关键关系，把 LLM 抽取留给核心语料。

08混合检索的关键字分支偶发 500、高亮字段为 null 就报错：词法索引的边界数据该怎么治理与降级

进阶 ｜ 混合检索词法索引多语种降级设计 ｜ issue来源 ↗

为什么会有这个问题

混合检索里大家把注意力放在向量侧，词法/全文分支常被当成「配一下就行」的基础设施，但它对输入数据的敏感度远高于向量：stemmer 按语种分词、payload 索引要求字段类型一致、highlight 依赖字段可被匹配到。一旦出现未验证的语种字符、带变音符的词形、nullable 字段里的 null，词法引擎可能在分词阶段抛异常直接返回 5xx，而不是「召回为空」。更糟的是这类错误是数据相关的长尾——同一批查询 99% 正常，某个语种或某几条文档一旦命中就稳定失败，客户端重试还会放大成雪崩。常见错误认知是「词法失败就当没召回」，但如果异常没被隔离在词法分支内，它会污染整个混合检索请求。

怎么做

  1. 把词法分支做成「可失败且失败可观测」的独立单元：单独设超时（远小于整体预算）、捕获所有异常、失败时返回空列表并 fail-open 到纯向量分支；同时按语种/字符集/错误类型打点，避免错误被静默吞掉。
  2. 建语种白名单：只对已验证过 stemmer 与分词的语种启用词法索引，新语种上线前用真实语料做回放（包含变音符号、大小写、混合语言、emoji、超长 token），验证通过再加入白名单；白名单之外的语种走向量分支或字符级 n-gram 匹配。
  3. 写入侧做规范化与校验：null 统一归一化为空串（或直接不写该字段），避免 nullable 字段在 match/highlight 时字段缺失；对文本做 NFC 规范化、控制字符剥离、长度截断，并在入库前跑一个轻量 preflight，把异常样本挡在索引外而不是等查询时炸。
  4. 高亮不要依赖引擎：在应用层用召回的原文做字符串匹配高亮，或对引擎返回的 highlight 做容错（字段缺失就回退到原文首段），避免「高亮失败导致整个响应构造失败」。
  5. 做数据分桶监控：按语种、是否有 payload 词法索引、字段是否为空统计 5xx 率与空召回率；对「同一 query 稳定失败」做指纹聚合，便于快速定位是数据问题还是引擎版本问题，并在升级引擎版本时把已知边界样本纳入回归集。
  6. 准备降级链：词法失败 → 纯向量；向量也失败 → 缓存/serve_stale 或明确返回降级提示；上游不要无脑重试 5xx，对可重试错误加 jitter 与上限。
LEXICON_LANGS = {"zh", "en"} def lexical_search(q, lang, limit=20, budget=0.15): if lang not in LEXICON_LANGS: return [] try: return call_with_timeout( lambda: client.search_text(q, lang=lang, limit=limit), budget) except Exception as e: metrics.incr("lexical_fail", tags={"lang": lang, "err": type(e).__name__}) return [] def normalize_payload(payload): out = {} for k, v in payload.items(): if v is None: continue out[k] = unicodedata.normalize("NFC", str(v))[:MAX_FIELD_LEN] return out def hybrid_search(q, lang, vec): text_hits = lexical_search(q, lang) vector_hits = vector_search(vec, limit=20) return fuse(text_hits, vector_hits)

真实场景

某项目做多语种知识库的混合检索，上线后前端偶发「搜索整个不可用」：同一批查询大部分正常，但某些查询稳定 5xx。按语言分桶后发现集中在少数小语种词形上——词法索引在分词阶段直接抛异常，请求返回 500；客户端带重试，单个坏查询在高峰期被放大成一片 5xx。另一条线是「高亮失败」：文档里的可匹配字段为 null 时，highlight 找不到字段直接报错，导致本来已经召回成功的请求在构造响应阶段失败。排查路径：先按语言和字段空值率给 5xx 分组，确认与某个语种字符和 null 字段强相关；再用最小请求复现，确认异常发生在词法分支内部而非向量分支；最后检查客户端重试策略，发现 5xx 被无上限重试。修复是把词法分支隔离成可失败单元并 fail-open、语种白名单 + 入库前 preflight、null 归一化，高亮改到应用层做。

面试官追问

Q：fail-open 到纯向量分支，会不会让召回质量在不知不觉中下降？

A：会，所以降级必须可观测：词法失败不只是返回空，要打点并算「降级请求占比」与「降级请求的答案采纳率/无答案率」。设阈值告警，超过阈值就当作故障处理，而不是长期静默降级。同时把失败样本沉淀为回归集，在引擎升级或新语种接入前回放。

Q：为什么不直接对所有语种关掉 stemmer，用字符 n-gram 更省事？

A：字符 n-gram 对中文、日文这类无空格语言其实不错，对英文会显著增加索引体积与误召回，而且丢掉词形归并后同义词召回变差。更务实的做法是分层：拉丁语种用验证过的 stemmer，CJK 用 n-gram 或分词器，未验证语种先退回字符级匹配并把词法权重调低，等语料回放通过再提权重。

09中间件注入的 trace_id 在接口里读不到，500 响应还丢了 CORS 头：BaseHTTPMiddleware 的边界与中间件顺序

资深 ｜ middlewarecontextvarsCORS请求生命周期

为什么会有这个问题

Starlette 的中间件栈是分层的：最外层 ServerErrorMiddleware，中间是用户通过 add_middleware 注册的中间件（后注册的反而更靠外），再往里是 ExceptionMiddleware，最内是路由。未捕获异常一路向上传递到 ServerErrorMiddleware，由它直接生成一个纯文本 500；此时内层的 CORSMiddleware 根本没见到 http.response.start，因此无法补上 Access-Control-Allow-Origin。浏览器把这次 500 报成跨域错误，真实的堆栈被掩盖。第二个问题来自 BaseHTTPMiddleware：它用 anyio 的 task group 把下游 app 放进独立的 task 里执行，contextvars 在 task 创建时按「向下拷贝」传播——中间件里 set 的值下游可见，但下游 endpoint、依赖、异常处理器里 set 的值不会回流到中间件，导致中间件层的访问日志、耗时统计里 trace_id 时有时无。它还会让流式响应多包一层，客户端提前断开时的取消语义改变，出现 No response returned 之类的怪象。

怎么做

  1. 固定中间件顺序：CORS 一定最后 add_middleware（最外层）；需要覆盖 500 场景时，用 application = CORSMiddleware(app=app, ...) 把 CORS 包在整个 ASGI app 外面。
  2. 把 trace 注入和耗时日志改写成纯 ASGI 中间件，直接包装 send，而不是用 @app.middleware('http') 的 BaseHTTPMiddleware 写法；contextvar 在入口 set、在 finally 里 reset，避免跨请求泄漏。
  3. 业务级上下文（用户、租户、trace）优先用 Depends 注入，而不是在中间件里塞 request.state 再指望下游回写。
  4. 注册 app.add_exception_handler(Exception, handler) 时要意识到它挂在 ServerErrorMiddleware 上；要么在最外层 CORS 处理，要么在 handler 内手动补 CORS 头和 trace 头。
  5. 补两条集成测试把行为锁死：断言未捕获异常返回 500 且响应头含 access-control-allow-origin；断言 endpoint 内 logger 输出的 trace_id 与响应头一致。
import uuid import contextvars from fastapi import FastAPI from starlette.datastructures import MutableHeaders from starlette.middleware.cors import CORSMiddleware from starlette.types import ASGIApp, Scope, Receive, Send trace_id: contextvars.ContextVar[str] = contextvars.ContextVar("trace_id", default="-") class TraceMiddleware: def __init__(self, app: ASGIApp) -> None: self.app = app async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None: if scope["type"] != "http": return await self.app(scope, receive, send) incoming = dict(scope["headers"]).get(b"x-trace-id", b"").decode() or uuid.uuid4().hex token = trace_id.set(incoming) async def send_with_trace(message): if message["type"] == "http.response.start": MutableHeaders(scope=message)["x-trace-id"] = incoming await send(message) try: await self.app(scope, receive, send_with_trace) finally: trace_id.reset(token) app = FastAPI() app.add_middleware(TraceMiddleware) # 内层 app.add_middleware(CORSMiddleware, allow_origins=["*"], # 后加即更外层 expose_headers=["x-trace-id"])

真实场景

某项目的日志平台按 trace_id 串联前后端，接入后发现约一半请求的访问日志里 trace_id 为空，但接口内部打的日志却有值；同时前端控制台频繁报跨域，后端却只看到零星 traceback。排查路径：先用 curl -i 直打接口，能拿到 500 且响应体是纯文本 Internal Server Error，但没有 access-control-allow-origin 头——说明这次响应由最外层生成、绕过了 CORS；再看中间件写法是 @app.middleware('http')，在中间件里 set contextvar 后立刻打日志，发现下游 endpoint 里额外 set 的字段回流不到中间件，异常路径下更是整个上下文丢失；把中间件换成纯 ASGI 实现、CORS 移到最外层后两个症状同时消失。

  SE->>CORS: 调用内层

面试官追问

Q：为什么不在 BaseHTTPMiddleware 里 try/except 把所有异常兜住，统一返回 JSON？

A：能兜住，但必须原样 re-raise 或自己构造完整响应，否则会把 ServerErrorMiddleware 和 ExceptionMiddleware 的职责搅在一起；而且 BaseHTTPMiddleware 给每个请求多建一个 task，流式响应下客户端断开的取消传播会被改变。所以网关级的行为（trace、CORS、限流）用纯 ASGI 中间件，业务级错误用 exception handler，权限用 Depends。

Q：后台任务里还能拿到中间件设置的 trace_id 吗？

A：Starlette 的异步 BackgroundTask 在响应发送后、同一个 task 上下文里 await 执行，可以看到；同步后台任务走 anyio 线程池，当前 context 会被复制进去，一般也能看到。但如果任务自己 asyncio.create_task 出去，或在别处新 set，就不会同步，跨进程、跨队列时必须把它显式放进消息体里携带。

10单测单独跑都过，一起跑就报 attached to a different loop：dependency_overrides 与连接池的测试隔离

进阶 ｜ 测试dependency_overrides事件循环fixture

为什么会有这个问题

两个独立的坑叠在一起。第一，app.dependency_overrides 是挂在 app 对象上的全局 dict，fixture 里 override 了 get_current_user 或 get_session 却没清理，后续用例拿到的是上一个用例的 mock 或已关闭的会话——典型症状是该返回 401 的用例意外通过，或者报「Session is closed」。第二，驱动类连接池（asyncpg / aiomysql / httpx.AsyncClient）在创建时绑定事件循环；如果 engine 是模块顶层实例化的，第一次用例在 loop A 建好连接，第二个用例在 loop B（pytest-asyncio 默认按用例新建 loop，TestClient 每次 with 也会起自己的 portal）复用时就会抛 Task got Future attached to a different loop 或 Event loop is closed。单独跑绿、随机顺序跑红，正是这两个全局状态被跨用例复用的特征。

怎么做

  1. 把 engine、池、外部 client 的创建从模块顶层挪进 lifespan 或 fixture，销毁时 await engine.dispose()，保证「谁创建、谁绑定、谁释放」都在同一个 loop。
  2. 用 yield fixture 包住 override，并在 finally 里 app.dependency_overrides.pop(key, None)（或恢复到快照），不要在用例内散落赋值。
  3. 测试客户端统一用 httpx.AsyncClient + ASGITransport，并用 asgi-lifespan 的 LifespanManager 显式驱动 startup/shutdown，确保生命周期钩子和用例跑在同一 loop。
  4. 若坚持复用一个全局 engine，就必须让整个测试会话共用一个 loop（固定 loop fixture 或 asyncio_mode=auto + session 级 loop），二选一，不要混用。
  5. 在 CI 里加一轮乱序或两两组合的抽样执行，专门用来暴露这类隐式顺序依赖。
import pytest_asyncio from httpx import ASGITransport, AsyncClient from asgi_lifespan import LifespanManager from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine from app.main import app from app.db import get_session @pytest_asyncio.fixture async def client(): engine = create_async_engine("postgresql+asyncpg://u:p@localhost/test") session_factory = async_sessionmaker(engine, expire_on_commit=False) async def _override(): async with session_factory() as session: yield session app.dependency_overrides[get_session] = _override try: async with LifespanManager(app): async with AsyncClient(transport=ASGITransport(app), base_url="http://test") as c: yield c finally: app.dependency_overrides.pop(get_session, None) await engine.dispose()

真实场景

某项目的 CI 上偶发红灯，本地单独跑该用例 100% 通过，全量跑则两三个用例随机失败；错误栈里出现 RuntimeError: Task 绑定到了另一个 loop 或 Event loop is closed。另一个更隐蔽的症状是：鉴权用例里断言「未登录返回 401」却拿到了 200。排查路径：先 pytest -p no:randomly 固定顺序复现，确认是顺序相关；在用例开头打印 app.dependency_overrides 的键，发现残留了上一个用例注册的 fake_user；再全局搜索 create_async_engine，发现它写在模块顶层、被 import 时创建，连接池因此绑在第一个 loop 上。把 engine 移到 fixture、override 用 yield + finally 清理后，全量与乱序都稳定通过。

面试官追问

Q：为什么用 TestClient 单跑时不报跨 loop 的错？

A：TestClient 每次进入上下文都新起一个 portal 和事件循环，模块级 engine 的连接池是在第一个 loop 上第一次用时才真正建连；只要后续用例没复用到池里的旧连接就不炸，一旦复用（或 dispose 不在同一 loop）就报错。所以它更像偶发问题，而不是必现问题。

Q：生产代码要怎么配合，才能让测试容易替换？

A：所有共享资源（连接池、模型 client、HTTP 客户端）只在 lifespan 里创建并挂到 app.state，业务侧通过 Depends 从 app.state 取；模块顶层不做实例化，避免 import 即绑定 loop，也让测试可以整体替换 app.state 或 override 依赖。
