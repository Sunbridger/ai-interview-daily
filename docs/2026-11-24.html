01Agent 长期记忆越用越蠢：写入噪声、召回污染与遗忘策略怎么治

资深 ｜ memory上下文工程召回排序评测 ｜ 面经来源 ↗

为什么会有这个问题

很多团队把 Memory 理解成“把对话 append 进向量库”，结果记忆只增不减：一次性闲聊、过期偏好、重复摘要全被写入，召回时又只按向量相似度取 top-k，最终无关记忆挤占上下文、旧事实覆盖新事实，模型表现随使用时长下降。Memory 的难点不在存，而在写入准入、冲突消解、分层 TTL 与召回预算控制；只加向量库不解决污染，反而放大成本与延迟。

怎么做

  1. 先分层：working memory 只保留当前任务槽位；episode 存带时间戳的交互摘要；semantic 存实体-属性-值事实。三类分开 TTL、召回权重与存储，禁止全部塞进同一向量集合。
  2. 写入前置闸门：候选记忆先过重要度阈值、去重相似度、敏感信息过滤；episode 设更高阈值，避免把寒暄写进长期库。抽取时保留 provenance（会话 id、来源消息），便于回溯和按用户删除。
  3. 冲突消解：semantic 记忆以 entity+attribute 为唯一键，新值写入时把旧值置为 superseded 而非物理删除；召回只取 active 版本，保留变更历史用于审计。
  4. 召回打分融合 relevance、importance、recency，再按 token 预算裁剪；低于相关性阈值的不注入，防止无关记忆稀释当前指令。
  5. 评估与淘汰：离线看 recall@k 与端到端答案正确率，线上做“关闭长期记忆”的 A/B；定期把低频 episode 压缩成摘要，用 TTL 淘汰，监控记忆注入 token 占比与采纳率。

真实场景

某项目 Agent 上线两个月后用户反馈“它记得乱七八糟的偏好”，同时首 token 延迟上升、context token 持续增长。抽样被召回的记忆发现：同一偏好有多个措辞重复条目、旧偏好没有失效、一次性闲聊被写成长期记忆，且注入的记忆 token 占比明显上升。排查路径是先把召回结果按来源和写入时间分组，统计重复率与过期率，再回看写入日志确认闸门缺失；修复后改为分层存储、写入去重和 entity+attribute 版本替换，并加召回预算裁剪。

面试官追问

Q：用户说“以后都用中文回答”，这类偏好和临时指令怎么区分？

A：偏好写入 semantic memory，带 scope（全局/项目/会话）与 source；临时指令只进 working memory。召回时按 scope 过滤，冲突时项目级覆盖全局级，会话级指令默认不落长期库。

Q：记忆删除与合规怎么做？

A：每条记忆带 subject_id 与 provenance，支持按用户/会话级联删除；向量库与原文库双删，删除走异步任务并记录墓碑，防止重建索引时复活。

02Prompt Caching 命中率骤降：上下文拼装顺序与工具大结果外置怎么改

进阶 ｜ prompt-caching上下文工程成本优化MCP ｜ 面经来源 ↗

为什么会有这个问题

Prompt Caching 按前缀逐字节匹配，只有稳定前缀完全一致才命中；很多实现把当前时间、用户额度、随机 id 拼进 system，或工具 schema 由未排序 dict 序列化，导致每轮前缀都变，缓存写入有溢价却几乎不命中。另一个常见错误是让 MCP 工具返回的大 JSON 原样进历史，后续每轮重复计费并挤占上下文。缓存不是打开开关就省钱，它依赖上下文拼装纪律。

怎么做

  1. 给每次请求算稳定前缀哈希（system、工具 schema、few-shot、历史），日志记录 prefix_hash 与 cache_read/cache_creation token；采样两轮请求做首个差异位置 diff，定位是谁在污染前缀。
  2. 重排上下文：静态 system 与工具定义放最前，工具按 name 稳定排序；历史 append-only；当前时间、用户配额、随机 id 等动态字段后置到 user 消息；会话中不改 system。
  3. 在稳定段末尾设置 cache breakpoint（按 provider 支持），保证断点前内容逐字节一致；工具 schema 走规范化 JSON 序列化，避免 dict 顺序漂移。
  4. 工具大结果外置：超过阈值（如 8KB）落对象存储，上下文只放摘要、句柄与关键字段；需要细节时通过单独的 fetch 工具按行号/JSONPath 取片段。
  5. 监控缓存命中率与单位请求成本并设回归告警；多租户场景缓存键要带 tenant，防止跨租户复用与数据泄露。
from hashlib import sha256 def render_tools(tools): return '\n'.join(f"{t['name']}: {t['description']}" for t in tools) def build_prompt(system_static, tool_schemas, history, user_input): tools = sorted(tool_schemas, key=lambda t: t['name']) msgs = [ {'role': 'system', 'content': system_static}, {'role': 'system', 'content': render_tools(tools)}, ] msgs.extend(history) msgs.append({'role': 'user', 'content': user_input}) return msgs def compact_tool_result(text, store, limit=8000): if len(text) <= limit: return text key = sha256(text.encode()).hexdigest()[:16] store.put(key, text) head = text[:limit] return f'ref={key} total={len(text)}\n{head}' def log_prefix_hash(msgs): blob = ''.join(m['content'] for m in msgs) return sha256(blob.encode()).hexdigest()[:12]

真实场景

某项目接入 Prompt Caching 后账单没有下降，p50 延迟反而上升，监控里 cache_read_input_tokens 长期接近于零。抓两轮请求体做 diff，发现 system 中拼了当前时间和用户额度，工具 schema 每次由未排序 dict 序列化；另有一个 MCP 工具返回大 JSON 直接进历史，后续每轮重复计费。排查路径是记录 prefix_hash、定位首个差异字节、改上下文顺序并规范化 schema，同时把大结果外置为句柄，命中率恢复后单位请求成本才下降。

flowchart TD
  A[请求拼装] --> B[稳定段 系统提示与工具 schema]
  B --> C[缓存断点]
  C --> D[追加式会话历史]
  D --> E[动态段 当前时间与用户输入]
  E --> F[工具大结果外置为引用]
  F --> G[调用模型]
  G --> H[记录前缀哈希与缓存命中指标]

面试官追问

Q：外置后模型需要看完整结果怎么办？

A：增加 fetch 工具，用 handle + 行号/JSONPath 分段读取，单次返回有上限；对高频小结果不落盘，设阈值和命中统计，避免为省 token 增加一轮工具调用。

Q：缓存写入有溢价，怎么判断值不值？

A：按 cache_creation 与 cache_read 的单价和 TTL 算盈亏平衡次数；长 system、多轮工具调用场景收益明显，短会话或前缀不稳定时关闭。用 prefix_hash 命中率和单位请求成本做灰度对照。

03Memory 检索预算被长会话吃穿：召回窗口、压缩与写回时机怎么权衡

资深 ｜ memory上下文工程成本控制召回质量 ｜ 面经来源 ↗

为什么会有这个问题

Agent 的 Memory 常被误当成「把历史都塞进向量库就行」，真实工程里它同时受三方面挤压：一是 token 预算固定而会话轮次线性增长，召回条目与系统提示、工具结果争抢同一窗口；二是写入端没有准入标准，模型随手生成的总结、失败的工具调用残留、用户的口误全被固化，后续召回被这些噪声占满；三是召回端用同一套 top-k 应对所有问题，导致「查偏好」拿到一堆流程日志，「查进度」却只拿到闲聊。更隐蔽的是写入时机：多数实现让 Agent 在每轮结束时异步总结，若总结任务与主流程共享同一份上下文快照，重试或并发会让同一事实写入多份互相矛盾的版本，召回时冲突无人裁决。

怎么做

  1. 先给 Memory 分层并明确各层的预算上限：工作记忆（当前会话窗口，按 token 硬上限计算，如占模型窗口的 60%）、情景记忆（会话摘要 + 关键事件，按条数与字节双限）、语义记忆（用户偏好、稳定事实，条数少但要求高置信）。每层独立配额，任一层的溢出不得挤占其它层。
  2. 写入端做准入闸门：只有满足「事实性、稳定性、可复用」三条的内容才允许持久化；工具原始返回、报错堆栈、模型臆测统一丢弃。写入前做实体与谓词归一化（如把「喜欢简短回答」「回复要短一点」归到同一 key），用 (entity, predicate) 做幂等键，冲突时按时间戳 + 来源可信度裁决，旧版本置为 superseded 而不是删除。
  3. 召回端改成按意图路由的多路召回，而不是固定 top-k：先用一个轻量分类（或规则）判断本轮是查偏好、查历史进度、还是查外部知识，各路使用不同的检索器与配额；召回结果必须过一次重排与去重，再做「与当前问题是否相关」的 LLM 二判，剔除噪声后再拼进上下文，且拼装顺序固定（稳定事实在前、易变状态在后）以保住前缀缓存。
  4. 压缩策略要在会话内周期性触发而不是等到超窗报错：保留最近 N 轮原文 + 一份滚动摘要，摘要只写决策、结论、未完成事项与用户明确约束，不写过程；摘要本身标记为派生数据，可重算，避免成为不可回滚的污染源。
  5. 设置可观测指标并设回归用例：记录每次召回的命中率（召回条目被模型实际引用）、噪声率（被判不相关而丢弃的比例）、每轮平均 memory token 占比、冲突裁决次数。用一组固定脚本会话做回归，改动写入或召回策略后重跑，比较答案正确率与 token 成本。

真实场景

某项目把 Agent 的 Memory 直接接到向量库，写入端每轮自动总结、召回端固定 top-8。上线一个月后出现典型症状：会话到第 15 轮左右开始答非所问，用户重复说过的偏好在被纠正后仍然出现旧版本；同一批回归用例上，memory 相关 token 占比从十二三成涨到占满上下文，首字延迟明显上升，但人工抽查发现召回的条目大半和当前问题无关。排查路径：先按层拆分 token 占比，确认是情景记忆无限膨胀而非系统提示变长；再抽样 50 条写入记录，发现大量工具原始返回与失败调用被总结成「用户希望重试」这类伪事实；最后复现出冲突场景——同一 key 存在三条不同值的 active 记录，检索时按向量相似度取到了旧的那条。改为分层配额 + 写入准入 + 按意图路由召回后，无关召回比例与每轮 memory token 都明显下降，纠正后的偏好能稳定生效。

面试官追问

Q：滚动摘要和原始对话冲突时，模型该信哪一个？你怎么在上下文里表达这种优先级？

A：优先原始近期对话，摘要是派生数据、只作背景。实现上在拼装时给两类内容加显式区段标题（如「以下是较早会话的摘要，可能不完整」与「以下是最近的实际对话」），并在系统提示里声明冲突时的取值顺序；同时对摘要里提到的关键结论保留原文引用（消息 id 或时间戳），当模型引用摘要结论时可回溯到原始消息校验。若摘要与原文矛盾且影响到最终答案，则触发一次轻量重算，用原始消息重建摘要而不是让模型自行调和。

Q：如果为了省 token 把 memory 检索做成异步预取，会不会引入「用了上一轮上下文」的错误？

A：会，这是典型的时序错配。关键在于区分「与当前 query 无关、可预取的稳定层」和「必须依赖当前 query 的召回」：语义记忆中的用户画像、权限、长期偏好在会话开始即可一次性载入，属于可预取部分；而意图相关的召回必须在本轮 query 确定后同步执行。预取结果要打上 session 版本号，若本轮已经发生写入导致版本前进，则丢弃预取结果回退到同步召回，宁可多一次检索延迟也不要答错。

04运行时动态编排的 Agent 花在选择上：路由漂移、并行收益与预算回收怎么控

资深 ｜ multi-agent动态编排延迟成本质量回归 ｜ 面经来源 ↗

为什么会有这个问题

固定拓扑的多 Agent 容易调，但覆盖不了任务复杂度差异巨大的流量，于是很多团队引入运行时动态编排：由一个规划器在每一步决定调用哪个子 Agent、串行还是并行、要不要追加一轮。问题随之而来。第一，路由决策本身是不稳定的——同一输入在不同时刻可能被分到不同子 Agent，温度、工具描述微调、上下文顺序变化都会让分布漂移，线上表现为「同样的工单昨天走两个 Agent，今天走五个」。第二，规划器只看语义不看预算，容易把可并行的子任务串行化，或在已经拿到足够信息后继续追加验证轮，延迟与成本随步数指数式放大。第三，并行分支的失败语义不统一：一个分支超时到底算整体失败还是降级返回部分结果，没有约定就会出现半成品答案被当成完整答案输出。第四，动态拓扑让 trace 无法对齐，出了问题只能看到一串无层级的调用，无法归因到是哪次路由决策导致的劣化。

怎么做

  1. 把「动态」限制在可控空间里：预先声明可用的子 Agent 集合、每个 Agent 的能力标签、输入输出契约与成本档位（模型、平均 token、典型耗时），规划器只能在这个注册表里做选择，不能凭空生成新角色。路由决策输出结构化对象（agent_id、并行分组、预算上限），而不是自由文本。
  2. 给每次编排设总预算与逐步预算：总预算按 token 与 wall-clock 双维度设上限，每进入一步先扣减；当剩余预算低于某个比例时，规划器被强制切换到「收敛模式」（只允许调用最快的 Agent 或直接由主模型作答）。并行分组要有扇出上限，避免一个分组把全部 Agent 拉起来。
  3. 统一并行分支的失败语义：把分支结果建模为 ok / partial / failed 三态并携带置信与缺失字段；聚合器按契约判断是否满足最小可交付集合，不满足则降级为「说明缺失 + 给出部分结论」，绝不把 partial 当 ok 输出。超时分支不阻塞已经完成的分支，但要在答案里显式标注未完成部分。
  4. 把路由决策变成可评估对象：为编排过程记录每一步的输入摘要、候选集、被选中的 Agent、理由、实际耗时与产出质量。用离线回放 + 小流量灰度对比「动态编排」与「固定拓扑」的成功率、P95 延迟、单任务成本三条线，任何一条显著劣化就回退。判据写死，不靠感觉。
  5. 引入决策稳定性约束：对同一输入的重复请求，在同样的上下文下应尽量得到同样的路由；可通过降低规划温度、对候选集排序取确定性 top-1、以及对路由结果做缓存（以任务特征指纹为 key，带 TTL）来实现。漂移检测用路由分布的散度指标，超出阈值即告警。
  6. 治理 trace：给每次编排分配 orchestration_id，每一步的 span 上带 orchestration_id + step_index + agent_id + 并行分组号，让同一棵调用树可在追踪系统里完整还原，出问题时能直接定位到「在哪一步、由谁决定、为什么」。

面试官追问

Q：怎么判断动态编排带来的质量提升是真实的，而不是聚合器把更多分支内容拼进答案带来的「看起来更全」？

A：把评估拆成「结论正确性」和「覆盖完整性」两个独立维度，并且用不依赖字面长度的判据：结论正确性用带标准答案集的离线评测（对关键字段做精确匹配或规则校验），覆盖完整性用「必须回答的子问题清单」逐项勾选。同时做一个反事实对照——把动态编排的多分支输出交给同一个聚合器合成，与固定拓扑的单分支输出做同条件比较，若两者在正确性上无差异，说明收益来自拼装而非编排本身。另外抽样人工盲评，隐藏来源标签，避免评审者被答案长度误导。

Q：如果规划器在收敛模式下仍被允许调用子 Agent，预算控制是不是形同虚设？

A：是，收敛模式必须改变的是「可选项集合」而不是「建议」。实现上把预算水位映射为能力白名单：预算充足时白名单包含全部 Agent，低于阈值时白名单收敛为最快的一到两个，耗尽时白名单为空、强制主模型直答。规划器的输出要在这个白名单上做交集校验，越界直接拒绝并重新规划一次，第二次仍越界则走兜底路径。这样预算约束是硬边界的，而不是提示词里的软性建议。

05离线用大模型生成假设答案来提升召回，上线后延迟和幻觉反而增加：HyDE 的适用边界与降级怎么定

进阶 ｜ HyDE查询改写召回率延迟预算 ｜ 面经来源 ↗

为什么会有这个问题

用户提问往往很短、口语化，且与知识库文档的写作风格（术语密集、陈述句）之间存在表达鸿沟，导致 query embedding 落在与文档向量不同的区域，出现「答案就在库里但召不回」。HyDE 的思路是先让 LLM 生成一段假设性答案，再用这段「伪文档」去检索，把查询侧向量拉近文档侧分布。常见错误认知有两个：一是把 HyDE 当成万能提效手段，忽略它引入了额外的 LLM 调用（首 token + 生成完整段落）、把生成模型的幻觉带进检索、以及在事实型精确查询（编号、错误码、人名）上会稀释关键词信号；二是只在离线评估集上调，忽略线上高并发下的 p99 抖动与成本。

怎么做

  1. 先判定是否真的需要：把线上 badcase 按「query 与命中片段的向量距离分位」和「关键词匹配情况」分桶，只有当短查询（如少于 8 个 token）、无稀有实体、召回为空或 top1 分数低于阈值时才触发 HyDE，其余走原始 query，避免全量加一次 LLM 调用。
  2. 实现上生成 1 段、长度受限（如 80–150 字）的假设答案，并显式约束「不要编造具体数字、专有名词」；同时保留原始 query 向量，做双路召回后融合，而不是用假设答案直接替换 query。
  3. 对含数字、错误码、型号的 query 做实体检测，命中则跳过 HyDE 或强制开启 BM25 混合召回，防止假设答案里的错误实体把正确文档挤出候选集。
  4. 设置超时与降级：HyDE 调用设 300–600ms 超时，超时或失败立即回退到原始 query 检索；把 HyDE 结果按 query 归一化做短 TTL 缓存（如几分钟），消化重复提问。
  5. 用 A/B 或影子流量对比四组指标：Recall@k、首答正确率、p95/p99 延迟、每次查询成本；只有在 Recall 提升能转化为答案正确率提升时才保留，而不是只看召回。
  6. 把假设答案写入 trace，便于事后归因：区分「HyDE 引入错误实体导致的错答」和「原本就召不回」两类问题。

面试官追问

Q：HyDE 和 query rewriting / query expansion 有什么区别，什么时候选哪个？

A：query rewriting 是把用户口语改写成检索友好的表达，保留原始语义意图，成本低、可控性强；query expansion 是补同义词或上位词，提升召回宽度但容易引入噪声；HyDE 是生成「答案形态」的伪文档去对齐文档侧向量分布，对「短问题 vs 长文档」的表达鸿沟最有效，但引入生成幻觉和更高延迟。经验判据：查询歧义大、需要澄清意图 → rewriting；术语不一致、同义表达多 → expansion；查询极短且知识库文档是长篇陈述体 → HyDE。三者可以叠加，但要分别量收益。

Q：怎么证明 HyDE 带来的召回提升是真实的，而不是评估集偏差？

A：第一，评估集要按线上 query 分布采样，包含空召回和事实型查询，不能只用「能答出来」的样本；第二，看 Recall@k 的同时看答案正确率和引用命中率，因为召回提升可能是召回了更多语义相近但事实错误的片段；第三，做分组分析（短查询/长查询/含实体/不含实体），确认收益集中在预期分组；第四，用影子流量跑线上真实分布，比较端到端指标而不是只看离线。

06用二进制量化把索引内存压下去后长尾 query 答不出来：量化的召回损失怎么定位、怎么补

资深 ｜ 向量量化二进制量化召回损失混合检索 ｜ 面经来源 ↗

为什么会有这个问题

把 float32 向量换成 binary 或 PQ 编码，本质是用更少的比特保留方向信息。二进制量化只保留每一维的符号位，等价于在超球面上做极粗的角度划分，向量间的细微差异被抹平：当多个候选片段的相似度非常接近时（长尾、细节型、近义文档多的场景），排序被打乱，top-k 里就混进了错的片段。常见错误认知是「量化只影响精度不影响召回，调大 top-k 补回来就行」——实际补 top-k 会同时放大候选集与重排成本，而且当哈希碰撞严重时，正确答案根本没进候选池，加大 k 也捞不回来，还会拖高延迟。另一个误区是忽略不同 embedding 模型对量化的友好度差异：分布各向异性强、维度低、或者模型本身未做归一化的向量，量化损失会显著更大。

怎么做

  1. 先量化损失，而不是先调参：用同一批真实 query，在原始 float 索引与量化索引上分别取 top-100，计算 Recall@k 的差值，并按 query 分桶（高频/长尾、单跳/多跳、含实体/纯语义），定位损失集中在哪一类。
  2. 分离两类误差：一是「候选池未命中」（正确答案不在量化索引的 top-N 中），二是「排序错乱」（在池中但被挤出 top-k）。前者必须靠扩大候选或混合召回，后者可以靠重排修复。
  3. 落地 rescoring 两段式：量化索引只负责粗召回（取较大的 N，如 100–200），再用原始 float 向量或交叉编码器对候选重排到 top-k；float 向量可放内存或磁盘，只对候选集加载。
  4. 对二进制量化叠加混合召回：语义分支走量化向量，词法分支走 BM25/全文索引，用 RRF 融合，弥补符号位抹平导致的近义文档混淆。
  5. 做参数与模型侧的取舍：优先选支持归一化的 embedding（余弦相似度下二进制量化更稳），必要时提升维度或用 int8 标量量化替代二进制；对比不同量化粒度的召回-内存曲线，而不是只看内存。
  6. 上线做灰度与监控：监控 recall 相关的线上代理指标（引用命中率、拒答率、用户追问率），一旦长尾 query 组指标下滑就回滚或切到混合模式。

真实场景

某项目为压内存把百万级向量集合改成二进制量化，内存占用明显下降、写入也变快，但上线后出现一类稳定复现的 badcase：用户问的是文档里某条细则的具体适用条件，库里存在多个高度相似的条款片段，回答开始张冠李戴，引用到相邻条款。排查路径：用线上真实 query 重放，对比量化前后 top-100 的候选集合，发现正确答案在量化索引里排到了 100 名开外，属于「候选池未命中」而非排序问题；同时该组 query 的向量相似度分布非常密集，符号位区分不开。最终改为量化粗召回 + float 重排 + BM25 融合，并把 coarse_n 按长尾组单独调大。

面试官追问

Q：二进制量化和 PQ 在召回损失上的差异来自哪里，怎么选？

A：二进制量化每维只存 1 bit 符号，压缩率最高、距离计算可用位运算，但只保留方向的正负，区分度极低，适合高维、归一化良好、候选充足且能重排的场景。PQ 把向量切段后用码本聚类中心近似，保留更多信息，同等压缩率下召回通常更好，代价是需要训练码本、查询时要做查表累加，且对数据分布漂移敏感（码本需重训）。选型判据：内存压力极端且能接受两段式重排 → 二进制；需要在中等压缩率下保持较高召回、数据分布稳定 → PQ 或 PQ 的改进变体；对精度要求高且内存尚可 → int8 标量量化往往是性价比最高的折中。

Q：如果 float 向量放在磁盘上做重排，延迟怎么控？

A：关键是限制重排规模并做局部性优化：coarse_n 要按延迟预算反推，而不是无脑加大；float 向量按 id 连续存放或按簇聚集，减少随机 IO；候选加载做并发批量读，避免逐条往返；对高频 query 的候选结果做短 TTL 缓存；必要时把热数据的 float 向量放内存、冷数据落盘，形成分层。上线前要用 p99 而不是均值来定 coarse_n。

07同一批召回片段换一下顺序答案就变了：上下文排布、位置偏置与块压缩怎么治理

资深 ｜ 上下文编排Lost in the Middle评估闭环token 成本 ｜ 面经来源 ↗

为什么会有这个问题

LLM 对长上下文的利用并不均匀，放在中间的片段被引用的概率明显低于首尾两段；而绝大多数 RAG 链路只是按相似度降序把 top-k 直接拼接，把最关键的证据放在中段；如果 k 偏大，噪声块还会稀释注意力。常见错误认知是「答案不好就加大 k、把上下文塞满」，实际效果往往相反：token 成本上升，中间位置的信息密度更低，模型更容易只依据首段作答，引用也常落在第一个块上。另一个隐性问题是切块把步骤、表格和跨段指代切断，模型只看到局部片段，无法还原完整语义。

怎么做

  1. 先做归因，不要急着改 prompt：固定同一批候选片段和同一批 query，只改变排列方式（相似度顺序、逆序、随机、把人工标注的金标块放在开头或结尾），观察答案正确率和引用命中率是否随位置波动。如果金标块换位置后答案就变，说明是位置利用问题；如果金标块无论放哪都答错，说明是切块质量或模型能力问题。
  2. 减少片段数量、提升密度：先按父块去重并合并相邻块，把 k 收到较小值（经验上 5 到 8 块），再用 rerank 截断；对超长块做抽取式压缩，只保留与 query 相关的句子，同时保留标题路径和行号。
  3. 调整位置策略：把 rerank 分数最高、与问题直接对应的证据放在开头和结尾，其余块按主题聚类后排列；多跳或汇总类问题不要一次性平铺，改成先分段提取再汇总的两阶段生成。
  4. 结构化上下文：每块都带 source_id、文档标题、章节路径和序号，块之间用明确分隔符隔开，并在 prompt 中要求逐条引用；生成后做引用校验，检查每条结论是否落在给出的块内。
  5. 建立回归指标：除答案正确率外，加入引用支持度、证据覆盖率、上下文 token 数和「引用落在第几块」的分布；上线时做 A/B 对比，避免只看个别 case 的观感。
  6. 守住成本边界：把上下文预算设成硬上限，超出时按重要性裁剪，而不是无限增加 k；对高频 query 缓存编排结果。
def dedup_by_parent(chunks): seen, out = set(), [] for c in sorted(chunks, key=lambda x: -x['score']): key = (c['doc_id'], c['parent_id']) if key in seen: continue seen.add(key) out.append(c) return out def arrange(chunks, k=6, mode='sandwich'): picked = dedup_by_parent(chunks)[:k] if mode == 'sim': return picked half = max(1, len(picked) // 2) front, back = picked[:half], picked[half:] return front + list(reversed(back)) def position_sensitivity(run_qa, queries, pool, modes=('sim', 'reverse', 'sandwich')): report = {} for mode in modes: hits = [] for q in queries: ctx = arrange(pool[q['id']], mode=mode) ans = run_qa(q['text'], ctx) hits.append(1.0 if q['gold_id'] in ans.citations else 0.0) report[mode] = round(sum(hits) / len(hits), 4) return report

真实场景

某项目做产品手册与 FAQ 的问答，最初把 top-20 全部拼进上下文，回答经常只引用第 1 条，问到手册中段的参数时开始编造或答成相邻型号；把 k 降到 6 并做父块合并后仍有波动。用位置实验复现：同一个金标片段放在第 1 位时答对，放在第 10 位时答错，说明检索本身没问题，是上下文利用问题。随后改成 rerank 截断、加压缩、高置信块前置和尾置，并加引用校验，引用正确率稳定下来，上下文 token 也明显下降；排查路径是「位置实验归因、切块与压缩、编排策略、引用校验指标」。

flowchart TD
    A[多路召回候选片段] --> B[按父块去重与邻近合并]
    B --> C[rerank 截断到少量高密度块]
    C --> D[高置信块置于首尾]
    D --> E[拼接带来源与章节的结构化上下文]
    E --> F[生成并做引用校验]
    F --> G[记录引用命中与位置分布]

面试官追问

Q：为什么不直接把 k 调大，让模型自己找？

A：k 变大会同时引入噪声和中间位置信息，注意力被稀释，成本线性上升，而且真正关键的片段被稀释在中间后更容易被忽略。正确方向是提高单块信息密度，而不是堆数量：父块合并、抽取式压缩、rerank 截断、把必要证据放到首尾。只有在问题本身需要跨多段汇总时，才用分段提取再汇总的方式扩展上下文。

Q：怎么区分是「位置问题」还是「召回/切块问题」？

A：做 oracle 注入：把人工标注的正确片段（或原文中对应段落）按不同位置注入上下文。如果注入后放首尾能答对、放中间答错，就是位置利用问题；如果放哪都答错，就是切块断裂、片段本身信息不足或模型能力问题。再用父块扩展和重新切块验证一次，即可定位。

08把 1536 维向量截到 512 维省存储，长尾类目召回崩了：降维的评估、重标定与回退怎么做

资深 ｜ embedding 维度Matryoshka分片评估影子索引 ｜ 面经来源 ↗

为什么会有这个问题

向量维度直接决定存储、内存和查询开销，截断维度看起来是最省事的降本手段，但这里有两个前提容易被忽略：只有经过 Matryoshka 式训练的模型，其向量前缀才近似可截断；普通模型直接切片，相当于把语义信息丢掉，而且不同维度上的能量分布被破坏。另一个常见错误是只看整体 recall@k：整体指标被高频简单 query 拉平，掩盖了长尾类目、含型号编号、专有名词这类 query 的下降。截断之后，向量模长和相似度分布都会变化，沿用原来的相似度阈值或拒答阈值，会出现漏召回或误召回；如果同时还叠了量化，误差叠加后更难定位。

怎么做

  1. 先确认模型是否支持前缀截断（MRL 训练），不支持就只能换低维模型或评估降维方法；不要直接对任意模型切片后上线。
  2. 建立分片评估集：按类目、query 长度、语言、是否含型号或编号、是否为长尾切片分别统计 recall@k 与 MRR，对比全维与截断维；同时构造高相似干扰项，观察区分能力。
  3. 截断后重新处理：重新做 L2 归一化；用分位数法而不是固定值重标定相似度阈值和拒答阈值；如果需要量化，先截断再量化，并单独评估组合后的损失。
  4. 归因排查时用 flat 暴力检索做基线，排除 ANN 参数造成的近似误差；再用相同索引参数分别建两套集合对比，确认是维度还是索引问题。
  5. 灰度与回退：建立低维影子集合，双写一段时间，按流量比例对比引用正确率、拒答率和长尾切片表现；低维只做粗召回，用全维向量对 top-N 重排，兼顾成本和精度。
  6. 成本核算要完整：算清存储、内存、构建时间、查询 QPS 的实际收益，与长尾损失对照；必要时按类目分层，高频类目走低维，长尾走全维集合路由。
  7. 准备回退开关：低维集合只是索引层，原文与全维向量保留在对象存储或关系库中，确保能在一个构建周期内重建并切回。
import numpy as np def truncate(vec, dim): v = np.asarray(vec, dtype='float32')[:dim] n = np.linalg.norm(v) return v / n if n else v def slice_recall(queries, gold, k=10, dims=(1536, 512, 256)): out = {} for d in dims: per_slice = {} for q in queries: qv = truncate(q['emb'], d) scored = sorted( ((float(truncate(c['emb'], d) @ qv), c['id']) for c in q['cands']), reverse=True, ) hit = 1.0 if gold[q['id']] in [i for _, i in scored[:k]] else 0.0 per_slice.setdefault(q['slice'], []).append(hit) out[d] = {s: round(sum(v) / len(v), 4) for s, v in per_slice.items()} return out

真实场景

某项目知识库向量占用内存压力大，把 1536 维截到 512 维以降低存储和查询开销，离线整体 recall@10 看起来变化不大就上线了。上线后用户反馈「搜不到具体型号」的工单增加，典型现象是：通用问题命中正常，含型号、参数编号和长尾类目的 query 命中明显变差，拒答率也异常升高。排查路径是：先按切片拆指标发现长尾类目下降，再用 flat 暴力检索确认不是 HNSW 参数问题，最后定位到截断后未重新归一化、阈值沿用旧值，且模型前缀可截断性在长尾语义上损失较大；回退到全维做重排、并只对高频类目使用低维集合后恢复。

flowchart TD
    A[全维向量基线] --> B[确认模型是否支持前缀截断]
    B --> C[按类目与含编号 query 分片评估]
    C --> D[截断后重新归一化与阈值重标定]
    D --> E[影子集合双写灰度]
    E --> F[长尾损失超阈值则回退全维]

面试官追问

Q：降维和量化应该先做哪个？

A：通常先降维再量化，两者误差来源不同，顺序会影响叠加效果，必须用同一套分片评估集实测组合后的 recall 和延迟。若只能选一个，优先看损失落在哪些切片：量化更均匀地影响所有 query，截断对长尾语义更敏感。无论哪种，都要保留全维向量用于重排和回退。

Q：怎么证明召回下降是维度造成的，而不是索引参数或数据漂移？

A：做三步对照：一是用 flat 暴力检索在同一批向量上跑，排除 ANN 近似误差；二是两套索引使用完全相同的构建参数和查询参数；三是固定评估集与数据快照，只改变维度变量。如果 flat 下低维仍然掉，且集中在特定切片，就可以归因到维度；如果 flat 不掉而 ANN 掉，则问题在图结构和参数上。

09上游 camelCase、内部 snake_case：Pydantic v2 的 alias 在入参、出参与缓存写回三处不一致，字段悄悄丢失怎么收口

进阶 ｜ Pydantic v2alias序列化契约一致性

为什么会有这个问题

FastAPI 用同一套 Pydantic 模型做请求校验、OpenAPI 文档和响应序列化，但 alias 在不同路径上的默认行为并不一致：response_model 默认按 alias 输出，而业务代码里直接调用 model_dump() 默认不按 alias 输出。如果缓存、消息队列、下游服务也复用这个模型，就会出现 HTTP 响应正常、异步链路字段丢失的分裂现象。常见错误认知是“加了 alias_generator 就全局生效”，忽略了序列化调用点和回读校验配置。

怎么做

  1. 先划清边界：API DTO 和消息 DTO 使用 alias，领域模型、ORM 模型不继承 alias 配置，避免传输契约污染内部字段访问。
  2. 把出站序列化收口到一个函数，显式使用 model_dump(by_alias=True, mode="json", exclude_none=True)，缓存、MQ、审计日志统一走它。
  3. 入站回读时要么统一按 alias 校验，要么在 DTO 上配置 populate_by_name=True，并补一条“dump 后再 load”的往返契约测试。
  4. 路由层显式声明 response_model_by_alias，保持 OpenAPI 文档、实际响应和缓存写入三处字段名一致；升级期可双写旧字段并观察消费端失败率。
  5. 排查时对比 HTTP 响应体、Redis 写入值、MQ 消息体三处的 key，检查所有 model_dump 调用是否漏传 by_alias，检查消费者 model_validate 是否因字段名不匹配被吞异常。
import json from pydantic import BaseModel, ConfigDict from pydantic.alias_generators import to_camel class WireModel(BaseModel): model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True) class ChatRequest(WireModel): request_id: str user_query: str class CachePayload(WireModel): request_id: str user_query: str def dump_wire(m: BaseModel) -> dict: return m.model_dump(by_alias=True, mode="json", exclude_none=True) def load_wire(data: dict) -> ChatRequest: return ChatRequest.model_validate(data) @app.post("/chat", response_model=ChatRequest, response_model_by_alias=True) async def chat(req: ChatRequest): payload = CachePayload(request_id=req.request_id, user_query=req.user_query) await redis.set(req.request_id, json.dumps(dump_wire(payload))) return req

真实场景

某项目做 LLM 编排服务，前端和网关约定 camelCase，内部代码习惯 snake_case。HTTP 接口返回的 requestId、userQuery 都正常，但上线后缓存反序列化失败率上升，消息消费者报缺少 requestId。排查发现缓存写入处直接调用了 model_dump()，落库是 request_id；消费者按 camelCase 解析后取不到值，而异常又被宽泛的 except 吞掉，只留下空字段。把写入统一到 dump_wire 后恢复，并补了往返契约测试。

面试官追问

Q：为什么不直接给所有模型加 alias_generator，省得每个地方单独转？

A：领域模型和 ORM 模型会被内部代码、数据库映射、任务队列长期复用，alias 会把传输契约泄漏到内部字段访问；上游一改字段名，内部逻辑被迫跟着改。正确做法是只在 API DTO 和消息 DTO 边界定义 alias，并用统一的 dump/load 封装收口。

Q：response_model_by_alias=False 什么时候可以用？

A：内部服务间明确约定 snake_case、且不面向浏览器时可以用；但必须同步 OpenAPI 文档和契约测试，否则网关或前端按文档生成客户端会出现字段不匹配。默认保持 True，特殊路由显式声明并写清原因。

10上传大文件到模型网关，接口内存随并发线性上涨：UploadFile 落盘阈值、流式转发与 413 边界怎么定

资深 ｜ UploadFile流式转发内存反向代理

为什么会有这个问题

UploadFile 底层是 SpooledTemporaryFile，超过阈值会落临时文件，但这只解决了“接收后放哪里”，不等于全链路流式。很多实现会在路由里 await file.read() 整体读入，再作为 bytes 传给 httpx，或者用 Pydantic 的 bytes 字段接收，导致每个并发请求在内存里保留完整文件副本。反向代理的 client_max_body_size 与应用层限制不一致时，413 还可能由代理直接返回 HTML 或重置连接，客户端拿不到可解析错误。

怎么做

  1. 入口做双层限制：反向代理限制粗粒度包体，应用层在分块读取时累计字节数并设置业务上限，超限返回统一 JSON 错误带 request id。
  2. 接收端只用 UploadFile，禁止 await file.read() 一次性读取，也避免用 bytes 字段接收大文件；按固定 chunk 读取并立即转发。
  3. 转发端用 httpx.AsyncClient 的流式请求，把异步生成器作为 content 传给模型网关，设置连接、读、写超时和并发上限，避免上游慢导致 worker 堆积。
  4. 在 finally 中显式 await file.close()，并监控进程 RSS、临时目录文件数、并发上传数、413 比例和上游超时率。
  5. 压测时用不同文件大小和并发梯度验证内存曲线，确认代理层与应用层阈值一致，并检查 chunked 上传场景下 Content-Length 校验是否失效。
from fastapi import FastAPI, UploadFile, HTTPException import httpx CHUNK = 1024 * 1024 MAX_BYTES = 200 * 1024 * 1024 class TooLarge(Exception): pass @app.post("/v1/files") async def upload(file: UploadFile): total = 0 try: async with httpx.AsyncClient(timeout=httpx.Timeout(60.0, read=300.0)) as client: async def body_iter(): nonlocal total while chunk := await file.read(CHUNK): total += len(chunk) if total > MAX_BYTES: raise TooLarge yield chunk try: resp = await client.post( "http://model-gateway/v1/files", content=body_iter(), headers={"content-type": file.content_type or "application/octet-stream"}, ) except TooLarge: raise HTTPException(status_code=413, detail="file too large") if resp.status_code >= 400: raise HTTPException(status_code=502, detail="gateway error") return {"bytes": total} finally: await file.close()

真实场景

某项目做文档解析和模型网关，上传 PDF 到 /v1/files，单文件上限 200MB。并发上传到二十路时，worker 的 RSS 从几百 MB 涨到数 GB 后被 OOM kill；nginx 对超大文件直接返回 413 HTML，前端解析失败。排查发现路由里先 await file.read() 拿到完整 bytes，再传给 httpx，UploadFile 的临时文件优势被抵消；同时代理层 client_max_body_size 与应用层限制不一致。改为分块读取、流式转发并统一 413 JSON 后，内存曲线随并发保持平稳。

    A[客户端上传大文件] --> B[反向代理检查 Content-Length]
    B -->|超限| C[返回 JSON 错误 413]
    B -->|通过| D[FastAPI multipart 解析]
    D -->|失败| E[关闭临时文件并返回 400]
    D --> F[UploadFile 临时文件]
    F --> G[分块读取并累计大小]
    G -->|超限| H[返回 JSON 错误 413]
    G -->|正常| I[httpx 流式转发]
    I --> J[模型网关]
    J --> K[返回结果并清理临时文件]

面试官追问

Q：已经用了 UploadFile，为什么进程内存还会涨？

A：UploadFile 只把超过阈值的部分落临时文件，不代表全链路流式。如果代码里整体读取、把 bytes 传给 httpx、或者 multipart 解析时复制，仍会占内存；并发高时临时文件 I/O 和多个副本也会放大。需要分块读、分块转发，并限制单请求大小和并发数。

Q：413 应该由 nginx 还是 FastAPI 返回？

A：代理层做粗粒度保护，防止大包进入应用；应用层做业务限额并返回统一 JSON 错误。两者阈值要一致并留余量。代理层返回 HTML 413 时，前端需要兼容，或者配置自定义错误页；关键是让客户端拿到可解析的错误和 request id。
