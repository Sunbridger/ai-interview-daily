01MCP Sampling 回调：第三方 Server 反向借用宿主模型时，递归放大、审批与费用归属怎么控

资深 ｜ MCPSampling成本控制权限边界 ｜ 面经来源 ↗

为什么会有这个问题

Sampling 的语义是 Server 通过 Client 请求一次 LLM 补全（createMessage），把模型与密钥留在宿主侧，看起来是安全设计，但它把调用链从 Client→Server 变成了 Client→Server→Client→LLM→Server→Client。工程上因此冒出四个真实问题：其一，递归与放大，Server 在拿到补全结果后可以再次发起 Sampling，宿主若不限制 depth，一次用户请求能膨胀成几十次计费调用；其二，阻塞与死锁，Server 的 handler 通常同步等待回包，而 Client 若把 Sampling 请求排在处理主请求的同一个事件循环或同一把锁后面，就会互相等待直到超时；其三，信任边界倒置，prompt 内容由不受控的 Server 决定，等于让它间接读取并外发上下文，还能影响用哪个模型；其四，费用归属模糊，per-tenant 的 token 配额无法落到具体 Server 上。常见错误认知是把它当成普通 Server→Client notification，以为不需要 request id 关联、超时与去重。

怎么做

  1. 能力协商先行：Client 初始化时声明是否支持 sampling，Server 侧在未声明时必须降级（自带模型或返回明确的 unsupported 错误），禁止假定所有宿主都支持。
  2. 把预算写进协议元数据：Sampling 请求的 _meta 携带 trace_id、session_id、depth、model_hint；Client 维护 per-session 的 depth 上限与 token 预算，超限返回结构化 JSON-RPC error，而不是静默截断或返回空串。
  3. 执行路径隔离：Server handler 用 await 而非阻塞等待；Client 侧为 Sampling 分配独立 worker 与独立 HTTP 连接池，避免与主对话争抢同一连接上限形成排队假死；每个请求注册超时并从 pending map 中清理。
  4. 审批与脱敏策略层：按 Server 来源、prompt 是否含 PII、目标模型单价决定「自动放行 / 需人工确认 / 拒绝」，全量落审计日志（谁触发的 Sampling、发了什么、消耗多少）。
  5. 模型选择权留在宿主：Server 只能给 maxTokens、temperature 之类的建议值，真实模型由 Client 按租户策略决定并做单价封顶。
  6. 计量与熔断：把消耗记到「调用方 Server」维度，做 per-server 配额与失败率熔断；request id 幂等去重，重试沿用同一 id 且次数封顶。
  7. 失败语义要可区分：超预算、需审批、超时（可重试）、被拒绝（不可重试）用不同错误码，让 Server 能正确降级而不是基于空结果继续幻觉推理。
import asyncio class SamplingGate: def __init__(self, llm, default_model, max_depth=2, token_budget=20000, timeout=20): self.llm, self.default_model = llm, default_model self.max_depth, self.token_budget, self.timeout = max_depth, token_budget, timeout self.used, self.seen = {}, set() async def handle(self, req): rid = req["id"] if rid in self.seen: return {"error": {"code": -32000, "message": "duplicate sampling id"}} params = req.get("params", {}) meta = params.get("_meta", {}) depth = meta.get("depth", 0) session = meta.get("session_id", "anon") if depth >= self.max_depth: return {"error": {"code": -32001, "message": "sampling depth exceeded"}} used = self.used.get(session, 0) if used >= self.token_budget: return {"error": {"code": -32002, "message": "sampling budget exhausted"}} self.seen.add(rid) try: resp = await asyncio.wait_for( self.llm.create_message( messages=params["messages"], max_tokens=min(params.get("maxTokens", 512), 1024), model=meta.get("model_hint") or self.default_model, ), timeout=self.timeout, ) except asyncio.TimeoutError: return {"error": {"code": -32003, "message": "sampling timeout", "data": {"retryable": True}}} self.used[session] = used + resp.usage.total_tokens return {"result": {"role": "assistant", "content": resp.text, "_meta": {"depth": depth + 1, "session_id": session}}}

真实场景

某项目接入一个第三方 MCP Server 做长文档摘要，上线后出现两个症状：账单消耗是一次普通请求的十几倍；高峰期 Server 侧出现大量 pending 调用，最终统一超时。排查路径：先在宿主侧按 trace_id 聚合 sampling 请求，发现同一 trace 下 depth 单调递增且没有上限，Server 在补全结果不满意时会再发起一次 Sampling 自我修订，形成放大；再看事件循环与连接池指标，Sampling 处理函数与主对话共用同一个 httpx client（连接上限配置得很小），主请求持有连接等待 Server 回包，Server 又在等宿主回 Sampling，互相等待。修复：depth 限制为 2、按会话设 token 预算、Sampling 走独立 worker 与独立连接池、超时 20s 并把可重试语义回传给 Server；同时把消耗按 Server 维度记账，异常 Server 直接熔断。

面试官追问

Q：为什么不干脆让 Server 自带模型 key，绕过 Sampling？

A：那就把密钥分发、成本与合规责任都推给了不受控的第三方：多租户无法统一审计，模型升级和降价也享受不到。Sampling 的核心价值就是模型与密钥留在宿主侧，代价是链路变长、递归风险内生化，所以真正的工程动作是在宿主侧做深度、预算、审批与计量四道闸门，而不是取消这个能力。

Q：Sampling 被拒绝时应该返回空内容还是错误？

A：必须返回结构化错误码并区分可重试与不可重试。返回空串或占位文本会让 Server 误以为拿到了有效补全并继续推理，最终把幻觉结果当成工具输出写回业务；错误码则让设计良好的 Server 走「降级到本地规则」或「终止并上报」两条确定路径。

02从可视化编排平台迁回代码：Agent 工作流的版本化、幂等语义与逃生舱怎么设计

资深 ｜ 工作流编排平台选型可观测发布治理 ｜ 面经来源 ↗

为什么会有这个问题

低代码编排平台（Dify、Coze、n8n 这类）在验证期最快，但进入生产后矛盾集中在四处：流程定义只存在于画布与平台数据库，进不了 Git review，改一个分支靠手点、没人能 review diff；没有单测与本地复现能力，故障只能在生产画布上试；平台的重试与循环语义是黑盒，经常和业务幂等冲突（一个「失败重试」把工单建了两遍）；trace 停在平台 UI，无法与自有 APM 的 trace_id 串起来。常见错误认知是把选型当成功能对比表打分，而真实约束是变更频率、参与角色、合规要求与退出成本——尤其是退出成本，选型时几乎没人量化「半年后想搬走要付多少」。

怎么做

  1. 做工作负载画像再决策：按「调用量 × 变更频率 × 失败后果」把流程分桶。高频稳定、失败后果重的走代码；低频多变、由运营自己改 prompt 的留在平台，不做一刀切。
  2. 抽象自有中间表示：定义 FlowSpec（节点类型、边与条件、幂等键、超时、重试上限）作为唯一事实来源，平台与代码 runtime 都只是它的执行器 adapter，避免锁定在某个 DSL 上。
  3. 流程定义入库并纳入 CI：FlowSpec 进 Git，CI 做 schema 校验 + 录制回放测试（固定输入、mock 工具，断言节点级输出），发布按 version 灰度分流。
  4. 对齐幂等与重试语义：每个写节点显式声明幂等键，重试上限与超时在 FlowSpec 里唯一声明，平台侧配置不得覆盖为默认无限重试。
  5. 打通可观测：adapter 统一注入 trace_id 并上报到自有 OTel collector，节点级 span 带上 flow name、version、node id，实现平台与自有服务同一条 trace。
  6. 保留逃生舱：同一份 FlowSpec 必须有代码 runtime 可执行，并定期对关键流程做双跑对账（写路径影子执行），差异率达标后才允许切流。

真实场景

某项目早期用可视化平台搭了二十多条客服与运营流程，半年后同时暴露三个症状：改一个分支要在画布上点几十分钟，且变更没有任何 review 记录，出问题无法回溯「上周谁改了什么」；线上一个循环节点因平台默认重试把同一张工单重复创建，客服侧出现重复回访；排查失败只能看平台 UI 的精简日志，无法和自家服务的 trace 关联。处理方式：先定义 FlowSpec 并把三条高频核心流程迁到代码 runtime，写节点加幂等键、重试上限显式声明；其余流程保留在平台但通过 adapter 统一上报 trace 与版本号；对两条写入类流程做两周影子双跑对账，节点级输出差异率收敛后切流，并把老画布标记为只读。

面试官追问

Q：双跑对账怎么避免成本和副作用翻倍？

A：写路径一律影子执行：工具调用走 mock 或只记录不落库，只对读取与决策路径真实双跑，并按采样率降频。对账比较的是节点级结构化输出差异率（分支走向、字段值），而不是最终自然语言答案文本是否一致，否则噪声会淹没真实回归。

Q：什么情况下应该继续留在平台，而不是迁走？

A：参与方是非工程角色、业务方需要自己高频改 prompt 与分支、流量低且失败可人工兜底，这几种情况自研 runtime 的维护成本高于锁定成本。判断标准是「变更频率 × 变更者是否是工程师」，而不是平台能力清单有多长。

03用户点了停止，Agent 还在花钱：SSE 断连后的取消传播、不可中断工具与副作用收敛

资深 ｜ asyncio取消传播幂等成本控制 ｜ 面经来源 ↗

为什么会有这个问题

Agent 的一次 run 往往挂在 HTTP 请求的协程上，通过 SSE 流式返回。常见的错误认知有三个：一是认为「客户端断开就等于任务结束」，但在流式生成器里不主动检测断连时，服务端协程会继续 await LLM 和工具；二是认为 asyncio.CancelledError 一定能传到工具层，实际上 run_in_executor 包住的同步 SDK、自定义的 except BaseException 重试、以及在 finally 里再次 await 被取消的清理逻辑，都会让取消停在半路；三是把「取消」当成「回滚」，可写类工具一旦提交就无法撤销，此时取消只能阻止后续步骤，已经产生的副作用必须靠幂等键和对账收敛。进一步说，网络抖动引起的断连与用户主动停止混为一谈，会导致正常任务被误杀；而 run 结束后如果计费、配额释放、事件落库不走同一条 finalize 路径，取消路径就会成为资源泄漏和账单对不上账的主要来源。

怎么做

  1. 把一次 Agent 执行抽象成带 run_id 的后台任务，由 RunManager 持有，SSE 只是订阅者。区分两种终止语义：用户显式 stop 触发 cancel；传输层断连只进入 N 秒 grace 窗口，期间允许携带 Last-Event-ID 重订阅，超时才取消。
  2. 在执行循环的每个 await 点设置取消检查点（LLM 调用前、工具调用前、每次状态写回后），并让整个 run 带 wall-clock 预算和 token 预算，超时与取消走同一个收敛出口。
  3. 把工具按副作用语义分两类：只读工具允许被中断；提交类工具（创建工单、发消息、扣款）先用 asyncio.shield 保护到底，再通过「intent 记录 + 幂等键（run_id:step_id）」保证最多一次生效。
  4. 发起提交类工具前先写 pending intent，成功后置 done；取消或超时后由后台对账任务扫描超时 pending，以工具侧的查询结果为准补写终态，绝不靠猜测。
  5. 所有终止路径（正常结束、取消、超时、异常）统一走 finalize：写 usage、释放并发信号量、上报 metrics、发送 run 结束事件。finalize 本身也要 shield + suppress，避免清理阶段被二次取消。
  6. 用混沌测试验收：在随机 await 点注入 cancel，断言没有泄漏的 Task、没有重复的业务副作用、计费条数与 run 数一一对应。
import asyncio, contextlib class RunManager: def __init__(self, repo, agent, budget_s=180): self.repo, self.agent, self.budget_s = repo, agent, budget_s self.tasks: dict[str, asyncio.Task] = {} def start(self, run_id, user_id, goal): t = asyncio.create_task(self._run(run_id, user_id, goal), name=f"run:{run_id}") self.tasks[run_id] = t t.add_done_callback(lambda _: self.tasks.pop(run_id, None)) return t async def _run(self, run_id, user_id, goal): try: async with asyncio.timeout(self.budget_s): await self.agent.loop(run_id, user_id, goal) except asyncio.CancelledError: await asyncio.shield(self.repo.mark_cancelled(run_id)) raise finally: with contextlib.suppress(Exception): await asyncio.shield(self.finalize(run_id)) async def stop(self, run_id, grace=2.0): task = self.tasks.get(run_id) if not task: return task.cancel() await asyncio.wait({task}, timeout=grace) async def call_writer_tool(repo, run_id, step_id, tool, args): key = f"{run_id}:{step_id}" await repo.upsert_intent(key, "pending") res = await asyncio.shield(tool(**args)) await repo.upsert_intent(key, "done") return res

真实场景

某项目的客服 Agent 上线后，用户点击「停止」后仍有工单被创建，并且后台又追加了两次 LLM 调用。典型症状是：SSE 断连日志与 run 结束日志之间存在数十秒错位，前端显示的会话数明显少于实际计费条数，某个租户的 token 消耗异常偏高。排查路径是：先比对断连时间与 finalize 时间定位生命周期错位；再查 intent 表中 pending 堆积，确认提交类工具在取消后继续执行；最后定位到一个 retry 装饰器用 except BaseException 吞掉了 CancelledError，导致取消在工具层失效，run 继续按原计划推进。修复后，把「断连不等于取消」和「finalize 单出口」两条写成 RunManager 的硬约束，并补充了注入式取消的混沌用例。

面试官追问

Q：为什么不让断连直接等价于取消？

A：移动网络切换、SSE 自动重连、代理超时都会造成假断连，直接取消会造成大量无辜失败和用户看到「回答到一半没了」。正确做法是断连只标记 detached，进入 grace 窗口并缓冲事件，重连后按 run_id/Last-Event-ID 续传；只有显式 stop、超过 grace 或超出预算才真正 cancel。代价是要维护事件缓冲与状态，需要设置硬上限防止缓冲区无限增长。

Q：取消之后怎么保证不会重复建单或重复计费？

A：两点：语义上承认取消只阻止「继续发起」，不能回滚「已提交」；机制上用 run_id:step_id 作为幂等键，提交前写 pending intent，最终以工具侧查询结果作为真实状态写回 done，后台对账任务扫描超时 pending 收敛。计费走 finalize 单出口，按实际发生的 token 与工具调用记账，并给 run 加唯一结算标识防止重复入账。

04Prompt 改一行就上线：Agent 回归门禁、eval 过拟合与金丝雀放量怎么定

进阶 ｜ eval回归门禁LLM-as-judge金丝雀

为什么会有这个问题

Agent 的输出是一条轨迹，而不是单个答案，同一句 prompt 变化可能影响工具选择顺序、步数、成本和安全性，单测和人工试用都覆盖不到。工程上常见的三个错误认知是：只比较最终答案相似度，忽略工具调用序列、冗余步数与 P95 成本；用同一批手写 case 反复调 prompt，把这批样本调成过拟合，离线全绿线上照样翻车；把 LLM-as-judge 的绝对打分当作真值，而 judge 存在位置偏置、长度偏置和自我偏好，与被测模型同源时分数系统性地虚高。更深一层的问题是分布不一致：手写 case 集中在主路径，线上长尾意图（查订单、催发货、投诉）样本极少，一旦某个桶退化，整体指标会被主路径的增长掩盖。

怎么做

  1. 定义分层指标：可规则判定的任务成功（结构化字段正确、工具返回被正确引用）、轨迹指标（首步工具选择准确率、冗余步数、无效重试次数）、成本与延迟分位、安全红线（越权工具调用、敏感信息外泄）。能用断言判定的绝不用 judge。
  2. 治理数据集：从线上采样脱敏后按意图分桶，每桶样本量设下限；划分固定的 holdout 集合，只在发版前跑，禁止用于调 prompt，并按季度轮换，避免长期记忆化。
  3. 校准 judge：改绝对打分为匿名成对比较并随机左右顺序；judge prompt 与 rubric 版本化；用人工标注子集算一致率，低于阈值时 judge 结果只能作为参考，不能作为门禁依据。
  4. 做门禁时用区间而非点估计：小样本成功率用 Wilson 置信区间判断「是否显著下降」，设置硬红线（任何越权调用即阻断）与软阈值（分桶成功率下降超过容差则阻断，成本上涨超阈值仅告警）。
  5. 节省成本：只跑受影响的子集（工具 schema 未变则跳过工具相关 case），全量 eval 放 nightly；用缓存固定住检索与工具返回，保证对比时只变被测变量。
  6. 发布节奏：影子流量回放对比，再按百分之一金丝雀放量，按意图分桶看线上指标是否与离线一致，不一致自动回滚 prompt 版本（用 feature flag 控制版本切换，而不是重新发版）。

面试官追问

Q：为什么不能直接用同一个 LLM 打分来做门禁？

A：judge 有位置、长度和自我偏好，同源模型打分还会系统性偏高，分数变化未必对应真实质量变化。可行做法是成对比较加随机左右顺序、rubric 版本化、用人工标注子集校准一致率；关键路径尽量换成可执行断言，例如工具序列、JSON schema 校验、必填字段比对，把主观判断压缩到最小范围。

Q：怎么避免 eval 集被调成过拟合？

A：三层措施：固定 holdout 集只用于发版判定、禁止用于调 prompt；按意图分桶并定期从线上采样轮换，让分布跟着真实流量走；把目标从「这批 case 全过」改成「分布指标不退化 + 硬红线不触碰」，同时把每次线上回归事故的样本反哺进对应桶，形成闭环。

05答案引用了片段但结论是模型自己编的：claim 级支撑校验与冲突证据处理怎么落地

资深 ｜ faithfulnesscitationeval ｜ 文档来源 ↗

为什么会有这个问题

很多 RAG 系统要求模型给片段编号来提升可信度，但模型常见行为是先给结论再补引用，或只让引用覆盖部分 claim；相似度检索还会把相关但不等价的片段混入上下文，例如旧版本、不同条件、不同权限来源。只看答案级相似度或整体 faithfulness 分数，会被正确 claim 稀释，无法定位哪一句没有证据，也无法处理上下文互相矛盾。工程上需要把忠实度拆成 claim 级支撑关系，并把冲突证据当作显式状态处理。

怎么做

  1. 生成阶段要求模型输出结构化 claims、evidence_ids 和条件限定；无证据 claim 标记 unsupported，prompt 明确禁止使用片段外事实，遇到冲突要列出冲突而不是强行合成。
  2. 校验阶段逐 claim 做支撑判定：数字、日期、版本号先用正则抽取做规则一致性校验，再用 NLI 小模型或 LLM judge 判定 entailed、contradicted、neutral；claim 与证据原文拼接，不能用摘要替代原文。
  3. 冲突处理按文档版本、生效时间、来源权威度和权限过滤排序；检测到矛盾证据时降级为澄清问题或多版本并列展示，不直接给单一结论。
  4. 建立 claim_support_rate、citation_precision、citation_recall、冲突率等指标，并按 query 类型分桶，避免整体分数掩盖局部失败。
  5. 门禁策略：低于阈值触发只基于证据重写或拒答；灰度上线并记录失败 claim 与证据对，回流到 eval set 做回归。
  6. 对 judge 做成本分层：规则优先，小模型处理多数 claim，低置信度再走大模型；缓存 claim 加证据对的判定结果，并定期抽样人工校准阈值。
def verify_claims(answer, evidences): claims = answer['claims'] results = [] for c in claims: ids = c.get('evidence_ids', []) if not ids: results.append((c['text'], 'unsupported', None)) continue cands = [evidences[i] for i in ids if i in evidences] best = max(cands, key=lambda e: nli_score(c['text'], e['text'])) label = 'entailed' if nli_score(c['text'], best['text']) > 0.7 else 'not_entailed' if has_number_conflict(c['text'], best['text']): label = 'contradicted' results.append((c['text'], label, best['doc_id'])) support_rate = sum(r[1] == 'entailed' for r in results) / max(len(results), 1) return results, support_rate def answer_with_guard(answer, evidences, threshold=0.8): results, rate = verify_claims(answer, evidences) if rate < threshold: return {'action': 'retry_or_abstain', 'details': results} if any(r[1] == 'contradicted' for r in results): return {'action': 'ask_clarify_or_show_versions', 'details': results} return {'action': 'answer', 'details': results}

真实场景

某项目客服知识库同时存在旧版和新版退款政策。用户问未发货退款多久到账，top-k 同时召回新旧条款。上线后人工抽检发现答案引用了新版条款编号，但结论写成旧版的到账时间；整体 faithfulness 分数并不低，因为上下文里确实有旧版时间。按 claim 拆解后，发现数值 claim 的 evidence 指向旧片段，citation_precision 低且冲突率上升。修复方式是引入 claim 级校验、版本过滤和冲突降级，并把失败样本回流到回归集。

B --> C{是否有引用}
C -- 否 --> D[标记 unsupported]
C -- 是 --> E[规则校验数字日期版本]

面试官追问

Q：为什么不能只用整体 faithfulness 分数做门禁？

A：整体分数是答案级聚合，部分 claim 无支撑会被其他正确 claim 稀释；judge 对长答案还有位置偏置。claim 级校验能定位具体证据和失败类型，便于重试、拒答和样本回流。

Q：NLI 或 LLM judge 本身不稳定，怎么控成本和误判？

A：分层处理：规则先校验数字日期版本，小模型处理多数 claim，低置信度再走大模型；缓存 claim 加证据对；固定 judge prompt 要求输出标签和理由；定期抽样人工校准阈值。

06语义分块上线后召回提升但每次小改都像全量重建：边界漂移、稳定块 ID 与父子块成本怎么一起控

进阶 ｜ chunkingindex-updatecost ｜ 文档来源 ↗

为什么会有这个问题

Semantic Chunking 按句子 embedding 相似度或主题漂移切边界，能减少一句话被切断，但边界依赖阈值、模型版本和全文上下文。文档小改一段可能导致后续边界整体移动，如果 chunk_id 用序号，差集删除会失效，增量更新变成大量删除加插入，出现重复块、旧块残留和索引膨胀。同时块数长尾会推高向量存储和 rerank 成本，所以不能只看召回提升。

怎么做

  1. 离线评估固定窗口、语义分块、父子块三种方案：比较 recall@k、答案正确率、平均块数、块长 P95，并把成本折算为向量条数乘单价加 rerank token。
  2. 稳定化：以段落、标题等结构边界作为硬边界，语义分块只在段内做；设置最小和最大块长；对边界打分做平滑，避免单句抖动。
  3. 稳定 ID：chunk_id 用 doc_id 加规范化文本 hash 加结构路径，而不是序号；父块保留稳定 doc 级 ID，便于小块检索大块生成。
  4. 更新路径：段内小改只重切该段，用内容 hash 做差集删除和插入；分块器或 embedding 模型变更才走影子索引全量重建。
  5. 新旧索引双读一段时间，按 chunker_version 过滤，验证无重复、无缺失后切流；失败则保留旧索引回滚。
  6. 监控 chunks_per_doc、平均块长、重复率、孤立块率和更新耗时，把分块版本纳入 eval 回归。
import hashlib, re def norm(text): return ' '.join(text.strip().lower().split()) def chunk_id(doc_id, section_path, text): h = hashlib.sha1(norm(text).encode('utf-8')).hexdigest()[:16] return f'{doc_id}:{section_path}:{h}' def diff_update(old_chunks, new_chunks): old_ids = {c['id'] for c in old_chunks} new_ids = {c['id'] for c in new_chunks} to_delete = old_ids - new_ids to_insert = [c for c in new_chunks if c['id'] not in old_ids] return to_delete, to_insert def split_in_section(text, max_len=800, min_len=120): sentences = re.split(r'(?<=[。！？.!?])', text) chunks, buf = [], '' for s in sentences: if len(buf) + len(s) > max_len and len(buf) >= min_len: chunks.append(buf) buf = s else: buf += s if buf: chunks.append(buf) return chunks

某项目把固定长度分块换成全文语义分块后，召回指标有提升，但文档每次小改都会触发大面积重建；索引条数明显上涨，rerank 延迟变高，还出现同一段落两个版本同时被召回。排查发现语义边界随全文 embedding 变化，chunk_id 用序号导致差集删除失效。修复为结构硬边界加段内语义切分、内容 hash 稳定 ID、局部差集更新，大变更才走影子索引重建。

面试官追问

Q：语义分块和固定分块的本质区别是什么？现在更常见的实践是什么？

A：固定分块按长度切，边界稳定但可能切断语义；语义分块按相似度或主题漂移切，召回可能更好但边界不稳定、成本更高。实践中更多采用结构感知加段内语义切分加父子块，而不是全文档自由语义切分，并把 chunker 版本化后纳入评估。

Q：小文档频繁更新，是否应该每次重建？

A：按变更范围决定：段内小改用稳定 ID 做差集局部替换；分块器、模板或 embedding 模型变更才重建。重建走影子索引和双读验证，避免线上混版。

07chunk 正文跟着向量一起 upsert，partial update 撞上消息体上限后静默丢字段：写入契约怎么定

资深 ｜ 写入路径数据建模幂等重放可观测性 ｜ issue来源 ↗

为什么会有这个问题

很多团队把 chunk 正文（几百到几千字）、元数据和向量塞进向量库的同一行，图省事少一次查询。但写入路径上不同操作的载荷形态并不一致：批量 insert 走打包序列化，partial update 走逐条变更消息，要受消息队列或 RPC 的单条体积上限约束；而且 partial update 的语义是「只覆盖给出的字段」，没给的字段保持原值还是被置空，取决于实现。常见错误认知有三个：以为 upsert 能覆盖一切场景；以为 partial update 更省带宽所以更安全；以为写入接口返回成功就代表数据可用——实际上向量库多为异步写入，真正的拒绝错误出现在服务端日志或 flush/compaction 阶段。最终症状是：向量还在、能召回，但正文是空或旧版本，模型拿不到证据，答成「没有相关信息」或自行编造。问题本质是把「检索必需的字段」和「展示、校验用的正文」混在同一存储里，导致写入路径被大字段绑架。

怎么做

  1. 重定写入契约：向量库只保存 id、vector 和少量可过滤标量（tenant、doc_id、version、lang、时间戳、deleted），正文与标题放到 KV、对象存储或搜索引擎，用 chunk_id 关联，检索命中后批量取回正文再做拼装。
  2. 改更新语义：内容变更不做「对已有行的半覆盖」，而是生成新 chunk_id 或递增 version 写新行，旧行先打 deleted 标记，再由离线任务按标记清理，避免 partial update 直接改大字段。
  3. 加体积守卫：写入前序列化估算字节数，超过阈值（例如 MQ 单条上限的 60%）就拒绝走默认路径，降级为只更新正文侧或按段落拆分，绝不让请求静默失败。
  4. 把幂等和重放设计进去：每批写携带 batch_id 和 version，失败落到 outbox 表，重放时按 (chunk_id, version) 去重，保证重复消费不会产生双份召回。
  5. 写入后要做读回校验：抽样按 chunk_id 读回，比对正文哈希和 version；同时统计空正文行的占比、写入失败率（按操作类型分）、从写入到可检索的延迟，把「写成功但不可用」变成可观测指标。
  6. 给检索侧加防御：拼上下文前校验取回的正文非空且 version 与命中行一致，不一致就丢弃该证据并记录垃圾行计数，宁可少召回也不要拿错版本回答。
MAX_PAYLOAD = 900_000 # 略低于 MQ 单条上限 def build_record(c, vec): # 向量库只放检索必需字段，正文不进向量库 return {"id": c.chunk_id, "vector": vec, "doc_id": c.doc_id, "version": c.version, "tenant": c.tenant, "deleted": False} def write_chunks(chunks, vecs, store, kv, outbox): for c, v in zip(chunks, vecs): rec = build_record(c, v) if len(json.dumps(rec).encode()) > MAX_PAYLOAD: outbox.put("kv_only", c) continue try: kv.put(c.chunk_id, {"text": c.text, "hash": c.hash, "version": c.version}) store.upsert([rec]) if c.prev_chunk_id: store.update(c.prev_chunk_id, {"deleted": True}) # 打标，异步清理 except Exception as e: outbox.put("retry", {"id": c.chunk_id, "ver": c.version, "err": str(e)}) def read_context(hits, kv): ids = [h.id for h in hits if not h.deleted] fetched = kv.mget(ids) # 只取 top-k 的正文，批量一次 RTT return [p["text"] for h, p in zip(hits, fetched) if p and p["version"] == h.version]

面试官追问

Q：为什么不把正文压缩一下继续放在向量库里？

A：压缩只是把上限往后推，而且解压占 CPU、正文无法用于过滤和高亮，元数据过滤、引用定位这些需求也做不了。真正的解法是按用途分离：向量库存检索所需的索引数据，正文库存展示与校验所需的内容，顺带还能做取回时的权限二次校验。

Q：正文拆出去多了一次 RTT，怎么保证检索延迟不退化？

A：只对 top-k 的 chunk 做批量 MGET，不逐条取；KV 与向量库同机房部署，并在应用侧加一层按 chunk_id 的 LRU；把这一步计入检索预算，超时则降级为只返回引用而不展开全文。多几毫秒换来写入路径稳定是划算的。

08让 LLM 自己选检索分支后长尾 query 走错路：路由置信度、并行回退与成本怎么定

进阶 ｜ query路由检索策略回退设计成本评估 ｜ 面经来源 ↗

为什么会有这个问题

知识库往往混合了多种数据：FAQ 短文本、工单和指标类的结构化表、长文档。团队自然想让模型在「向量检索、SQL 查询、关键词检索、直接回答」中选一个分支。问题在于：① 分类器只看 query 文本，看不到库里到底有没有这类数据，无法判断「问了但知识库没有」；② 单一分支、没有回退，判错一次整条链路就白跑，且错误不会暴露成异常，只会变成「答非所问」；③ 模型对措辞很敏感，口语化、多意图、带数字和单位的 query 判错率明显偏高；④ 每次路由多一次模型调用，延迟和 token 成本直接叠加在首字延迟上。常见错误认知是「把路由 prompt 写得更详细就能稳」，实际上 prompt 只能提升先验，真正需要的是可验证的判定加兜底并行。

怎么做

  1. 规则前置：先用正则、字段名、单位、时间词、编号格式吃掉高确定性的 query（含订单号、指标名、「环比、占比、平均」这类词直接进结构化分支），只有规则判不出来的才交给模型。
  2. 让路由输出结构化且带置信度和多标签：要求返回 routes 列表、confidence 和简短 reason，不要让它只吐一个单词；置信度低于阈值时不作单选。
  3. 低置信度改并行：路由结果不确定时并行两路（例如结构化检索加向量检索），各自设更小的 top-k 和更短的超时，用融合或优先级合并，避免单点判错导致 0 召回。
  4. 定义各分支的可验证成功条件：结构化分支要校验 SQL 执行成功、字段在 schema 内、返回行数大于 0；向量分支用 top1 相似度阈值加 answerability 判定。任何一路满足即视为可回答，全不满足才降级为拒答或转人工。
  5. 建立分层评估集：按查询类型（FAQ、指标、多跳、无答案）分别统计路由准确率、端到端正确率、平均分支数、p95 延迟与 token 成本；上线前用 shadow 方式记录「如果走另一条分支会得到什么」，定位是路由错还是分支本身弱。
  6. 监控路由分布漂移：各分支占比、低置信度占比、并行触发率、单分支空结果率。分布突变通常意味着文档口径变化或 schema 变更，而不是模型突然变差。
  7. 缓存路由决策：query 归一化后缓存 routes，key 必须带上 ACL scope 与索引或数据版本号，权限或数据版本变化时按 scope 失效，避免缓存把结果带偏。
RULES = [(r"(工单|订单|GMV|占比|环比|平均)", "sql"), (r"(怎么申请|办理流程|需要哪些材料)", "vector")] def route(query, llm): for pat, name in RULES: if re.search(pat, query): return {"routes": [name], "conf": 0.9, "mode": "rule"} out = llm.structured(ROUTER_PROMPT, schema={"routes": "list[str]", "confidence": "float"}, query=query) if out["confidence"] < 0.6 or len(out["routes"]) != 1: picks = out["routes"][:2] or ["vector", "sql"] return {"routes": picks, "conf": out["confidence"], "mode": "parallel"} return {"routes": out["routes"], "conf": out["confidence"], "mode": "single"} def retrieve(query, plan, branches, budget): for name in plan["routes"]: b = branches[name] r = b.search(query, top_k=budget.k(plan["mode"]), timeout=budget.t(plan["mode"])) if r and r.top_score >= b.min_score: return r # 任一路可验证成功即可回答 return None # 全部失败才走拒答/转人工

真实场景

某项目做客服 Copilot，知识库既有制度文档也有工单指标表。症状：问「上个月这类工单的平均处理时长」时，答案里的数字对不上，日志显示 query 像自然语言被路由到向量检索，而向量库里只有文档、没有指标表，于是返回几段相似制度文档，模型据此编了数值；同时首字延迟 p95 上升，因为每条 query 都多了一次小模型调用。排查路径：抽样一批错例按路由分支分组 -> 发现含「平均、多少、占比」的指标类 query 大量被判成 vector -> 补规则前置并把低置信度改为并行两路 -> 指标类正确率回升，而成本只在少数低置信度 query 上多花一次检索。

面试官追问

Q：并行多路会放大成本，你怎么权衡？

A：只在低置信度区间并行，这一区间占比通常不高；并行分支强制更小的 top-k 和更短超时，把额外成本锁在上界。比较对象是「多花一次检索」与「答错一次导致转人工或投诉」的代价，后者通常更贵；如果预算紧，可以先只保留规则加单分支，把并行作为兜底开关。

Q：路由缓存怎么防止权限或数据版本变化后带出错误结果？

A：缓存 key 里加入 query 归一化文本、用户可见的 ACL scope 和索引或数据版本号，任一变化都会自然换 key；同时对缓存命中率按 scope 拆分监控，避免某个 scope 命中率异常高说明 key 设计漏了维度。

09进程内 Semaphore 控上游并发，扩到 4 个 worker 后 429 与账单一起翻倍：全局闸门该放哪一层

资深 ｜ 并发控制多进程部署成本治理限流

为什么会有这个问题

很多人把 asyncio.Semaphore(20) 当成全局并发上限，但 uvicorn --workers 4 和 gunicorn 多 worker 是彻底独立的进程，内存、信号量、计数器都不共享，真实并发是 4×20；如果跑在 K8s 上再乘副本数，滚动发布时新旧 Pod 并存还会瞬时翻倍。上游按 API key 限流，于是表现为：单机压测完全正常，一上线就 429 飙升，重试进一步放大调用量与费用。更隐蔽的是每个进程自己的 in-flight 指标都只有 20，监控上看不出超限，排查方向容易被带到上游或网络。另一种常见错误是用 threading.Semaphore 或全局 dict 计数，前者只跨线程不跨进程，后者在 fork 后各写各的，同样失真。

怎么做

  1. 先确认闸门目标：要保护的是上游配额，key 必须是配额主体（API key / tenant / model），而不是进程或 Pod。
  2. 量化失真：启动日志打 pid 与 worker 序号，把 in-flight、等待时长按实例聚合后再求和，对比上游返回的 429 与配额用量。
  3. 用 Redis 做租约式信号量：ZSET 存 token + 过期时间，acquire 时先按 score 清理过期租约再判断基数，release 时 ZREM；进程崩溃靠租约过期自动回收，长请求用心跳续期。
  4. 保留本地 Semaphore 作为每进程保险丝，值取全局额度除以最大进程数再留余量，防止 Redis 抖动时完全失去保护。
  5. 排队策略要有界：等待 2~3 次即可快速失败，返回 429/503 加 Retry-After，不要让请求在应用层无限排队占住连接与内存。
  6. 重试要有预算：最多一次、指数退避加 jitter，且重试同样过闸门；对计费类调用加幂等键去重。
  7. 流式与长连接单独计量：SSE 只在首 token 前占上游并发名额，之后按活跃 stream 数单独限，避免长连接把名额长期占死。
  8. 观测闭环：全局 in-flight、闸门等待 P99、429 率、每 key 单位时间消耗，任一越阈值告警。
import asyncio, time, uuid import redis.asyncio as redis ACQUIRE_LUA = """ local k = KEYS[1] local now = tonumber(ARGV[1]) local ttl = tonumber(ARGV[2]) local limit = tonumber(ARGV[3]) local id = ARGV[4] redis.call('ZREMRANGEBYSCORE', k, '-inf', now) if redis.call('ZCARD', k) >= limit then return 0 end redis.call('ZADD', k, now + ttl, id) redis.call('PEXPIRE', k, ttl * 2) return 1 """ class Busy(Exception): pass class RedisGate: def __init__(self, r, key, limit, ttl_ms=30_000): self.r, self.key, self.limit, self.ttl = r, key, limit, ttl_ms self.token = '' async def __aenter__(self): self.token = uuid.uuid4().hex for _ in range(3): ok = await self.r.eval(ACQUIRE_LUA, 1, self.key, int(time.time() * 1000), self.ttl, self.limit, self.token) if ok: return self await asyncio.sleep(0.05) raise Busy(f'gate {self.key} full') async def __aexit__(self, *exc): await self.r.zrem(self.key, self.token)

真实场景

某项目的模型网关用单 worker 开发，lifespan 里建 asyncio.Semaphore(20) 包住上游调用，压测时上游并发稳定在 20，一切正常。改成 uvicorn --workers 4 后，白天高峰上游 429 从偶发变成持续，重试把调用量又抬高，费用曲线同步上扬；但看应用指标，每个进程 in-flight 都没超过 20，值班同学先怀疑上游容量，直到把四个进程的 in-flight 相加才看到真实并发长期在 60 以上。滚动发布当天更差，旧 Pod 未摘流量、新 Pod 已就绪，短时并发再翻一倍。

面试官追问

Q：每次都访问 Redis 会不会让 Redis 成为新瓶颈？

A：会。两条路：一是把额度分段预取到本地令牌桶，一次拿 N 个，用不完按过期归还，精度换吞吐；二是把全局配额控制下沉到网关或上游 SDK 侧，应用内只保留本地保险丝。关键是明确可接受的超额比例，比如允许短时超出 10%。

Q：SSE 长连接要不要一直占着全局名额？

A：不该。占名额的应该是上游正在处理的请求，而不是连接时长。做法是首 token 返回后释放并发租约，另建活跃 stream 计数做二级限制，否则几个慢速客户端就能把整个租户的额度占死。

10给 async 鉴权依赖套上 lru_cache：权限回收后仍能访问，还偶发 cannot reuse already awaited coroutine

进阶 ｜ 依赖注入缓存失效并发安全鉴权

为什么会有这个问题

FastAPI 的 Depends 自带缓存是请求级的：同一请求内同一个 callable 加同一组参数只执行一次，请求结束就失效，这是安全的。而 functools.lru_cache 是进程级、跨请求、无 TTL、无主动失效的，两者语义完全不同却被当成同一件事用。三个具体坑：一是把 async 函数直接装饰，缓存的是 coroutine 对象，第二次命中返回已 await 过的协程，抛 RuntimeError，并发命中时多个请求还会 await 同一个协程共享结果；二是缓存 ORM 对象或带 session 的对象，请求结束后 session 已关闭，下一个请求拿到 detached 实例，访问属性触发 DetachedInstanceError 或懒加载失败；三是权限、角色、禁用状态变更后缓存不会失效，多 worker 下每个进程各存一份，出现同一个人在 A Pod 能进、B Pod 被拒的诡异现象。

怎么做

  1. 止血优先：移除装饰器并滚动重启，确认 401/403 与越权告警回落，再谈优化。
  2. 全量排查依赖链上的进程级缓存：grep @lru_cache、@cache、模块级 _cache = {}、类属性字典，逐一判断 key 是否含身份、value 是否可变、是否有失效路径。
  3. 划边界：只允许缓存不可变、无用户上下文、可容忍过期的数据，例如 JWKS 公钥、settings、模型价格表、模型元数据；用户、权限、会话、DB session、HTTP client 一律不进进程内缓存。
  4. 必须缓存时用显式 key，包含 tenant + user_id + 权限版本号，value 只存纯 dict 或 dataclass，配 TTL 与容量上限，版本号变更即自然失效。
  5. async 场景缓存值而不是协程：函数内部 await 完成后写缓存，加 asyncio.Lock 做双检，避免缓存 coroutine。
  6. 加并发回归用例：两个不同 token 交替请求断言返回身份一致；撤销权限后立刻请求断言 403。把这条写进评审规则，禁止在 Depends 链上出现 lru_cache。
  7. 补观测：鉴权耗时的收益要用缓存命中率衡量，同时监控缓存对象与 token 身份的匹配断言。
import asyncio, time from functools import lru_cache # 反例：缓存 coroutine，且无 TTL、无失效 @lru_cache(maxsize=2048) async def get_current_user(user_id: str): return await repo.get_user(user_id) # 正例：缓存不可变值，key 带权限版本，TTL 兜底 _perm_cache = {} _lock = asyncio.Lock() async def get_perm(tenant: str, user_id: str, version: int) -> dict: key = (f'{tenant}:{user_id}', version) hit = _perm_cache.get(key) if hit and hit[0] > time.monotonic(): return hit[1] async with _lock: hit = _perm_cache.get(key) if hit and hit[0] > time.monotonic(): return hit[1] data = await repo.load_perm(tenant, user_id) _perm_cache[key] = (time.monotonic() + 30, data) return data

真实场景

某 AI 应用中台的鉴权依赖每个请求要查两次库，有人为了降 P99 给 get_current_user 加了 lru_cache，压测确实好看。两周后客服反馈：员工账号被禁用后仍能调用接口，且只有部分实例复现；同一时间段告警里出现 RuntimeError: cannot reuse already awaited coroutine，集中在并发高峰。排查发现四个 worker 各自持有一份缓存，禁用操作只改了数据库，没有任何失效广播；而低并发时偶发的 500 则来自第二个请求命中了第一个请求留下的协程对象。

面试官追问

Q：换成 TTL 60 秒的缓存能接受吗？

A：lru_cache 本身没有 TTL，得换 cachetools 或自建。即便有 TTL，权限回收仍存在最长 60 秒的越权窗口，多进程之间还不一致；权限这类数据更适合版本号加事件失效，TTL 只作为兜底。若业务明确可接受该窗口，也要把窗口写进安全评审结论里，而不是默认。

Q：Depends 的 use_cache 能不能替代跨请求缓存？

A：不能。它只在单次请求的依赖树内去重，请求结束即销毁，正好是安全的那个级别。跨请求复用只能靠外部缓存，并且必须自己解决 key 隔离、失效与容量问题。
