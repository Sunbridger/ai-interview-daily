01HITL 审批排队期间计划已漂移：票据过期、参数哈希与旧快照执行怎么防

资深 ｜ HITL审批票据幂等越权防护 ｜ 面经来源 ↗

为什么会有这个问题

HITL 的工程本质不是弹窗确认，而是把高风险副作用放进可审计、可拦截的闸门。审批是异步的：人可能在几分钟甚至几天后响应，而 Agent 的计划、工具参数、资源状态、权限和预算都可能变化。如果审批只返回一个 approved=true，执行端没有把审批绑定到具体计划快照和参数，就会出现 TOCTOU：人批准的是 A，执行的是 B。常见错误认知是「审批通过就安全」，忽略票据有效期、执行前复核和重复执行。

怎么做

  1. 审批对象分级：只读、可逆、低风险操作走自动策略和采样审计；资金、外发、删除、权限变更等高风险工具必须做步骤级审批，计划级审批只用于可逆批量任务。
  2. 票据绑定快照：ticket 至少包含 plan_hash、step_id、tool_name、args_hash、tool_schema_version、resource_version、approver、expires_at；任一字段变化票据立即失效。
  3. 执行前 preflight：重新拉起资源版本，校验权限、预算、参数 schema 和业务前置条件；不满足就拒绝执行并进入 replan，不允许静默改参数。
  4. 幂等与副作用账本：以 ticket_id 作为幂等键传给工具，记录 intent、executed、committed 状态；不可幂等工具用 outbox 或两阶段确认，避免审批后重放导致重复副作用。
  5. 过期与拒绝处理：TTL 按风险分级；过期后把审批时快照与当前状态差异展示给审批人重新签发，不自动续期；拒绝则回退计划重写。
  6. 审计与指标：记录审批快照、执行快照和 diff；监控 approval_latency、stale_ticket_reject_rate、duplicate_side_effect、replan_rate；异常升高时暂停该类工具并人工排查。
from dataclasses import dataclass from hashlib import sha256 import json, time @dataclass(frozen=True) class Ticket: ticket_id: str plan_hash: str args_hash: str expires_at: float approved_by: str = 'pending' def digest(obj): raw = json.dumps(obj, sort_keys=True, ensure_ascii=False) return sha256(raw.encode()).hexdigest() def issue(plan, step, ttl=600): return Ticket( ticket_id='apr_%s_%d' % (step['id'], time.time()), plan_hash=digest(plan), args_hash=digest(step['args']), expires_at=time.time() + ttl, ) def execute(ticket, plan, step, approver, precheck): if ticket.approved_by != approver: raise PermissionError('not approved') if time.time() > ticket.expires_at: raise PermissionError('expired') if ticket.plan_hash != digest(plan): raise PermissionError('plan drifted') if ticket.args_hash != digest(step['args']): raise PermissionError('args drifted') if not precheck(step): raise RuntimeError('precondition failed') return step['call'](idempotency_key=ticket.ticket_id)

真实场景

某项目做退款和工单处理 Agent，审批队列积压，人工在较晚时间点才点通过；等待期间用户取消订单或金额变化，Agent 仍按审批时的旧参数调用退款工具，出现重复退款或越权操作。排查发现日志里只有 approved=true，没有 plan_hash 和 args_hash，执行端也无法判断票据是否过期。修复后票据绑定计划与参数哈希，执行前复核资源版本，过期票据进入 replan，重复副作用才被收敛。

面试官追问

Q：审批粒度太细会让人工成为瓶颈，怎么平衡？

A：按风险分级：低风险自动执行加采样审计，中风险做计划级审批或批量审批，高风险做步骤级审批；用金额、数据敏感度、可逆性、外发对象动态升级。审批界面只展示关键 diff 和证据，同时监控积压，超过阈值时转异步或直接拒绝，不能默认放行。

Q：审批通过后 precheck 失败，能不能让 Agent 自动调整参数再执行？

A：不能静默调整。参数变化意味着审批对象变了，必须重新签发票据；可以让 Agent 生成新计划并展示差异，走快速审批。若业务有容差，必须在策略里显式定义容差范围并记录审计，不能由模型自行判断。

02并行子 Agent 部分失败被合成成全量成功：覆盖率契约、可信度与降级结论怎么设计

进阶 ｜ 多Agent并行编排部分失败结果合成 ｜ 面经来源 ↗

为什么会有这个问题

fan-out 并行子 Agent 能降时延，但部分失败是常态：超时、限流、工具报错、子 Agent 返回空结果。问题常出在收集与合成阶段：异常被 except 吞掉，results 里只 append 成功项，模型看到的是「看起来完整」的上下文，于是把部分覆盖当成全量覆盖，输出确定结论。另一种错误是把「成功但空」和「失败」混为一谈，或者对所有失败无脑重试，放大成本和重复副作用。

怎么做

  1. 子任务契约：拆解时标记 required/optional、是否幂等、超时预算、可重试错误类型；required 决定是否允许降级。
  2. 统一结果信封：每个子 Agent 返回 task_id、status、data、error_class、coverage、source_refs、trace_id；禁止只返回裸 data 或字符串。
  3. 收集阶段不吞异常：用 gather(return_exceptions=True) 或等价机制，把异常转成 failed/timeout 信封，保留失败原因和已耗时。
  4. 确定性 gate：合成前计算 coverage；required 未全覆盖进入 degraded 模式，缺失项单独列出；optional 缺失可继续，但输出必须标注。
  5. 重试策略：只对 retryable 且幂等的子任务重试，预算随链递减；权限拒绝、业务拒绝不重试；重试仍失败则固化结果，不无限重入。
  6. 合成约束：给模型的输入包含 coverage 和 missing，prompt 明确禁止推断缺失项；输出 schema 要求每个结论带 source_task_id，后置校验 unsupported claim。
  7. 降级输出与接管：degraded 结果附带覆盖率、限制和下一步建议；高风险结论进入 HITL 或二次补采，不直接对外。
import asyncio from dataclasses import dataclass from enum import Enum class Status(str, Enum): OK = 'ok' FAILED = 'failed' TIMEOUT = 'timeout' @dataclass class Envelope: task_id: str required: bool status: Status data: dict | None = None error: str | None = None async def run_one(task, agent): try: data = await asyncio.wait_for(agent(task), timeout=task.timeout) return Envelope(task.id, task.required, Status.OK, data) except asyncio.TimeoutError: return Envelope(task.id, task.required, Status.TIMEOUT) except Exception as e: return Envelope(task.id, task.required, Status.FAILED, error=type(e).__name__) async def collect(tasks, agent): return await asyncio.gather(*(run_one(t, agent) for t in tasks)) def synthesis_gate(results): missing = [r.task_id for r in results if r.required and r.status is not Status.OK] coverage = sum(r.status is Status.OK for r in results) / max(len(results), 1) if missing: return {'mode': 'degraded', 'missing': missing, 'coverage': coverage} return {'mode': 'full', 'coverage': 1.0}

真实场景

某项目做行业研究 Agent，并行拆出财报、新闻、招聘、专利等子任务，其中部分子任务超时；合成模型仍输出完整结论和确定数字，用户追问时发现关键数据没有来源。排查发现收集阶段把异常吞掉，失败子任务没有进入 results，synthesis prompt 也没有 missing 字段。修复后每个子任务返回统一信封，required 缺失时进入降级合成并列出缺失项，结论必须带 source_task_id；同时监控 subtask_success_rate、synthesis_coverage、unsupported_claim_rate 和重试成本。

面试官追问

Q：required 子任务失败时，应该阻塞等待还是先输出降级结果？

A：看时效、风险和补采成本：可补采且预算允许时做有限重试或换源；否则输出降级结果并明确缺失，不阻塞整个会话。对外高风险结论走 HITL。关键是不能让模型把缺失当已知。

Q：如何避免合成模型编造缺失项？

A：输入结构化，只给 covered data，missing 单独字段；prompt 明确禁止推断；输出 schema 强制 source_task_id；后置规则校验无来源断言；必要时用模板化合成替代自由生成。

03代码执行 Agent 的沙箱：超时残留、容器复用污染与产物回灌怎么控

资深 ｜ 工具执行沙箱隔离资源限制故障定位

为什么会有这个问题

代码解释器类工具把模型生成的不可信代码直接跑在服务侧，执行时长和资源占用都不可预知，最常见的错误认知是「给个 timeout 就安全了」。实际上有三个坑：一是超时后 kill 只杀了父进程，模型代码里 fork/subprocess 出去的子孙进程仍在跑，形成孤儿进程；二是容器池复用时工作目录和 pip 缓存被跨会话继承，模型读到上一次会话的文件却当作本会话数据；三是产物（csv/图片）被 base64 塞回工具结果，直接把下一轮上下文打爆，表现为请求 400 而不是工具报错。三者都不报异常，线上只看到「Agent 结论怪」或「偶发超限」。

怎么做

  1. 执行隔离：每次执行创建会话级独立 workspace（mkdtemp），容器根文件系统只读，HOME 指向 workspace，python 用 -I 隔离开环境变量与用户 site-packages，避免上一次会话的模块与数据残留。
  2. 进程回收：用 Popen(start_new_session=True) 让执行体独占进程组，超时后 os.killpg 整组 SIGKILL，并在 finally 里再补一次 killpg（吞掉 ProcessLookupError），覆盖模型代码已经 spawn 子进程的场景；内存用容器侧 limit/ulimit 做硬限，不依赖代码自检。
  3. 输出与产物契约：stdout/stderr 按字节截断并回传 truncated 标记，让模型知道内容不全；产物一律落 artifact store，工具结果只返回 {artifact_id, name, size, preview 若干行}，需要细看时由模型再调用读取工具按需取片段。
  4. 错误分类回灌：把 returncode / signal / OOM / timeout 分成不同 reason，回灌给模型的文本不同（超时要提示拆分数据或降低复杂度，OOM 要提示分块处理，语法错误才回 traceback 末尾若干行），避免把整段堆栈塞进上下文引发连锁重试。
  5. 可观测与容量：每次执行记录 exec_id、排队等待、执行耗时、peak rss、kill reason；用等待时间占比区分「池容量不足」与「模型代码慢」，前者扩池或排队超时降级，后者改 prompt 或限制单次数据量。
  6. 池化复位校验：容器归还前删除 workspace、清 pip 缓存与 /tmp，并对关键目录做一次 diff 校验，防止清理逻辑漏掉路径导致跨会话污染。
  7. 压测与回归：用固定的一组恶意样例（死循环、fork 炸弹、写大文件、读上一会话文件）纳入回归，每次改沙箱配置都跑一遍。
import os, signal, subprocess, tempfile, shutil OUT_LIMIT = 8 * 1024 def run_python(code: str, timeout: float = 20.0) -> dict: workdir = tempfile.mkdtemp(prefix="exec-") proc = subprocess.Popen( ["python", "-I", "-c", code], cwd=workdir, stdout=subprocess.PIPE, stderr=subprocess.PIPE, start_new_session=True, env={"PATH": "/usr/local/bin", "HOME": workdir}, ) reason = None try: out, err = proc.communicate(timeout=timeout) except subprocess.TimeoutExpired: os.killpg(proc.pid, signal.SIGKILL) out, err = proc.communicate() reason = "timeout" finally: try: os.killpg(proc.pid, signal.SIGKILL) except ProcessLookupError: pass if proc.returncode in (-9, 137): reason = reason or "oom_or_sigkill" artifacts = [ {"name": n, "size": os.path.getsize(os.path.join(workdir, n)), "artifact_id": put_artifact(os.path.join(workdir, n))} for n in os.listdir(workdir) ] shutil.rmtree(workdir, ignore_errors=True) return {"reason": reason, "returncode": proc.returncode, "stdout": out[:OUT_LIMIT].decode("utf-8", "replace"), "truncated": len(out) > OUT_LIMIT, "artifacts": artifacts}

真实场景

某项目的分析类 Agent 挂了代码执行工具。症状一：夜间批量任务偶发把宿主 CPU 打满，排查发现执行超时后主进程被杀，但模型代码里起的多进程仍在跑，killpg 缺失是根因。症状二：容器池复用后，某次会话的分析结论引用了上一轮遗留的 data.csv，数据完全对得上但业务方说「这不是我们的客户」。症状三：工具生成的 csv 被 base64 回填进工具结果，下一轮请求直接超上下文，前端只看到一个 400，链路里没有任何工具层错误。

面试官追问

Q：为什么不用线程 join(timeout) 或 signal.alarm 做超时？

A：线程无法被强制终止，join 超时只是放弃等待，执行体仍在跑并继续占 CPU；signal.alarm 只对主线程有效，且与业务侧其他定时器冲突。超时必须落到进程边界：独立进程组 + killpg，资源上限交给 cgroup/ulimit，仅靠 Python 层控制不住。

Q：怎么区分「模型写的代码慢」和「沙箱资源不足」？

A：看三个指标：排队等待时间、执行耗时、peak rss。排队占大头是池容量问题，扩池或加排队超时；执行耗时集中撞 timeout 且 rss 接近上限，是算法或数据量问题，应把提示改成「先采样再聚合」而不是加超时。两类要打不同 reason 标签，否则优化方向会跑偏。

04strict 默认值被封装层翻转后，工具参数三层校验错位：静默回默认与批量拒绝怎么定位

进阶 ｜ 工具调用schema 校验SDK 升级灰度发布 ｜ issue来源 ↗

为什么会有这个问题

工具参数的约束实际上分散在四层：模型侧的 JSON Schema（strict 模式）、SDK 封装层构造请求时的默认值、应用层 pydantic 校验、下游服务自己的校验。四层语义并不一致，常见错误认知是「有 pydantic 就安全了」。典型错位有两类方向相反的故障：一是封装层或 SDK 升级把 strict 从 false 改为 true，以前能跑的宽松 schema（缺 additionalProperties:false、optional 字段没进 required）被上游直接拒绝，表现为批量 400；二是应用层用 extra=ignore 把模型多给的字段悄悄丢掉，缺失的必填字段又有默认值，工具「成功」返回但参数是默认值。前者是硬失败容易发现，后者静默出错，往往等业务方反馈才发现。

怎么做

  1. 确立唯一事实源：用 pydantic 模型生成 JSON Schema，生成后显式补 additionalProperties:false，并要求所有字段在 strict 模式下都进入 required，可空字段用 Optional + null 表达，不允许「字段可缺省」这种表达能力。
  2. schema 快照测试：把每个工具的最终 spec 存成快照文件，SDK 或模型适配层升级后跑 diff，任何字段类型、required 列表、默认值变化都在 CI 阶段拦住，而不是等线上错误率抬升。
  3. 应用层显式严格：模型用 ConfigDict(extra="forbid")，必填字段一律不给默认值；校验失败时不填默认值兜底，而是返回结构化错误（字段名 + 允许值 + 简短原因）回灌给模型，让它自己改参数重试一次。
  4. 打 rejected_by 标签：工具结果里区分 model_schema / sdk / app_schema / upstream 四类拒绝来源，以及一个 silent_default 标记（参数由默认值填充而非模型给出），把静默失败变成可统计指标。
  5. 灰度与止血：先在 shadow 模式记录「如果按 strict 校验会被拒」的比例，再按工具维度打开 strict；出问题时按工具名 + rejected_by 快速回滚成旧 spec，而不是整体降级 SDK。
  6. 兼容不支持 strict 的模型：适配层把统一 spec 降级成自然语言描述 + 应用层强校验，同时记录降级标记，按模型统计参数错误率，超过阈值就禁止该模型接这个工具。

真实场景

某项目升级 agent SDK 小版本后，create_ticket、search_docs 等带枚举和可选字段的工具错误率一夜抬升，日志里只有下游返回的 invalid_request，本地单测全绿。同期另一批工具看起来正常，但工单 priority 全部落在 low——因为模型多给的字段在应用层被 extra=ignore 丢掉，priority 缺失又走了默认值。两种症状一个硬失败一个静默错误，只有加上 rejected_by 与 silent_default 标签、并做 schema 快照 diff 后，才定位到是封装层 strict 默认值与本地 schema 不完整叠加导致的。

面试官追问

Q：为什么不在 prompt 里把 schema 写清楚就够了？

A：prompt 不是契约，模型输出会随版本和采样漂移，且不同 provider 的 strict 语义不同。schema 必须由代码生成、做快照、由服务端校验兜底；prompt 只放描述与示例，承担引导作用而不承担正确性。

Q：如何兼容不支持 strict JSON Schema 的模型？

A：对外统一一份严格 spec 作为事实源，适配层对弱能力模型降级成「自然语言描述 + 示例 + 应用层强校验」，并给调用打 model_degraded 标签。按模型统计参数错误率与 silent_default 比例，超阈值就把该模型从这个工具的候选列表里摘掉。

RAG 专题

05知识经常变却用 SFT 灌进去，两周后模型还在答旧政策：RAG、微调与规则层的职责怎么切、回归验证怎么做

资深 ｜ ragfinetune评测选型 ｜ 面经来源 ↗

为什么会有这个问题

团队遇到答不准时第一反应是「模型不行，微调一下」，于是把产品文档、政策条款、FAQ 全部做成 SFT 数据。问题在于：参数化记忆没有 TTL、不能按单条失效、不能按用户权限过滤、也无法溯源引用，知识一旦进权重就只能靠再训一次覆盖，而 base model 升级又会把上一次的知识全部丢掉。反过来说，RAG 也治不了所有病：输出格式不稳定、领域缩写解读错误、该拒答时硬答、工具调用参数不规范，这些是「行为分布」问题，靠检索塞上下文往往越塞越乱。真实工程里必须先把「缺知识 / 行为不稳 / 流程没设计好」切开，再决定是补索引、写约束还是上 SFT，否则两个手段互相背锅。

怎么做

  1. 建立 badcase 归因表：每条失败样本必须落盘 query、召回 top-k 的 doc_id 与分数、gold 文档是否命中、模型答案、人工判定标签（缺证据 / 有证据没用上 / 多次回答不一致 / 流程走错），没有这张表就没有选型依据。
  2. 按归因分流：gold 文档不在 top-k → 知识缺失或召回问题，走补数据、改切分、加词法通道；gold 在但答案没用到 → 提示词与上下文排布、引用契约；同一 query 同等召回下多次采样答案不一致 → 行为不稳；多步任务中间步骤错 → 编排与工具契约。
  3. 只有当「证据齐全但模型持续不遵守输出规范或不懂领域表述」时才考虑 SFT，且训练集里不放易变事实，只放行为样本：引用格式、拒答话术、字段解读、工具参数范式。
  4. 采用混合形态：RAG 提供事实与权限边界，SFT 只教「怎么用检索结果说话」；用 LoRA 小学习率，混入 10%–20% 通用指令与「依据上下文作答」样本抵抗遗忘。
  5. 把「不改模型就能改」的东西全部下沉到规则层：schema 约束解码、答案校验器、低置信度转人工、路由规则，这些才能按天迭代。
  6. 建回归门禁：把评测集拆成知识子集与行为子集，任何一次 prompt、切分、索引参数或 SFT 版本变更都要跑双集，知识集不允许下降，行为集看格式合规率与拒答准确率，通过后灰度。
  7. 版本治理：索引侧支持热更新与 alias 切换；SFT 版本必须绑定 base model 版本，base 升级视为重训，不能默认继承。
def triage(case): docs = case["retrieved"][:10] if not ({d["doc_id"] for d in docs} & set(case["gold_doc_ids"])): return "knowledge_missing" # 补文档、改切分、加召回通道 used = any(g in case["answer"] for g in case["gold_spans"]) answers = {r["answer"] for r in case["repeats"]} if len(answers) > 1 and all(r["top5"] == case["top5"] for r in case["repeats"]): return "behavior_unstable" # 约束解码、schema、少量 SFT if not used: return "prompt_or_context" # 引用契约、上下文排布 return "workflow" # 路由、工具契约、流程校验 def decide(counts, total): share = {k: v / total for k, v in counts.items()} plan = [] if share.get("knowledge_missing", 0) > 0.5: plan.append("fix_retrieval_first") # 此时微调几乎无收益 if share.get("behavior_unstable", 0) > 0.2: plan.append("constrain_then_sft") if share.get("workflow", 0) > 0.15: plan.append("refactor_orchestration") return plan

真实场景

某项目做内部制度问答，运营每两周改一次报销与假期政策，团队最初把政策条文做成 SFT 数据，上线初期效果很好。两周后出现两类症状：一是用户问新政策时模型给出旧金额且语气非常肯定，检索日志里新文档其实已被召回，但模型答案与上下文冲突；二是同一个问题，一次带引用一次不带，格式合规率只有七成左右。排查路径：先跑归因表，发现知识缺失只占少数、大部分是「有证据没用上」和「多次回答不一致」；再对比 SFT 前后在知识子集上的表现，确认微调把「优先相信权重」这个偏好带了进来。最终把政策事实全部退回索引层，SFT 只保留引用格式与拒答行为的样本，并把格式校验下沉为输出 schema 校验，旧模型版本按 alias 回滚。

面试官追问

Q：如果 SFT 之后行为集变好但知识集明显下降，你怎么处理？

A：先确认不是评测集与文档版本错位；然后按灾难性遗忘处理：降低 LoRA rank 与学习率、缩短步数、在训练集里混入「仅依据给定上下文作答」和通用指令样本；同时把知识类问题在推理侧强制走 RAG，并在 prompt 里明确上下文优先于参数记忆。若仍下降，说明这批 SFT 数据本身在教模型「凭记忆答」，应删样本而不是继续调参。

Q：为什么不干脆把全部文档塞进长上下文，省掉索引和微调的争论？

A：成本、权限与更新粒度三方面都不成立：长上下文按 token 计费且每轮重复付费；文档级权限过滤在拼接前就要做，长文直塞很难保证不越权；一次政策改动要重建整个 prompt 缓存。长上下文适合「少量、稳定、同一租户」的材料，知识型、多租户、频繁变更的场景仍然要靠检索分层。

06服务指标全绿但用户说新文档搜不到：向量索引的健康度该监控哪些层、抽检召回怎么建

进阶 ｜ ragvector-index监控召回评估 ｜ 面经来源 ↗

为什么会有这个问题

向量库的故障几乎都是静默的：不会抛 5xx，也不会让 p99 变红，只会让召回一点点变差。原因在于 ANN 索引本身是近似结构且异步维护——删除是打墓碑、更新是写新段、段合并与索引构建在后台跑、量化与剪枝有损，任何一环滞后都只体现在「结果里少了几条」。只监控 QPS、延迟、错误率等于没监控；只看向量条数也不够，条数对但内容过期、删除未生效、部分 partition 没重建，都会让条数看起来完全正常。必须把数据层、索引层、效果层分开定义指标，并用带 gold 的抽检集持续验证真实召回。

怎么做

  1. 数据层指标：期望条数（由上游文档 manifest 与切分版本推算）与实际 num_entities 的缺口、删除率 tombstone ratio、最新一条写入的时间水位、以及每个 partition 的向量数与文档数是否同比例。
  2. 索引层指标：段数量与单段大小分布、索引构建滞后 build lag（写入成功到可被检索的时间差）、索引字节与原始向量字节之比（判断是否膨胀或未压缩）、内存驻留率与是否落盘、索引版本号。
  3. 效果层指标：分层抽检集的 recall@k 与 nDCG、空结果率、top1 相似度分数分布漂移、拒答率；分数分布漂移往往先于 recall 下降出现，是最早的信号。
  4. 抽检集建设：200–500 条 query，按业务类目分层并显式覆盖长尾，每条绑定当前文档版本的 gold doc_id；文档改版时必须重标，否则监控会长期失真。定时任务跑结果写入时序库，与上一基线比较。
  5. 线上 trace 关联：每次请求记录 top-k 的 doc_id、score 与 index_version，badcase 可原样回放，直接判断是「没召回」还是「召回了没用上」。
  6. 告警分级与处置动作：效果层跌超过阈值 → 通知并考虑切回上一 alias；build lag 超阈值 → 暂停批量写入或降级读旧索引；删除率过高 → 触发 compaction 或重建；变更（换 embedding、改切分、调参）必须跑同一套抽检集才允许放量。
def inspect(store, golden, baseline, dim=1536): s = store.stats("kb") alive = s["num_entities"] expected = store.manifest_chunks("kb") tomb = s["deleted"] / max(s["inserted"], 1) bloat = s["index_bytes"] / max(alive * dim * 4, 1) ok = sum(1 for q, g in golden if {d["doc_id"] for d in store.search(q, k=10, partition="kb")} & g) recall = ok / len(golden) alerts = [] if alive < expected * 0.95: alerts.append("count_gap") if tomb > 0.30: alerts.append("tombstone_high") if bloat > 1.6: alerts.append("index_bloat") if recall < baseline["recall"] - 0.03: alerts.append("recall_drift") if store.build_lag_seconds() > 900: alerts.append("build_lag") return {"recall@10": round(recall, 3), "tombstone": round(tomb, 2), "alerts": alerts}

真实场景

某项目上线三个月，看板上 QPS 平稳、p99 正常、错误率为零，但陆续有用户反馈「上周上传的文档问不到」。排查路径：先核对写入侧，SDK 调用全部返回成功；再看索引层，build lag 曲线在白天持续爬升，段数量随每日增量单调增长，删除率因频繁重刷同一批文档已接近四成而合并没跟上；再用抽检集跑效果层，recall@10 相对基线缓慢下滑，空结果率同时抬升——说明不是写入失败，而是可检索性与索引结构在退化。处置是限制批量写入速率、触发 compaction、按 alias 切到重建后的索引，并把删除率与 build lag 加进告警。另一类事故是换 embedding 时只重建了部分 partition，同一集合里混了两套向量空间，条数完全正常但相似度不可比，靠 index_version 维度的抽检对比才定位到。

  A --> C[索引层 段数 构建滞后 字节比]

面试官追问

Q：抽检集怎么选才不会被误导？

A：分层抽样而不是随机抽样，长尾类目必须有代表样本；gold 要绑定文档版本，文档改版即重标；定期用线上真实 query 补充，并结合采纳、点击、人工纠错等信号扩充难例。同时监控抽检集自身的命中率分布，如果某类目长期全对或全错，说明该层样本已经失去区分度。

Q：只监控 recall 够不够？

A：不够。recall 只反映「能不能捞到」，不反映「捞到之后有没有用上」，也不反映延迟和成本。要同时看空结果率、top1 分数分布漂移（阈值会跟着失效）、索引字节与构建滞后。诊断时用 trace 把召回结果和最终答案对齐，才能区分是检索问题还是生成与流程问题。

07全量重建 RAG 索引时导入很快、可检索却晚了数小时：导入后 compaction 与段可见性怎么算进重建窗口

资深 ｜ 索引重建compaction写入放大容量规划 ｜ issue来源 ↗

为什么会有这个问题

很多团队用「导入吞吐」估算重建窗口，把写入任务完成当成索引可用；但向量库内部通常是分段写入 + 后台合并 + 建索引 + 段发布，导入只完成了日志与原始段落盘，真正可高效检索要等索引构建完成、段发布、compaction 收敛。逐条 upsert 会制造大量小段，后台合并与在线查询抢 CPU/IO，导致「导入 40 分钟、可服务却拖到几小时后」，同时在线 p99 抖动。另一个常见错误认知是只看导入任务的成功状态，不看 searchable/indexed 比例、段数量与后台任务积压，于是把「搜不到新文档」误判为应用层缓存或 embedding 问题。

怎么做

  1. 先把重建拆成四个可观测阶段：写入接收完成、段可服务（searchable）、索引构建完成（indexed）、后台 compaction 积压归零。每个阶段都设门禁，而不是只看导入任务退出码。
  2. 在 staging 用与生产同规模、同更新比例的数据做基准，记录不同 batch size 与并发下的导入吞吐、段数量增长、compaction backlog 曲线，把重建窗口算成「导入 + 索引构建 + 合并收敛 + 灰度切换 + buffer」，不要用单次小样本外推。
  3. 控制写入形态：优先用 bulk import 通道而非逐条 upsert；按时间或业务分区重建到新 collection，稳定后切别名；避免边导边大批量删除，减少 tombstone 与写放大。
  4. 做资源隔离与限流：给 compaction 设并发上限或错峰执行，让在线 query 节点与重建写入不共享同一批 CPU/IO；导入窗口避开业务高峰。
  5. 建立切换门禁与回滚：searchable 比例达标、段数量与行数比例合理、compaction backlog 低于阈值、冒烟集召回通过，才允许切别名；旧 collection 保留一段时间用于回滚。
  6. 上线后持续监控 segment 数、indexed ratio、后台任务积压、查询 p99 与召回抽检，防止「一次性重建成功、日常增量又把段数堆回去」。
import time def rebuild(alias, new_collection, client, max_backlog=50, timeout=6 * 3600): client.create_collection(new_collection) bulk_import(client, new_collection, source="snapshot/latest") client.flush(new_collection) deadline = time.time() + timeout last = {} while time.time() < deadline: last = client.get_collection_metrics(new_collection) ready = ( last["searchable_ratio"] >= 0.999 and last["indexed_ratio"] >= 0.999 and last["compaction_backlog"] <= max_backlog and last["segment_count"] <= max(8, last["rows"] // 200_000) ) if ready and smoke_test(client, new_collection): client.switch_alias(alias, new_collection) return True time.sleep(60) raise TimeoutError(f"rebuild not ready: {last}")

真实场景

某项目夜间做全量重建：导入任务约一小时就显示完成，但新文档到第二天早上才稳定可搜，期间在线查询 p99 明显抬升。排查发现写入走的是逐条 upsert，产生大量小段，后台 compaction 持续积压并与在线查询抢 IO；运维只监控了导入任务成功率，没有监控 searchable 比例与段数量。改为快照 bulk import + 新 collection 重建 + 指标门禁后，可服务时间点变得可预测，切别名前也能提前发现未就绪。

  B --> C[flush 并等待段可服务]
  C --> D{searchable 与 indexed 达标}
  D -- 否 --> C
  D -- 是 --> E{compaction 积压低于阈值}
  E -- 否 --> C

  F -- 通过 --> G[切换别名]

面试官追问

Q：直接把 compaction 并发调大不就能缩短窗口吗？

A：不一定。瓶颈可能在单分片、磁盘 IO 或索引构建线程，盲目提高并发会加剧写放大并与在线查询抢资源，表现为导入更快但查询长尾更差。应先定位瓶颈在 CPU、IO 还是段数量，再做限流与错峰，而不是只调大并发。

Q：怎么判断「新文档搜不到」是段未发布、索引未建完，还是应用缓存？

A：分层验证：先按主键做精确查询，能中说明数据已写入；再做向量查询，不能中多为索引未就绪或段未发布。对照 searchable/indexed 指标与 segment 状态；最后在应用侧带 trace 重放，确认是否命中语义缓存或旧别名。

08同一个问题昨天答对今天答错、trace 里检索却都命中：缺知识、行为不稳与流程缺陷怎么分层归因

资深 ｜ 可观测性归因回归评测trace ｜ 面经来源 ↗

为什么会有这个问题

RAG 回答不好往往被笼统归因为「模型不行」或「知识不够」，但真实原因分布在四层：知识层（文档没入库、切块丢内容、权限过滤把证据删掉）、检索层（没召回、排名低、被噪声淹没）、生成层（有证据仍答错、prompt 遵循差、上下文截断）、流程层（路由走错、工具没调、语义缓存返回旧答案、会话状态污染）。缺少固定输入快照与分层指标时，任何单点修改都无法验证，还会出现「改 prompt 治好了个例、整体回归变差」。另一个常见错误认知是线上日志能直接复现，实际上模型温度、缓存、索引版本与 query 改写都会让结果不可复现。

怎么做

  1. 先固化可复现证据：记录原始 query、改写后 query、filters、top-k 文档 id/分数/版本、prompt 版本与 hash、模型与采样参数、工具调用链、命中的缓存键、最终答案。没有这些就无法 replay。
  2. 做分层判定而不是直接改 prompt：第一步确认 gold 证据是否在库且未被权限/切块丢弃；第二步确认是否被召回及排名；第三步做 oracle 注入，把 gold 证据直接喂给模型看能否答对；第四步检查路由、工具与缓存是否走对。
  3. 用对照实验隔离变量：同一 prompt 与证据换温度或模型；同一模型换检索结果；关闭缓存重放；固定采样参数。一次只动一个变量，避免「补了文档又改了 prompt」导致归因失效。
  4. 建立小规模分层回归集，按失败类型打标签（缺知识/未召回/生成错误/流程错误），每次改动跑同一批样本，统计各层通过率与拒答率，而不是只看整体准确率。
  5. 按归因结果修复：缺知识补库、修切块与权限；未召回调召回与改写；生成层收紧 prompt、降温度、加结构化校验或 claim 支撑检查；流程层修路由规则、工具契约与缓存键/失效策略。
  6. 把分层指标与抽检做成日常门禁：新文档入库抽检、缓存命中抽检、模型或 prompt 变更前后回归，避免同类问题反复出现。
def diagnose(case, rag, llm): q = case["query"] ctx = rag.retrieve(q, filters=case["filters"], trace=True) if not rag.exists(case["gold_doc_id"], filters=case["filters"]): return "缺知识: 文档未入库或被切块/权限过滤" if case["gold_doc_id"] not in [d.id for d in ctx.docs]: return "检索层: 未召回或排名过低" oracle = llm.answer(q, evidence=[case["gold_text"]], temperature=0) if not case["judge"](oracle, case["gold_answer"]): return "生成层: 有证据仍答错, 查 prompt/模型/截断" base = llm.answer(q, evidence=ctx.docs, temperature=0) if not case["judge"](base, case["gold_answer"]): return "上下文层: 排序或噪声导致证据被淹没" return "流程层: 缓存/路由/会话状态或评测口径"

真实场景

某项目客服 RAG 出现「同一问题上午答对、下午答错」，日志显示两次都召回了同一篇文档。分层 replay 后发现：一部分是语义缓存命中了旧答案；一部分是权限过滤把关键段落删掉后模型仍然编造；还有一部分是 query 改写把产品型号写错导致根本没召回。此前团队一直在调 prompt，整体指标没有改善；按层打标签后，修复分别落到缓存键与失效、权限与切块、改写规则与召回阈值上，回归集通过率才稳定提升。

面试官追问

Q：怎么区分「检索没召回到」和「召回了但模型没用」？

A：做 oracle 注入：把 gold 片段直接放在上下文首位喂给模型，若答对说明生成层可用，问题在召回或排序；若仍答错则查 prompt 约束、上下文长度截断与模型参数。再用原始召回结果对照，就能把两层拆开。

Q：线上没有人工标注，怎么低成本做归因？

A：用 LLM-as-judge 对「证据是否充分」「答案是否被证据支撑」打分，并人工抽检校准 judge 的一致性；按 query 聚类采样而不是全量跑，优先覆盖高频与高风险意图，同时保留原始 trace 以便复核。

FastAPI 专题

09滚动发布时 LLM 流式响应被拦腰截断：SIGTERM 到 lifespan shutdown 之间，在途请求和后台任务谁来兜

资深 ｜ lifespangraceful-shutdownstreaminguvicorn

为什么会有这个问题

多数人默认「容器收到 SIGTERM 会自动优雅退出，等请求跑完」，这套假设在流式 LLM 接口上几乎必然失效。第一，uvicorn 排空连接的等待上限由 timeout-graceful-shutdown 决定，老版本甚至没有该参数；Gunicorn 侧还有 HTTP 流的 graceful-timeout，超时直接 SIGKILL。LLM 一次生成长回答常在几十秒到几分钟，正好落在被强杀的时间窗口里。第二，lifespan 的 shutdown 阶段只在连接排空后执行，被 SIGKILL 的进程一行 shutdown 代码都不会跑，连接池没关、进程内 BackgroundTasks 全部丢失，而且不会有错误日志。第三，K8s 从 Endpoints 摘除和发送 SIGTERM 是并行发生的，存在新请求仍打到正在退出 pod 的窗口期。最恶劣的症状是客户端拿到 200 和半截正文：重试逻辑不触发、前端只表现为一直转圈，比直接 503 难排查一个数量级。

怎么做

  1. 先摘除流量再退出：单独提供 /healthz/ready，draining 置位后返回 503，readiness probe 因此失败；同时 ASGI 层对新的业务请求直接返回 503 和 Retry-After，避免窗口期接到新请求。
  2. 在 preStop 里 sleep 的时间要不少于摘除流量在负载均衡各节点的传播时间，保证 SIGTERM 到达前新请求已停；stuck 的 preStop 会拖慢发布，需要与 rollout 的 progressDeadline 对齐。
  3. 把 timeout-graceful-shutdown 与 Gunicorn 的 graceful-timeout 显式设为大于流式请求 P99.9 的值，不要使用默认值；两个参数的先后关系要理清：Gunicorn 的值必须大于 uvicorn 的值，否则在 worker 还活着时就被强杀。
  4. 自己做排空：在 ASGI 中间件层统计在途请求数，进入 draining 后等待计数归零或达到上限，再置 server.should_exit 交给 uvicorn 走正常退出；不要指望 lifespan 里等待，那时排空已经结束，或者根本没有执行。
  5. 流式生成器要在 finally 里补结束帧或 error 帧，让客户端能区分「正常结束」和「被截断」，否则只能靠超时兜底。
  6. 耗时不可控的任务（长文档处理、批量 embedding）不要塞进请求进程，改成任务 ID 加队列，前台轮询或重连；进程内 BackgroundTasks 只用于可丢弃的事。
  7. lifespan 内按反序关停：先确认 draining、再等 in-flight 清零、随后 aclose 上游 client、最后关闭 DB pool 并写一条 shutdown 完成日志；线上排查时最重要的证据就是这条日志是否存在。

真实场景

某项目用 Gunicorn 加 uvicorn worker 部署 4 进程，接口是流式问答。每次滚动发布，监控都能看到一小部分请求返回 200，但正文明显不完整，前端一直停在加载态；同时后台用 BackgroundTasks 写的会话摘要记录，在发布窗口内出现丢失。排查路径：先把 SIGTERM 时间点与网关侧 ingress 日志对齐，发现 pod 收到 TERM 后仍有新请求进来，说明摘除流量存在延迟窗口；再看进程退出日志，一部分 pod 完全没有 shutdown 阶段的记录，判定为 graceful timeout 到期后被 SIGKILL；最后核对配置，Gunicorn graceful-timeout 是默认值，明显小于流式响应的 P99 时长。

面试官追问

Q：为什么不能用 @app.middleware('http') 里的 call_next 前后计数在途请求？

A：@app.middleware('http') 底层是 BaseHTTPMiddleware，await call_next 返回的是 Response 对象，此时响应体还没真正发出去，尤其是 StreamingResponse 的 body 会在之后异步迭代。用它做计数会在流式响应刚开始时就减一，排空判断提前成立，结果还是被截断。要通过包装 ASGI 的 send，以最后一个 more_body 为 False 的 http.response.body 帧作为真正结束标志。

Q：进程被强杀时，除了请求被截断还有什么隐患？

A：lifespan 的 shutdown 不执行，上游 AsyncClient 和 DB 连接池没有关闭，连接在服务端仍然保留到超时，重连风暴会打到刚起来的 pod；进程内的 BackgroundTasks、定时清理、指标 flush 全部丢失且没有痕迹。所以凡是有副作用的写入，都不能只依赖后台任务，要在请求内完成持久化，或者投递到持久队列。

进阶 ｜ idempotencyretrydependspostgres

为什么会有这个问题

超时不等于失败。移动端 SDK 或网关在 60 秒拿不到响应时会重发，此时服务端第一次请求可能还在跑，也可能已经成功只是响应慢，没有幂等键就只能当成两次独立请求处理：两次调用 LLM、两份账单、两条会话。常见错误认知是用请求体哈希做去重，这有三个坑：用户先后问同样的问题是合法业务，应该计费两次；请求体里带 timestamp 或 nonce 时哈希永远不命中；哈希无法表达去重的时间窗口。第二个坑是并发同键：两个相同 key 同时到达，双方都判定「记录不存在」，然后都执行，或者唯一索引冲突直接冒泡成 500。第三个坑是流式场景，第一次已经吐了一半 token，重试时既不能续上也不能重放半截内容。

怎么做

  1. 定契约：客户端必须带 Idempotency-Key（建议 UUID，一次用户动作生成一次，重试沿用），服务端用 (tenant, key) 做唯一索引；缺失时按非幂等路径处理或直接 400，取决于产品能否接受重复计费。
  2. 建幂等表：key、tenant、route、fingerprint、status（in_progress / succeeded / failed_retryable）、status_code、response_body、updated_at、expires_at。写入与业务数据放同一个库，保证能在同一事务里提交，跨服务调用再补 outbox。
  3. 抢占用 INSERT ... ON CONFLICT DO NOTHING，看影响行数决定是执行者还是观察者；观察者按状态分流：succeeded 直接回放存储的状态码和 body；in_progress 且租约未过期返回 409 加 Retry-After；租约过期则用带条件的 UPDATE 抢占，防止进程崩溃后这条键永久卡住。
  4. 拿到执行权后必须校验指纹：同 key 换了请求体说明客户端复用错了，返回 422，绝不能用旧结果冒充新请求的响应。指纹用 route 加规范化后的 body 计算，并排除签名、时间戳这类易变字段。
  5. 业务成功与幂等表置 succeeded 在同一事务提交，或者在 handler 里先写 usage 记录再更新状态；调用上游 LLM 时把幂等键透传成上游的 request 标识，上游侧再去一次重，形成双保险。
  6. 流式接口不缓存 token 流，只落最终全文与 usage；重试方拿到 409 后改为轮询 GET /runs/{key} 或依赖 SSE 的 Last-Event-ID 续传，避免在半截流上做幂等。
  7. 过期清理由定时任务批量删除，同时在幂等表上监控 in_progress 超期比例，这个指标能直接暴露进程崩溃和上游卡死。

真实场景

某项目接入移动端 SDK，SDK 默认超时 60 秒并对 POST 重试 3 次。上线长回答功能后，账单里出现同一段 prompt 连续多次调用，会话表中也有多条内容一致但 id 不同的记录。排查路径：先按用户 ID 拉出同一分钟的入站日志，发现同一个业务动作对应多条 X-Request-Id，说明是客户端重发而不是上游重试；再看第一次请求的耗时分布，多数超过 60 秒且最终成功，确认是「成功的慢请求」被客户端判为失败；核对请求头，POST 上没有携带任何幂等键，服务端也没有去重表。压测阶段还复现了并发同键双双执行、以及崩溃后同一键永久卡在 in_progress 两种边界。

面试官追问

Q：业务已经把 LLM 调成功，但在更新幂等表之前进程崩了，重试会怎样？

A：这条键会停在 in_progress，租约过期后重试方会抢占并再次执行，于是重复扣费。缓解要三道：一是调用上游时把幂等键透传成上游可识别的 request 标识，让上游也去重；二是把扣费落到独立的 usage 表，以业务键做唯一索引，重复写入自然冲突；三是 in_progress 超期的记录不要自动重放，转入告警与对账流程，宁可让用户重试一次，也不要静默重复计费。

Q：为什么不用 Redis SETNX 直接把 key 锁住，而要落库？

A：Redis 可以做第一层锁压低数据库压力，但它不能作为权威记录：主从切换或淘汰策略可能丢键，过期后重试方拿不到上次的结果，只能重新执行，幂等就退化成限流。正确做法是 Redis 承担短时并发控制、数据库承担持久状态，并且幂等结果要和业务写入保持同源，才能在一个事务里提交。
