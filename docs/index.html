01委派链上的权限放大：Policy Engine 的授权收敛与可回放审计怎么设计

资深 ｜ multi-agentpolicy-engine审计权限收敛 ｜ 面经来源 ↗

为什么会有这个问题

多 Agent 系统里权限常常是按「入口身份」一次性授予的，子 Agent 在委派时直接继承甚至叠加父级 scopes，形成 ambient authority（环境权限）放大。另一个常见错误是把 Policy Engine 写成 prompt 里的一句「不要执行危险操作」，或写成散落在各个 tool 里的 if-else。这样做的后果是：决策输入没有被固化（谁发起、在哪个会话、对哪个资源、基于哪条策略），allow 无法回放，deny 无法解释；策略缓存按 agent_id 命中却忽略了参数维度；更危险的是，模型在收到 deny 之后换个参数重试，就能绕过被拒的那条路径。审计只记录 allow/deny 结果而不记录决策依据，等于出事之后查不出是哪一层委派放的行。

怎么做

  1. 把决策输入固化成五元组：subject（含委派链）、action、resource（归一化键）、有效 scopes、policy_version。Policy Engine 做成无状态纯函数 evaluate(request) -> Decision{effect, policy_id, obligations}，模型侧不参与判定。
  2. 委派时权限单调收敛：子 Agent 的有效 scopes = 父 scopes ∩ 任务声明 scopes ∩ 工具白名单，TTL 取两者最小值，随委派生成 capability token 向下传递。禁止任何形式的并集或「继承父会话全部权限」。
  3. 工具执行器作为唯一 choke point：模型只能产出意图，真正执行必须过 Policy Engine。deny 返回结构化原因（缺哪个 scope、命中哪条策略）供模型自我修正，但同一 turn 内相同 (tool, args) 的重试要计数，超限直接终止并上报，防止换参试探。
  4. 审计与决策解耦：审计写入走独立进程或独立 sink，Agent 只能 append 自己的 trace，不能写审计通道。审计记录决策输入 hash、policy_version、obligations 的实际执行结果（如脱敏是否生效），保证可按事件回放。
  5. 缓存以 (policy_version, subject, action, resource_key) 为 key，resource_key 必须归一化（路径折叠、大小写、租户前缀）。策略热更新时整体升版本号失效；执行前用 policy_version 二次校验，版本不一致则重新评估，避免飞行中的旧决策生效。
from dataclasses import dataclass from typing import Literal @dataclass(frozen=True) class Request: subject: str action: str resource: str scopes: frozenset policy_version: str @dataclass(frozen=True) class Decision: effect: Literal["allow", "deny"] policy_id: str policy_version: str obligations: tuple def delegate(parent_scopes, parent_ttl, task_scopes, task_ttl, allowlist): return { "scopes": frozenset(parent_scopes) & frozenset(task_scopes) & frozenset(allowlist), "ttl": min(parent_ttl, task_ttl), } def evaluate(req: Request, rules) -> Decision: for r in rules: if not r.match(req.action, req.resource): continue if not req.scopes >= r.required_scopes: return Decision("deny", r.id, req.policy_version, ("scope_insufficient",)) return Decision("allow", r.id, req.policy_version, r.obligations) return Decision("deny", "default", req.policy_version, ("no_matching_policy",)) def execute(tool, args, req, rules, retry_counter): d = evaluate(req, rules) if d.effect == "deny": retry_counter.bump(req.subject, req.action, args) if retry_counter.over(req.subject, req.action, args): raise PermissionError("retry_exhausted") return {"denied": d.policy_id, "obligations": d.obligations} return tool.run(args, obligations=d.obligations)

真实场景

某项目的客服 Agent 上线后，被发现能调用原本只开放给运营侧的批量数据导出工具。审计日志里只有一条 allow，看不到是哪一层授权的。排查后得到两条线索：一是主 Agent 委派子任务时把父 session 的 scopes 全量透传，子 Agent 又叠加了工具白名单，实际权限是并集；二是策略缓存 key 只有 agent_id，同一个 Agent 第一次被允许导出后，后续不同资源参数全部命中缓存直接放行。修复方向：委派改为交集收敛 + capability token 带 TTL，缓存 key 加入归一化资源与 policy_version，审计补齐五元组与策略版本，并对 deny 后的重试加计数上限。

flowchart TD
    A[入口 Agent 收到请求] --> B[委派生成子任务]
    B --> C[有效权限取父权限与任务声明权限的交集]
    C --> D[Policy Engine 评估五元组]
    D -->|deny| E[返回结构化拒绝原因并累加重试计数]
    D -->|allow| F[产出带 obligations 的 Decision]
    F --> G[工具执行器作为唯一 choke point 执行]
    G --> H[审计事件写入独立通道]
    E --> I[同一轮重试超限则终止并上报]

面试官追问

Q：策略热更新时，已经生成但还没执行的 allow 决策怎么处理？

A：Decision 里携带 policy_version，执行器在真正调用工具前做一次版本比对：版本不一致就重新评估，评估失败则拒绝并记录 stale_decision 指标。不要靠失效缓存来保证，因为决策可能已经在队列或另一个 Agent 手里。

Q：如何保证审计日志不被 Agent 自己污染？

A：审计写入与 Agent 运行时物理隔离：Agent 只能写自己的 trace span，审计 sink 由独立的 sidecar 或服务消费执行器事件生成，Agent 无写权限。同时审计记录要带决策输入 hash，事后可重算比对，防止记录被篡改或缺失。

02主动式 Agent 的事件入口：重复投递与事件风暴下如何做到不丢不重

进阶 ｜ event-drivenmcp-triggers幂等背压 ｜ 面经来源 ↗

为什么会有这个问题

MCP Triggers / Events 让 Agent 从被动响应变成主动感知，但事件源本身就是 at-least-once：webhook 会重投，队列会重放，文件监听会乱序。Agent 的触发不像普通消费者那样天然幂等——一次触发往往引发多次工具调用和写副作用，而且推理成本远高于一次普通的消息处理。最常见的错误认知是把「消息去重」等同于「触发去重」：一个 PR 在十分钟内推了十次，去重键各不相同，于是十次全都放行。反过来，用时间戳做去重键又会把合法的两次变更合并掉，造成丢事件。加上事件风暴时的无限堆积，最终表现为重复评论、API 限流、任务雪崩。

怎么做

  1. 事件规范化：统一成 {source, resource_id, version, payload}，用 source + resource_id + version 构造 dedup_key，落 Redis/DB 做 SETNX 带 TTL。优先用单调递增的 version 而不是 timestamp，避免时钟与乱序问题。
  2. 资源级防抖与聚合：同一 resource 在静默窗口内只保留最终态，窗口结束回捞一次；对持续高频的资源设窗口上限，超时强制 flush，防止永远等不到静默期。
  3. 触发与执行解耦：事件先转成触发决策，再入队为任务，任务 ID 复用 dedup_key；worker 侧再做一次幂等检查，做到 at-least-once + 幂等 = 业务上的 effectively-once。
  4. 背压与配额：按 tenant / agent 维度做令牌桶，队列水位超阈值时降级为摘要触发或直接丢弃并打点，绝不允许无限堆积。丢弃要可解释，记录 dropped 原因。
  5. 可观测：trace 从 event_id 贯穿到工具调用；分别统计 duplicate、debounced、dropped、executed 四类计数，用这些比例反过来调窗口与配额，而不是拍脑袋定参数。
import hashlib, time def dedup_key(event) -> str: raw = f"{event.source}:{event.resource_id}:{event.version}" return hashlib.sha1(raw.encode()).hexdigest() async def on_event(event, store, queue, window=30.0): if not await store.setnx(dedup_key(event), 1, ttl=86400): return "duplicate" await store.upsert_pending(event.resource_id, event, ttl=window * 4) await queue.enqueue_delayed( task_id=f"flush:{event.resource_id}:{int(event.ts // window)}", delay=window, payload={"resource_id": event.resource_id}, ) return "accepted" async def flush(resource_id, store, queue): event = await store.pop_pending(resource_id) if event is None: return "noop" await queue.enqueue(task_id=f"run:{dedup_key(event)}", payload=event.payload) return "enqueued" async def worker(task, agent): if await task.store.seen(task.task_id): return "skip" await task.store.mark(task.task_id) return await agent.run(task.payload)

真实场景

某项目接了代码仓库 webhook 来触发代码评审 Agent。凌晨一次批量 rebase 造成事件风暴，同一分支短时间内涌入大量 push 事件，去重键各不同，Agent 为同一分支起了几十个评审任务，重复刷评论并撞上模型 API 限流；同时有用户反馈部分变更没有触发评审，排查发现去重键里用了 timestamp，同一秒内的两次不同变更被误判为重复丢弃。修复路径：去重键换成 version、加资源级静默窗口聚合、入队任务 ID 复用 dedup_key、worker 二次幂等，并在网关加租户令牌桶与 dropped 打点。

面试官追问

Q：静默窗口设多长，依据什么定？

A：按资源的自然收敛时间和事件间隔分布来定：观察同一 resource 的 P95 事件间隔，窗口取略大于该值，并设置窗口上限兜底长尾。上线后看 debounced 与 dropped 的比例以及「用户感知延迟」两个指标互相校正，不要一次拍死。

Q：事件乱序或者版本回退时怎么处理？

A：用 version 单调比较：低于资源已处理版本的直接丢弃并计数 stale_event；无法比较版本的源，在资源维度维护状态机，只接受合法的状态跃迁，非法跃迁记录并告警，避免用「最后到达者胜出」这种隐式规则。

03MCP Server 独立发版后工具 schema 漂移：Registry 升级把线上 Agent 批量打挂，如何做契约兼容与快速止血

资深 ｜ MCP工具契约灰度发布故障定位 ｜ 面经来源 ↗

为什么会有这个问题

MCP 把工具能力外置成独立服务后，Server 的发版节奏和 Agent 的解耦了，但 Agent 侧真正依赖的是 tools/list 返回的 name、description、inputSchema 三件套。现实中 Server 发版常顺手改字段名、把可选字段改成必填、收窄枚举或改返回结构，而 Agent 侧要么在会话开始时拉一次工具清单并长缓存（甚至写进 prompt cache），要么按 tool name 做本地路由表，根本没有版本语义可以感知变化。常见错误认知是「Registry 里写了版本号就安全」——实际客户端多数按 name 拉 latest，或者 pin 了 Server 版本却没 pin 工具契约，模型看到的仍是旧描述、生成的仍是旧参数，执行层直接校验失败。更糟的是失败被当成「模型不会用工具」，于是加 prompt、加 few-shot，把问题越掩盖越深。

怎么做

  1. 把工具契约变成可 diff 的 artifact：每次发布前抓 tools/list 快照存进 git，CI 对新旧快照做结构化 diff，并把差异分级（必填新增、枚举收窄、类型变更、字段重命名为 breaking；可选字段新增、枚举扩展、返回字段新增为非 breaking），breaking 未声明就直接卡发布。
  2. 运行时显式寻址 + 版本锁：工具引用写成 server@version#tool=name 的形式，禁止隐式 latest；同时保证 N-1 版本与 N 版本并行可路由，为蓝绿/回滚留出物理条件。
  3. 执行层强校验替代模型自觉：tool call 前用 JSON Schema / pydantic 校验 arguments，失败第一次把校验错误回灌给模型做一次自愈重试，第二次仍失败则抛结构化错误并降级（走兜底工具或转人工），避免重试风暴。
  4. 按版本灰度放量：新版本先路由到小比例会话，观测 tool_call 失败率、参数校验失败率、平均重试轮次、任务完成率四个指标，任何一项劣化立即把路由切回 N-1。
  5. 发布纪律写进规范：破坏性变更必须换 tool name（search → search_v2）而不是原地改，让模型描述和路由表都能区分；字段只增不删，必填只能从「有默认值的可选字段」升级而来。
import math from jsonschema import Draft202012Validator def diff_tools(old, new): issues = [] for name, nt in new.items(): ot = old.get(name) if ot is None: issues.append(f'added_tool:{name}') continue o, n = ot['inputSchema'], nt['inputSchema'] added = set(n.get('required', [])) - set(o.get('required', [])) if added: issues.append(f'required_added:{name}:{sorted(added)}') for k, nv in n.get('properties', {}).items(): ov = o.get('properties', {}).get(k, {}) if ov.get('enum') and set(nv.get('enum', [])) < set(ov['enum']): issues.append(f'enum_narrowed:{name}.{k}') if ov.get('type') and nv.get('type') != ov['type']: issues.append(f'type_changed:{name}.{k}') return issues def call_tool(registry, tool_ref, args, retries=0): version, name = tool_ref.split('#tool=') schema = registry.schema(version, name) errs = [e.message for e in Draft202012Validator(schema['inputSchema']).iter_errors(args)] if errs and retries < 1: return registry.reask(name, errs) if errs: raise ToolContractError(tool_ref, errs) return registry.invoke(version, name, args)

真实场景

某项目把知识检索类 MCP Server 从 1.3 升到 1.4，把 query 字段改名为 q，并新增必填的 scope。Agent 侧工具清单有十分钟 TTL 缓存，prompt 里还是旧描述。发布后短时间内 tool_call 失败率明显跳升，日志里集中出现 'scope' is a required property 与 unknown field query，模型重试一到两轮后开始绕开工具、凭记忆直接作答，用户看到的症状是「答得挺顺但引用了不存在的文档」。排查路径：先按 tool name 与 server 版本二维打点，定位失败集中在单一 Server 的新版本 → 取出两版 tools/list 快照做 diff，确认是 breaking 变更 → 路由整体切回 1.3 止血 → 事后改成版本显式寻址 + 蓝绿并行，并把 schema diff 加进 CI 门禁。

面试官追问

Q：为什么不让模型自己适配新 schema，非要客户端做校验和版本路由？

A：模型每次会话只看到一次工具描述，长尾会话仍跑在旧描述上，而且工具多时描述本身占大量 token，不可能频繁刷新；依赖模型自愈会带来重试放大、延迟上升和偶发的「假装调用成功」。执行层校验是确定性的，能立刻把问题变成可观测的失败率指标，而版本路由是唯一能在分钟级止血的手段。

Q：你用什么标准判定一次 schema 变更是 breaking？

A：用「旧客户端按旧 schema 生成的合法参数，在新 schema 下是否仍然合法且语义不变」来判定：必填字段增加、枚举收窄、类型变更、字段重命名、返回结构删字段都算 breaking；可选字段新增、枚举扩展、返回字段新增、描述文案调整不算。无法判断语义是否变化时，一律按 breaking 处理，换新 tool name 并行发布。

04多模态 Agent 把截图原样塞进上下文：视觉 token 膨胀、历史重放与分辨率取舍怎么治

进阶 ｜ 多模态上下文预算成本优化VLM ｜ 面经来源 ↗

为什么会有这个问题

VLM 的图像成本不是常数，而是由分辨率与切块策略决定（切块数乘以每块 token，再加基础开销），同一张图在不同 provider 上可能差出数倍。真实痛点是 Agent 多轮循环里每一步都产生新截图，而多数实现是直接把图片 base64 append 进 messages 且从不裁剪历史，于是每一轮都把全部历史图像重新送一遍，token 随轮次近似平方增长，延迟和费用同步放大，最终撞上下文上限。更隐蔽的问题是盲目压缩：把整图等比缩小后小字、图标、禁用态读不出来，模型「看到但读不准」，表现为参数编造或反复点同一个位置。常见错误认知是「一张图就是一次性的固定成本」，以及「降分辨率总是省钱的」——实际上裁剪比缩放更省也更准。

怎么做

  1. 先量化再优化：按 provider 的图像计费规则写一个估算函数（宽高、切块大小、每块 token），给每个会话设 image_token_budget，超出即拒绝注入新图或强制压缩，把预算变成硬约束而不是事后看账单。
  2. 把图像从消息体里挪出去做 artifact：工具产出的截图落到对象存储，返回 artifact_id 加尺寸元数据和 OCR/结构摘要；默认进上下文的是摘要与引用，模型需要细节时再通过 view_artifact 主动取图。
  3. 按任务选表示层级：文字密集的表格、表单用高分辨率加区域裁剪（先定位目标 bounding box 再裁，token 少且识别准）；布局与场景理解用低分辨率整图；不要用整图缩放代替裁剪。
  4. 历史压缩：轮次结束后把图像替换成带 id 的文本占位，仅保留最近一到两张原图，保证可回溯但不再重复计费。
  5. 监控四个指标：每会话 image token 占比、上下文占用率峰值、因超限触发的截断或重试次数、含图会话的任务完成率与纯文本会话的差值；用任务完成率而不是「接口有没有报错」来判断压缩是否伤精度。

真实场景

面试官追问

Q：既然图像这么贵，为什么不干脆只把 OCR 文本给模型？

A：OCR 丢掉了布局、图标、颜色状态（禁用、报错、选中）和相对位置，在 UI 定位与表单校验这类任务上精度明显下降，而且视觉模型对坐标的推理依赖图像本身。正确做法是分层：默认给结构化摘要与元素坐标文本，留一个 view_artifact 让模型在不确定时主动请求裁剪图，把图像成本花在真正需要看的局部。

Q：怎么证明降分辨率或裁剪没有伤害准确率？

A：离线构造带标注的关键区域集（含小字、密集表格、灰色禁用按钮），对每一档分辨率与裁剪策略跑端到端任务成功率与关键字段抽取准确率，画出分辨率到成功率的曲线找拐点，拐点以下不采用；线上用 A/B 看任务完成率与平均步数，而不是只看单次调用有没有异常。

05多路召回里某一路超时后 RRF 融合结果悄悄变差：分路预算、缺失标记与降级怎么落地

资深 ｜ 多路召回RRF降级可观测性 ｜ 面经来源 ↗

为什么会有这个问题

多路召回通常把向量、BM25、图谱等异构召回器并发执行，再用 RRF 按排名融合。RRF 只看名次，不关心某一路是否因为超时、限流或异常返回空列表，所以单路失败不会让接口报错，却会让融合后的候选集悄悄偏向剩余路径。常见错误是只监控总 p95 延迟和接口错误率，不记录 per-path 的召回数量、失败状态与耗时；空结果和失败结果被同等对待，长尾 query 的召回覆盖先下降，最终表现为答案变窄但无人告警。

怎么做

  1. 给每条召回路定义独立超时预算和 SLO：从总检索预算反推，例如总 300ms，向量 120ms、BM25 80ms、图谱 60ms，融合与重排预留剩余时间；超时不是异常抛出，而是返回带 status 的结构化结果。
  2. 融合层显式携带 degraded 标记：区分 ok、timeout、error、empty 四种状态；缺失路不参与 RRF 计分，记录 per-path hit rate、empty rate、p99 延迟和融合前后 top-k 重叠率。
  3. RRF 实现保持简单：score = sum(weight / (k + rank))，对 chunk 按 doc_id + 内容指纹去重；每路设置 topN 配额，避免某一路召回数量过大主导融合；不要直接把不同召回器的原始分数加权平均。
  4. 对高贡献路径设置熔断与 fallback：单路失败率连续超过阈值时告警并降级到缓存结果或单路检索；用故障注入回归测试验证单路超时后的答案质量下降在可接受范围内。
  5. 按查询类型调整路径权重：精确术语查询提高 BM25 权重，语义问法提高向量权重，关系型问题提高图谱权重；权重来自离线评估，不在线用 LLM 动态调参。
  6. 把路由与融合决策写入 trace：记录 query 类型、各路 topN、状态、耗时、融合后 top-k 变化，便于事后定位是召回缺失还是生成问题。
import asyncio, hashlib from dataclasses import dataclass @dataclass class Hit: doc_id: str text: str rank: int = 0 async def run_path(name, fn, query, timeout, weight): try: items = await asyncio.wait_for(fn(query), timeout) return name, weight, items, 'ok', timeout except asyncio.TimeoutError: return name, weight, [], 'timeout', timeout def rrf(path_results, k=60, limit=20): scores, store, degraded = {}, {}, [] for name, weight, items, status, _ in path_results: if status != 'ok': degraded.append(name) for rank, hit in enumerate(items, 1): key = hashlib.md5((hit.doc_id + hit.text[:64]).encode()).hexdigest() store[key] = hit scores[key] = scores.get(key, 0.0) + weight / (k + rank) ranked = sorted(scores.items(), key=lambda x: -x[1])[:limit] return [store[key] for key, _ in ranked], degraded async def search(query, paths): results = await asyncio.gather(*[ run_path(name, fn, query, timeout, weight) for name, fn, timeout, weight in paths ]) hits, degraded = rrf(results) return {'hits': hits, 'degraded': degraded}

真实场景

面试官追问

Q：RRF 和加权分数融合应该怎么选？

A：异构召回器的分数量纲和分布通常不可比，RRF 只用排名，冷启动和线上漂移更稳；加权分数融合需要归一化或学习校准，维护成本高。可以先用 RRF 融合，再用轻量 rerank 统一打分。

Q：单路超时阈值怎么定才合理？

A：从总检索预算反推，结合每路 p99 延迟和对最终答案的离线贡献度分配；高贡献路给更大预算并设置熔断，低贡献路可快速失败。用故障注入验证不同超时下的召回和答案质量。

06百万 token 长上下文把整本手册塞进 prompt 后成本翻倍且引用对不上：RAG 与长文直塞的路由边界怎么定

资深 ｜ 长上下文成本建模路由引用可验证 ｜ 面经来源 ↗

为什么会有这个问题

长上下文模型扩大了单次可输入的 token 上限，但窗口大小不等于有效可用上下文。把整本手册直接塞进 prompt 会带来 prefill 成本、首 token 延迟、注意力稀释、引用无法回溯和更新不经济等问题。常见错误是用离线 demo 的汇总效果决定线上架构，忽略 prefix cache 需要稳定前缀，文档顺序每次变化导致缓存不命中；引用由模型自由生成，无法映射回原文 section，最终出现答案看似完整但页码和条款对不上。

怎么做

  1. 先做查询分类和路由表：lookup、compare、summarize 三类查询分别评估 RAG、长文直塞、混合模式的效果与成本；路由输入包括候选文档 token 数、更新频率、引用要求和延迟预算。
  2. 建立单请求成本模型：input_tokens × 输入单价 × cache_miss 比例 + output_tokens × 输出单价 + 检索与重排成本；长文直塞要固定文档顺序和前缀以命中 prefix cache，否则每次请求都在重复 prefill。
  3. 长文直塞的工程约束：文档预处理为带 section_id 和 offset 的结构，prompt 中保留可引用 id；超过 token 预算时走 map-reduce 摘要，摘要结果仍保留来源 id；输出流式返回并设置超时降级。
  4. 构建分层评测集：lookup、compare、summarize 分别评估 answer accuracy、citation precision、cost per resolved query、p95 TTFT；用 A/B 路由对比长文直塞和 RAG，不只看窗口大小或单次演示。
  5. 设置回退链路：长文直塞超时或超预算时回退 RAG；RAG 证据不足且查询属于汇总类时再升级长文；每次路由决策记录 mode、token 用量和降级原因。
  6. 按文档更新频率选择策略：高频变更的 FAQ 走 RAG 增量索引，静态手册可长文直塞加 prefix cache；权限过滤仍在检索层完成，不能把无权限文档塞进长上下文。
PRICE_IN = 0.5 / 1_000_000 PRICE_OUT = 2.0 / 1_000_000 RETRIEVAL_COST = 0.0002 def estimate_tokens(text: str) -> int: return max(1, len(text) // 3) def classify(query: str) -> str: if '对比' in query or '区别' in query: return 'compare' if '总结' in query or '汇总' in query: return 'summarize' return 'lookup' def route(query, docs, cache_hit=False): total_tokens = sum(estimate_tokens(d.text) for d in docs) qtype = classify(query) if qtype == 'lookup' or total_tokens > 200_000: return {'mode': 'rag', 'reason': '精确问答或超预算'} input_price = PRICE_IN * (0.1 if cache_hit else 1.0) long_cost = total_tokens * input_price + 600 * PRICE_OUT rag_cost = RETRIEVAL_COST + 8_000 * input_price + 600 * PRICE_OUT if long_cost <= rag_cost * 1.5: return {'mode': 'long_context', 'tokens': total_tokens, 'cost': long_cost} return {'mode': 'rag', 'cost': rag_cost}

真实场景

某项目知识库以产品手册和 FAQ 为主，团队尝试用百万 token 长上下文直接替代检索。离线汇总类问题效果变好，但线上 p95 首 token 延迟上升、单请求成本明显增加，回答中的页码和条款经常对不上。排查发现每次 prompt 的文档顺序不同，prefix cache 基本不命中；引用是模型自由生成而非 section_id 映射；lookup 类问题也被路由到长文直塞。修复后按查询类型路由，固定长文前缀并启用缓存，引用改为 section_id 映射，lookup 回退 RAG，并设置 token 预算和超时降级。

面试官追问

Q：长上下文模型会不会让 RAG 消失？

A：不会。RAG 解决索引、权限、更新、成本和可验证性问题；长上下文是另一种取数方式。更合理的架构是按查询类型和成本在 RAG、长文直塞、混合模式之间路由。

Q：如何避免长文直塞的引用幻觉？

A：预处理保留 section_id 和 offset，要求模型只输出 id，由服务端映射回原文；无 id 或映射失败的引用直接拒答或降级；离线用 citation precision 做回归评估。

07PDF 里的图表和扫描页接进 RAG 后，文本题反而被答错：多模态 Embedding、图片转描述与重嵌入成本怎么取舍

资深 ｜ multimodal-embeddingchunking选型成本建模 ｜ 文档来源 ↗

为什么会有这个问题

线上知识库很少是干净的纯文本：PDF、扫描件、PPT 里大量关键信息在表格、架构图、截图里。纯文本抽取会丢（表格被打散成乱序 token，图片直接丢弃），团队于是想一步到位，把每页渲染成图片、用多模态模型编码后塞进同一个 collection。常见认知错误是「同一维度就能比较」：如果文本块用文本编码器、图片块用另一个多模态编码器，即便维度相同，向量分布也不在同一空间，跨模态相似度没有可比性，阈值和 top-k 全失效；更隐蔽的后果是图片块在高相似区间挤占名额，原本能答对的文本题反而答错。另一条错误路线是只做 OCR 转文本，图表语义丢了，检索命中了也答不出。此外图片的分辨率决定视觉 token 与重嵌入耗时，全量重渲染会把更新链路拖慢一个量级。

怎么做

  1. 先按文档类型和真实 query 意图分层：统计哪些问题必须靠视觉证据（图表数值、版式、示意图），哪些用文本足够；只对前者投入视觉链路，避免全量上图片。
  2. 两条路线并列评估并量化：路线 A 用同一多模态编码器对文本块与图片块编码（同空间可比）；路线 B 用视觉模型把图表转成结构化描述（表格转 markdown、图转要点），与图注、邻近正文一起编码。对比维度固定为：图表类问题的 recall、单文档 ingestion 成本、重嵌入耗时、生成侧视觉 token 成本、可解释性。
  3. 推荐混合落地：图片走多模态向量召回候选，命中后再把原图（按需裁剪、降分辨率）送生成模型；低风险类别（如流程图类问答）用路线 B 的文本描述兜底。
  4. 分块上采用父子结构：图片与其 caption、上下文段落绑定为一个父块，图片向量作为子块，检索命中子块后返回父块全文给生成侧，保证上下文完整。
  5. 存储分层：图片二进制放对象存储，向量库 payload 只放 uri、模态标识、父块 id 与页码，不要把 base64 塞进 payload，否则集合膨胀且影响快照与备份。
  6. 检索端加模态配额（quota）：文本与图片分别检索后再合并，限制图片块最多占 top-k 的一定比例，避免单一模态淹没结果。
  7. 重嵌入与切换：新模态单独建 collection 并影子双跑，用同一套评测集对比「原文本链路」与「新链路」在文本题上的 recall 不掉、图表题 recall 提升，达标再切流量。
  8. 把 ingestion 做成可增量：只对变更页重渲染，记录每页的渲染参数（dpi、裁剪框）作为版本，避免改一次模型就全量重跑。

某项目的产品文档库里约三成页面含表格或架构图，用户高频问「这张表里 A 和 B 的参数差异」「这个流程图里失败分支走哪」。纯文本链路对这类问题经常答成泛泛描述。团队随后把每页渲染成 PNG、用多模态模型编码，与文本块混写同一 collection。上线后典型现象是：图表类问题略有好转，但原先答得对的纯文本题开始答错，且 top-k 里大量是整页图片块；同时每次文档更新都要全量重渲染重编码，更新延迟从小时级变成隔天。排查路径：把评测集按「文本题 / 图表题」拆成两条曲线分别看 recall，再看 top-k 结果里的模态分布与相似度分布，会发现图片块在中间相似度区间堆积，把文本块挤出名额；同时比对文本块与图片块所用编码器是否同一个，确认向量是否同空间可比。

面试官追问

Q：多模态 Embedding 和「图片转文本描述」两条路，你怎么量化选型？

A：用同一套按题型分层的评测集对比：图表数值类、版式理解类、普通文本类分别看 recall 与最终答案正确率；再叠加成本项——图片编码的算力、存储体积、重嵌入耗时，以及生成侧是否必须回传原图（视觉 token 成本）。结论通常不是二选一，而是图片向量负责召回、文本描述负责兜底与可解释，按题型路由。

Q：同一 collection 混模态，怎么防止一类挤占另一类的 top-k？

A：不要让不同模态直接混排：检索时按模态分别查询再做配额合并，或使用 named vector 分字段检索；此外为每个模态单独标定阈值，因为两个编码器（或同编码器不同模态）的相似度分布尺度不同，共用一个阈值必然出现一侧过召回一侧欠召回。

为什么会有这个问题

RAG 的成本与延迟大头在生成侧，语义缓存（对 query 向量做近邻匹配、命中即复用历史答案）是最直接的降本手段。问题在于「query 向量相似」不等于「答案等价」：否定词（要不要 / 需不需要）、时间与版本限定（新政策 vs 旧政策）、实体替换（换成另一个产品名或套餐）、权限范围不同的租户，向量距离都可能很近。常见错误有三类：一是只用单一相似度阈值就上线，没有做实体与约束一致性校验；二是缓存键里只放 query，没带 tenant、知识库版本、prompt 与模型版本，导致越权复用和版本漂移；三是失效策略只有统一 TTL，知识库更新后旧答案还会继续回放很久。另一个隐性错误是把「命中率」当收益指标，没有扣掉命中后的差评与不一致率。

怎么做

  1. 明确缓存作用域（scope）：归一化后的 query + tenant_id + 权限范围 + 知识库版本 + 模型/prompt 版本，任一维度变化一律视为未命中，从结构上杜绝越权与版本漂移。
  2. 做两级判定：先向量近邻取 top-n 候选，再对候选做约束一致性校验——数字、日期、专有实体、否定词方向是否一致，不一致直接跳过，宁可回源。
  3. 阈值不靠拍脑袋：构建等价/不等价 query 对标注集，扫阈值看 precision-recall 曲线，按业务错答成本定阈值；高风险类目（计费、合规、合同条款）直接禁用缓存或要求近乎文本级匹配。
  4. 定向失效：缓存条目记录其答案引用的 doc_id/chunk_id 集合，文档更新时反查受影响的条目批量删除；统一 TTL 只作为兜底，不作为主要手段。
  5. 影子与灰度：先以影子模式只记录「若命中则返回什么」，与线上实时答案比对，统计不一致率与差评率，再放量到低风险类目。
  6. 观测口径：同时看命中率、命中后的负反馈率、缓存答案与实时答案的一致率、以及分租户的命中分布，避免某一租户命中异常。
  7. 降级设计：缓存层超时或不可用时直接跳过，主链路不受影响；缓存写入异步化，不阻塞首字节响应。
SCOPE = ("tenant_id", "kb_version", "prompt_version") def lookup(q, ctx): cat = classify(q) if cat in NO_CACHE_CATEGORIES: return None cands = idx.search(embed(normalize(q)), k=5, flt={k: ctx[k] for k in SCOPE}) for c in cands: if c.score < THRESHOLD[cat]: continue if not constraints_ok(normalize(q), c.query): continue return CacheHit(answer=c.answer, cite=c.cited_doc_ids) return None def constraints_ok(qn, cn): if has_negation(qn) != has_negation(cn): return False return extract_slots(qn) == extract_slots(cn) def invalidate(doc_ids): for e in idx.scan(flt={"cited_doc_ids": {"any": doc_ids}}): idx.delete(e.id)

真实场景

某项目的问答接口在高峰期成本压力大，接入语义缓存后整体调用量与平均延迟明显下降。随后客服侧反馈两类问题：政策类问题返回的是旧版本说法；个别客户看到明显属于其他客户的方案细节。排查路径：先抽查被判为命中的样本，会发现两条 query 仅产品名不同但相似度远高于设定阈值；再查缓存 payload，发现缓存键里没有 tenant 与知识库版本字段；最后查失效链路，文档更新后条目仍在，只能等统一 TTL 过期。关键指标是对比「缓存答案」与「强制回源答案」的不一致率，以及命中样本的负反馈率——命中率上升但这两个指标同步恶化，说明阈值与 scope 设计有问题，而不是缓存本身不该用。

面试官追问

Q：命中率涨了但差评也涨了，怎么确认是缓存导致的？

A：做两组对照：一是影子回源，对命中样本同时算一次实时答案，比对不一致率并按类目拆分；二是按是否命中分桶看负反馈率，若命中桶显著高于未命中桶且集中在特定类目（政策、价格、权限相关），即可归因。再抽不一致样本看相似度分布，判断是阈值过低还是 scope 缺字段。

Q：文档更新后，怎么让相关缓存条目及时失效而不是等 TTL？

A：在缓存条目里落答案的引用来源（doc_id/chunk_id），知识库更新事件触发时按来源反查删除；对无法精确归因的条目按知识库版本整体提升 version 使旧条目自然失效（scope 不匹配），TTL 只做兜底。同时保留一个可开关的「高风险类目不走缓存」白名单用于事故止血。

FastAPI 专题

09流式响应发出 200 后上游报错：SSE 错误帧、结束标记与断开感知怎么补

资深 ｜ StreamingResponseSSE异常处理LLM 流式

为什么会有这个问题

StreamingResponse 一旦开始发送，HTTP 状态码和 headers 已经写给客户端；如果异常发生在 async generator 内部，Starlette 无法再把响应改成 500，全局 exception_handler 也不会按预期接管。常见错误是直接在 generator 里 raise HTTPException，或者只依赖连接关闭表示结束。结果是客户端收到 200 加半截内容，把截断当正常完成；服务端 5xx 指标几乎不动，但用户重复提交、上游 token 继续计费。

怎么做

  1. 先定协议：流内至少区分 token、error、done 三类事件，done 是唯一成功结束标志；error 帧带 code、retryable、request_id，客户端据此决定重试还是提示。
  2. 在 generator 内部 try/except：上游异常转成 error 帧后正常结束，不要 raise；finally 里关闭上游流并记录 usage，避免已断开还在计费。
  3. 显式感知断开：循环中检查 request.is_disconnected()，并捕获 asyncio.CancelledError；断开时 cancel 上游任务，不要只等 finally。
  4. 处理代理缓冲：返回 text/event-stream，设置 Cache-Control: no-cache、X-Accel-Buffering: no，对 event-stream 关闭 gzip，并周期性发心跳注释帧。
  5. 观测口径：单独统计首 token 延迟、流时长、error 帧比例、客户端断开率；不要把流内 error 混进 5xx 告警，否则故障不可见。
from fastapi import FastAPI, Request from fastapi.responses import StreamingResponse import asyncio, json app = FastAPI() async def gen(req: Request, prompt: str): upstream = None try: upstream = await open_llm_stream(prompt) async for token in upstream: if await req.is_disconnected(): break yield 'data: ' + json.dumps({'type': 'token', 't': token}, ensure_ascii=False) + '\n\n' yield 'data: ' + json.dumps({'type': 'done'}) + '\n\n' except asyncio.CancelledError: raise except Exception as e: yield 'data: ' + json.dumps({'type': 'error', 'retryable': True, 'msg': str(e)[:200]}) + '\n\n' finally: if upstream is not None: await upstream.aclose() @app.get('/chat/stream') async def chat_stream(request: Request, q: str): return StreamingResponse( gen(request, q), media_type='text/event-stream', headers={'Cache-Control': 'no-cache', 'X-Accel-Buffering': 'no'}, )

真实场景

某项目的 LLM 流式接口偶发上游 429 或读超时。前端表现为 HTTP 200、答案输出到一半后 loading 不结束；服务端 5xx 指标接近零，网关只看到连接被重置。用户以为失败重复提交，费用和下游压力一起上涨。排查路径：先确认流式响应状态码始终是 200，再在 generator 内打点看异常是否被抛出，检查客户端是否以 done 帧作为完成条件，最后看断开后上游 stream 是否被 aclose/cancel。

面试官追问

Q：流式接口还能做上游重试吗？

A：只能在首 token 发出前重试：用有限次数加指数退避和 jitter，并设置总预算；一旦已经 yield token 就不能透明重试，否则客户端会收到重复内容，正确做法是发 error 帧让客户端带 request_id 重新生成，计费侧用幂等键去重。

Q：为什么本地 curl 能看到流，线上经过网关就变成一次性返回？

A：常见是代理缓冲和压缩：Nginx 默认 proxy_buffering 会攒包，gzip 也会缓冲 event-stream；需要关闭对应缓冲、设置 X-Accel-Buffering: no，并保证读超时大于心跳间隔。还要注意长连接会占用 worker，流式接口最好独立部署或限制并发。

10每个请求都新建 AsyncClient：连接池复用失效、TIME_WAIT 飙升与多 worker 配额失控

进阶 ｜ lifespanhttpx.AsyncClient连接池多进程部署

为什么会有这个问题

httpx.AsyncClient 不是轻量对象，它内部维护连接池、keep-alive 和 TLS 会话。如果在每个 handler 或每个请求的依赖里 async with AsyncClient()，连接无法复用，TCP/TLS 握手成本被摊到每次调用上，容易出现 TIME_WAIT 堆积和 P99 抖动。更隐蔽的是多 worker 部署：每个进程各有一份池，总连接数约等于 workers 乘 pool_size，扩容 worker 反而可能打爆下游连接配额或触发限流。常见错误认知是“用了 async 就一定快”，忽略客户端生命周期和配额。

怎么做

  1. 在 lifespan 中创建共享 AsyncClient，写入 app.state；shutdown 时 await aclose()，保证在同一个事件循环内创建和关闭。
  2. 用依赖 get_http(request) 返回同一实例；禁止在请求内 new client；不同下游按 base_url 分池，避免一个慢下游占满所有连接。
  3. 按下游配额反推 limits：workers 乘 max_connections 要小于下游连接上限并留安全余量；max_keepalive_connections 和 keepalive_expiry 要对齐下游 idle timeout。
  4. 超时要拆开：connect、read、write、pool 分别设置；pool timeout 要短，快速失败并暴露连接池等待指标，而不是让请求无限排队。
  5. 多 worker 下的限流、缓存、计数器不能只用进程内状态；需要 Redis 或网关集中限流，readiness 检查依赖可用性，滚动发布时避免流量打到未初始化完的 worker。
from contextlib import asynccontextmanager from fastapi import FastAPI, Depends, Request import httpx @asynccontextmanager async def lifespan(app: FastAPI): app.state.http = httpx.AsyncClient( limits=httpx.Limits(max_connections=50, max_keepalive_connections=20, keepalive_expiry=30), timeout=httpx.Timeout(connect=1.0, read=10.0, write=5.0, pool=0.5), ) try: yield finally: await app.state.http.aclose() app = FastAPI(lifespan=lifespan) def get_http(request: Request) -> httpx.AsyncClient: return request.app.state.http @app.get('/proxy') async def proxy(http: httpx.AsyncClient = Depends(get_http)): r = await http.get('https://downstream.example/api') return r.json()

真实场景

某项目把内部服务调用写成每个接口里 async with httpx.AsyncClient()。流量上来后下游看到大量短连接，服务端 TIME_WAIT 升高，TLS 握手 CPU 上升，P99 从几十毫秒抖到几百毫秒；扩容 worker 后下游连接数按进程数成倍增长，开始出现 429 和连接拒绝。排查路径：看 netstat 的 TIME_WAIT、下游按来源 IP 的连接数、应用日志里的 pool timeout，再对照 workers 与 pool_size 的乘积；修复为 lifespan 共享 client 并调整 limits 后，连接数和 P99 才稳定。

面试官追问

Q：为什么不直接把 AsyncClient 定义成模块级全局变量？

A：模块导入时创建可能不在目标事件循环里，测试或多 loop 场景容易踩 attached to a different loop；而且没有明确的关闭时机。lifespan 能保证在应用启动的事件循环内创建、在 shutdown 时关闭，测试里也更容易用依赖覆盖或 lifespan 管理。

Q：多 worker 下想做全局限流，进程内令牌桶为什么不够？

A：每个 worker 独立计数，实际总速率是 workers 乘单进程限额；worker 重启还会清零。要么把限额按 worker 数分摊并留余量，要么用 Redis 或网关做集中限流；同时 readiness 要检查下游依赖，避免滚动发布时新 worker 还没建好连接池就接流量。
